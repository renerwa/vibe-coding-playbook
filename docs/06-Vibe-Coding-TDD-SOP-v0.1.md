# Vibe Coding TDD SOP v0.1

> 用途：给“用 AI 开发项目”提供一套可执行、可检查、可复盘的 TDD 工作流。
> 状态：v0.1，先用一个真实小任务试运行，再根据实际成本调整。
> 最后更新：2026-11-06
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[TDD 开发模式](01-TDD开发模式.md)、[Vibe Coding 中的 TDD 工作流](02-Vibe-Coding中的TDD工作流.md)。
> 不覆盖：测试运行器内部机制、具体项目架构、多 Agent 调度细节。

## 一句话结论

这套 SOP 的核心不是“让 AI 多写测试”，而是：

> **人定义正确，Agent 实现并验证，测试充当可执行合同，人工负责最终验收。**

它的目标不是追求 100% 覆盖率，而是让每个重要行为都有明确的验收依据，让 AI 不能靠“看起来做完了”自行宣布完成。

## 适用范围

| 场景 | 适用程度 | 建议 |
|---|---|---|
| 稳定的业务规则 | 高 | 默认使用本 SOP |
| API 契约、数据转换 | 高 | 先定义请求、响应和异常行为 |
| Bug 修复 | 高 | 先写复现测试，再修复 |
| 数据库、权限、金额等高风险逻辑 | 高 | 加严验证，必要时增加集成测试和独立审查 |
| 老项目改造 | 中高 | 先补保护性测试，再修改行为 |
| 页面交互 | 中 | 测试关键行为，视觉和体验由人工验收 |
| 需求探索、一次性原型 | 中低 | 可以先做 spike，但不要当作生产实现 |
| 纯视觉设计、主观体验 | 低 | 以人工评审为主，不为“好不好看”强行写测试 |

## 术语速查

| 术语 | 一句话解释 | 在本 SOP 中怎么用 |
|---|---|---|
| 单元测试 | 直接验证一个小模块或函数的测试 | 适合稳定、纯粹的业务规则 |
| 集成测试 | 验证多个模块、数据库或 API 组合后的行为 | 适合验证真实协作边界 |
| 端到端测试（E2E） | 从用户入口走完整流程的测试 | 只覆盖少量关键用户旅程 |
| 契约测试 | 检查服务之间的请求、响应和错误约定是否一致 | 适合前后端或微服务接口 |
| 冒烟测试 | 用少量关键检查快速确认系统“基本能跑” | 适合部署后或联调前快速验证 |
| characterization test | 给现有系统拍行为快照，固定当前行为 | 适合老项目改造前建立安全网 |
| spike | 为验证技术方向而做的一次性试验 | 结果可用于决策，代码不直接当生产实现 |
| CI（持续集成） | 每次提交后自动运行测试和检查 | 项目稳定后再接入，不要求一开始就上 |
| 快照测试 | 保存当前输出作为基准，之后比对是否变化 | 适合稳定的结构性输出，不代替视觉和业务判断 |
| 幂等 | 同一操作重复执行不会产生额外副作用 | 支付、重试、消息处理等场景要重点验证 |

## 三条不可省的原则

1. **先定义正确，再实现**：重要行为必须有测试或明确的验收方式。
2. **先看到合理的失败**：测试要真实失败，失败原因应当是“功能尚未实现”，而不是环境、语法或测试本身写错。
3. **人工审查测试合同**：实现可以变，但测试描述的业务行为不能由 Agent 偷偷改掉。

## 三个可以按需调整的点

1. **不要求 100% 覆盖率**：覆盖核心规则、边界和异常即可，按风险分配测试成本。
2. **不要求每轮都重构**：代码清楚、没有明显重复和设计问题时，可以跳过重构。
3. **不要求一开始就上 CI**：项目初期先固定一条可复现的本地测试命令，稳定后再接入持续集成。

## 关键概念澄清

### 1. 一个行为，不是一行代码

TDD 的循环单位是“可观察的行为”，不是“改了哪一行代码”。

- 行为：金额满 100 元时减免 10 元；
- 场景：120 元、100 元、99.99 元、负数金额；
- 测试用例：每个场景对应一组输入和预期输出；
- 测试组：同一个行为下的一组测试。

因此，更准确的说法是：

> 一个最小行为对应一组代表性场景测试，而不是“一个测试包含所有场景”。

### 2. “最小实现”限制的是范围，不是代码质量

最小实现不等于：

- 故意写一版很差的代码；
- 只针对当前测试断言写特判；
- 把所有未来可能用到的逻辑一次性写上。

它等于：

> 只实现当前已确认的行为范围，不顺手扩展未定义功能；在范围内写出清晰、可维护的实现。

如果实现过程中发现有逻辑确实属于当前任务，但测试没有覆盖，正确做法不是偷偷写进代码，而是先补验收场景和测试，再继续实现。

### 3. 严格 TDD 与 AI 协作流程不是一回事

严格 TDD 的核心循环是：

```text
红：新增或修改一个失败测试 → 运行并确认失败
绿：写实现让测试通过 → 运行确认通过
重构：改善结构 → 再运行测试
```

在 AI 协作中，为了便于人工审查，可以增加一个外部关卡：

```text
Agent 只写测试 → 停下来 → 人工审查 → Agent 再实现
```

“只写测试并停下来”不是 TDD 的第四个阶段，而是 AI 场景下的协作控制点。

## 任务分级

不是所有任务都值得走完整流程。先给任务定级，再决定测试强度。

| 等级 | 典型任务 | 测试要求 | 人工关卡 | 验证强度 |
|---|---|---|---|---|
| L0 轻量 | 文案、格式、改名、无行为变化的配置调整 | 不新增测试；运行相关检查或测试 | 看差异 | 轻量 |
| L1 小任务 | 单个低风险规则、小型修 Bug | 至少一个失败测试或复现测试 | 审查测试 + 目标测试 | 标准 |
| L2 标准功能 | 新业务规则、API、数据转换、一般页面交互 | 正常、边界、异常等代表性场景 | 审查测试 + 目标测试 + 完整测试集 + 人工验收 | 较完整 |
| L3 高风险 | 金额、权限、数据迁移、并发、外部支付、数据一致性 | 在 L2 基础上增加集成、契约或专项检查 | 独立审查 + 完整回归 + 人工验收 + 回滚方案 | 严格 |
| P0 探索 | 技术验证、一次性原型、方向不确定的 spike（一次性技术试验） | 不强制 TDD，但必须标明“非生产代码” | 人工判断是否继续 | 先验证方向 |

判断规则：

- 只是改变代码结构、不改变外部行为：可以只依赖现有测试；
- 新增或改变可观察行为：先补测试；
- 修 Bug：先写能复现 Bug 的失败测试；
- 不确定技术方案：先 spike，确认方向后，正式实现仍按 TDD 写；
- 高风险路径：不要只靠一个单元测试，要增加更接近真实环境的验证。

## 主流程

### 第 0 步：准备测试基线

在开始写业务代码前，先确认：

- 项目的测试命令是什么；
- 当前测试是否本来就能正常运行；
- 哪些失败是本次改动之前就存在的；
- 本次需要跑哪一层测试：单元、集成、端到端或人工验收。

产出物：

- 可复制的测试命令；
- 当前基线结果；
- 已存在的失败或环境问题记录。

如果测试环境本身不可用，先修环境。不要把环境错误误判成“功能尚未实现”的红灯。

### 第 1 步：切出一个最小行为

只选择一个可以独立验收的行为，写清：

- 一句话目标；
- 输入和输出；
- 本次明确不做什么；
- 不能改动的接口、数据或兼容性要求。

不要一次处理“完整订单系统”。先处理“金额满 100 元减 10 元”这类可验收的单元。

产出物：行为卡，建议包含“目标、范围、不包含、风险”。

### 第 2 步：定义代表性验收场景

至少考虑三类场景：

- 正常情况：最常见、最有业务价值的路径；
- 边界情况：刚好等于阈值、空值、最大值、最小值；
- 异常情况：非法输入、缺少权限、外部服务失败、重复操作。

不需要穷举所有输入。选择能代表一类情况的例子即可。高风险功能再增加并发、幂等、安全或数据一致性场景。

同时决定测试层级：

- 纯业务规则：优先单元测试；
- 数据库、API、模块协作：优先集成测试；
- 关键用户旅程：少量端到端测试；
- 视觉、体验和主观判断：人工验收。

产出物：验收例子表，以及每个例子对应的测试层级。

### 第 3 步：让 Agent 只写测试

要求 Agent：

- 只新增或修改测试，不修改业务实现；
- 遵循项目现有测试目录和命名约定；
- 复用已有测试工具，不擅自引入新框架；
- 运行相关测试，展示真实失败输出；
- 逐条说明测试与验收场景的对应关系。

说明：

- 严格 TDD 可以一次只推进一个测试；
- AI 协作中，可以把同一个行为的几个代表性测试一起写出来再审查，但不要跨多个行为打包；
- 测试写完后先停下来，等待人工确认。

产出物：测试改动、测试命令、失败输出、场景映射说明。

### 第 4 步：人工审查测试

这里审查的不是“测试有没有跑”，而是“测试有没有测对”。

重点检查：

1. 是否覆盖了已确认的正常、边界、异常场景；
2. 断言是否检查业务结果，而不是绑定内部实现；
3. 是否存在一个测试同时检查太多行为；
4. 测试名称是否能说明业务含义；
5. 失败原因是否是“功能尚未实现”，而不是语法、路径或依赖错误；
6. 是否为了让测试通过而提前弱化预期。

如果测试本身写错，先修测试，不要急着进入实现。

产出物：人工确认结论；必要时补充或修正测试。

### 第 5 步：让 Agent 写实现

确认测试合理后，再要求 Agent 修改业务代码。

实现阶段的要求：

- 只实现当前行为范围内的逻辑；
- 不修改、跳过、弱化或删除测试预期；
- 在范围内写清晰、可维护的代码，不为“最小”而故意写临时代码；
- 发现测试遗漏或需求矛盾时停下来，不要擅自扩大范围；
- 先运行目标测试，再运行完整测试集；
- 汇报修改文件、关键取舍、命令、结果和退出码。

产出物：业务代码改动、目标测试结果、完整测试结果。

### 第 6 步：按需重构

重构不是每轮必做。只在出现以下情况时进行：

- 重复逻辑明显；
- 命名或职责不清；
- 函数过长或耦合过重；
- 实现虽然能通过测试，但明显难以维护。

重构约束：

- 不改变外部行为；
- 不修改测试预期；
- 每次小步修改后重新运行测试；
- 如果重构需要改变接口或业务行为，停下来，当作新任务处理。

产出物：重构说明、重构后的完整测试结果。

### 第 7 步：人工验收并记录证据

自动化测试通过后，还要验证测试难以覆盖的部分：

- 关键用户流程是否真的能完成；
- 错误提示是否可理解；
- 权限、数据隔离和业务规则是否符合预期；
- 真实外部服务或页面体验是否正常；
- 是否存在“技术上通过、产品上不可用”的情况。

最终至少保留：

- 验收条件；
- 实际执行的测试命令；
- 通过数量、失败信息和退出码；
- 人工验收结论；
- 剩余风险和未覆盖内容。

## 测试范围与覆盖率策略

### 不需要穷举，也不需要 100%

覆盖率是诊断工具，不是 KPI。100% 行覆盖率仍然可能漏掉业务错误，也可能诱导团队为无意义的代码写测试。

建议按风险分配：

| 区域 | 建议强度 |
|---|---|
| 核心业务规则 | 覆盖主要正常、边界和异常路径 |
| 金额、权限、数据一致性 | 加严覆盖，必要时增加集成和专项测试 |
| API 契约 | 覆盖成功、失败、权限和异常响应 |
| 关键用户旅程 | 少量端到端测试，验证串联结果 |
| 普通胶水代码、日志、配置 | 由集成测试、冒烟测试或人工检查覆盖 |
| 视觉和主观体验 | 人工验收为主 |

### 什么时候需要新增或修改测试

| 情况 | 是否需要测试动作 |
|---|---|
| 新增业务行为 | 是，先写失败测试 |
| 修改已有业务行为 | 是，先修改测试预期 |
| 修 Bug | 是，先写复现测试 |
| 纯重构、改名、格式化 | 不需要新增测试，运行现有测试 |
| 内部小函数且已被更高层测试覆盖 | 通常不需要单独测试 |
| 一次性 spike | 不强制；决定保留后补测试或重写 |
| 纯视觉调整 | 人工验收；关键交互可加测试 |
| 简单配置、日志、胶水代码 | 通常由集成或冒烟测试覆盖 |

### “测试没覆盖的逻辑就不写”怎么办

不是“没测就不写”，而是：

1. 属于当前任务且已确认的逻辑：先补测试，再实现；
2. 只是未来可能需要的逻辑：不要现在写，放入后续任务；
3. 实现时发现的真实缺口：暂停，向人说明，由人决定是否纳入本次范围；
4. 无法自动化验证的部分：明确记录人工验收方式，不要假装测试已经覆盖。

## 特殊任务处理

### Bug 修复

1. 先写一个能复现 Bug 的失败测试；
2. 确认失败原因确实是该 Bug；
3. 做最小修复；
4. 运行目标测试和完整测试集；
5. 记录复现条件和回归测试。

如果技术上无法先写自动化测试，必须记录原因、手工复现步骤和后续补测计划。

### 修改已有行为

先修改测试预期，确认测试因旧行为而失败，再修改实现。不要先改代码，再回头让测试适应新代码。

### 老项目改造

先用 characterization test 固定现有行为，再开始修改。

这里的 characterization test 可以先理解为“给现有系统拍行为快照”：它不证明现有设计正确，只用于发现改造过程中是否意外改变了原有行为。

### 技术方案不确定

先做时间盒的 spike，验证可行性。spike 代码必须明确标记为一次性试验，不能直接混入生产实现。方向确定后，正式代码仍按本 SOP 写。

### 页面和视觉

自动化测试优先覆盖：

- 关键交互；
- 表单校验；
- 加载、空状态和错误状态；
- 基本的可访问性行为。

视觉美观、信息层级和操作体验由人工验收。不要用快照测试代替产品判断。

### 外部服务集成

单元测试可以模拟外部依赖，但关键路径还需要：

- 契约测试或集成测试；
- 真实测试环境中的冒烟测试；
- 超时、重试、失败和幂等行为检查。

不要因为模拟全部通过，就认为真实集成已经可靠。

### 多 Agent 协作

可以拆出独立的调查者、实现者和验收者，但实现阶段应尽量保持一个写入者。验收者不应同时担任实现者，详见[多 Agent 协作理解与实操](05-多Agent协作理解与实操.md)。

## 可直接复制的 Agent 提示词

### 提示词 1：只写测试

```text
目标：【本次要实现的一个行为】

范围：
- 输入：【...】
- 输出：【...】
- 不包含：【...】

验收场景：
1. 正常：【...】
2. 边界：【...】
3. 异常：【...】

测试层级：【单元 / 集成 / 端到端】

本阶段只新增或修改测试，不修改业务实现。
请遵循项目现有测试目录、命名约定和测试工具。
完成后运行相关测试，展示真实失败输出，并逐条说明每个测试对应哪个验收场景。
失败原因应当是“功能尚未实现”。如果失败来自环境、语法或测试本身错误，请先修正并说明。
不要跳过、弱化、删除测试，也不要擅自引入新测试框架。
完成后停止，等待我确认。
```

### 提示词 2：写实现

```text
现在进入实现阶段。

请读取当前失败的测试，只实现这些测试所描述的当前行为。
实现范围以已确认的验收场景为边界，不顺手扩展未定义功能。
请写出清晰、可维护、符合项目现有风格的代码；不要为了“最小实现”而故意写临时代码或只针对断言写特判。

约束：
- 不修改、跳过、弱化或删除测试预期；
- 如果发现测试遗漏、需求矛盾或必须扩大范围，先停止并说明；
- 先运行目标测试，再运行完整测试集。

完成后请给出：
1. 修改的文件；
2. 关键设计取舍；
3. 执行的完整命令；
4. 目标测试和完整测试的结果、失败信息与退出码；
5. 仍存在的风险或未覆盖内容。
```

### 提示词 3：只做重构

```text
现在只做重构，不增加新功能，不改变外部行为，不修改测试预期。

请先说明要改善的问题，再按小步骤修改。
每次修改后运行相关测试，最终运行完整测试集。
如果重构需要改变接口、数据结构或业务行为，先停下来，把它当作新任务另行讨论。

完成后请给出修改文件、行为是否保持不变的说明、测试命令和结果。
```

### 提示词 4：修 Bug

```text
请先不要修复代码，先为下面的 Bug 写一个能稳定复现问题的失败测试。

Bug 现象：【...】
复现步骤：【...】
预期行为：【...】
实际行为：【...】

本阶段只新增或修改测试，不修改业务实现。
运行测试并展示真实失败输出，说明失败是否确实对应这个 Bug。
完成后停止，等待我确认。

确认后再进行最小修复，并运行目标测试和完整测试集。
```

### 提示词 5：独立审查测试

```text
你是独立的测试审查者。不要修改代码，只审查当前的测试改动。

请检查：
1. 是否覆盖已确认的正常、边界和异常场景；
2. 断言是否验证业务结果，而不是实现细节；
3. 是否存在一个测试承担过多行为；
4. 测试名称是否表达业务含义；
5. 是否存在跳过、弱化或删除测试的情况；
6. 失败原因是否合理。

请按“严重问题 / 建议改进 / 可以接受”分类输出，并引用具体文件和测试名称。
如果你认为测试不充分，请给出缺少的场景，不要直接替实现者改测试。
```

## 检查清单

### 开始前

说明：L0 可以跳过与行为无关的条目；L1 至少覆盖与本次风险相关的场景；L2 起系统性考虑正常、边界和异常场景。

- [ ] 已确认这是一个行为，而不是一个过大的功能包
- [ ] 已写清目标、输入、输出和不包含内容
- [ ] 已按任务等级列出必要的正常、边界、异常等代表性场景
- [ ] 已确定测试层级和测试命令
- [ ] 已运行基线测试，知道哪些失败是原有的
- [ ] 已给任务定级：L0 / L1 / L2 / L3 / P0

### 红灯关卡

- [ ] 只新增或修改了测试，没有提前修改业务实现
- [ ] 测试遵循现有目录和命名约定
- [ ] 已运行测试并保留真实失败输出
- [ ] 失败原因合理，不是环境或语法错误
- [ ] 测试与验收场景能逐条对应
- [ ] Agent 已停下，等待人工确认

### 测试审查关卡

- [ ] 已按任务等级覆盖必要的正常、边界、异常场景
- [ ] 断言检查业务结果，而非内部实现
- [ ] 一个测试没有承担过多行为
- [ ] 测试名称能说明业务含义
- [ ] 没有跳过、弱化或删除测试
- [ ] 如有遗漏，已先补测试再进入实现

### 绿灯关卡

- [ ] 实现范围没有超出当前行为
- [ ] 测试预期没有被修改
- [ ] 目标测试通过
- [ ] 完整测试集通过
- [ ] 没有通过跳过测试来制造绿灯
- [ ] 已记录命令、结果和退出码

### 重构关卡

- [ ] 重构没有改变外部行为
- [ ] 测试预期没有被修改
- [ ] 每次小步修改后都运行了测试
- [ ] 最终完整测试集通过
- [ ] 如需要改变接口或行为，已另开任务

### 验收关卡

- [ ] 关键业务流程已人工走通
- [ ] 错误提示和异常路径符合产品预期
- [ ] 权限和数据隔离符合预期
- [ ] 测试难以覆盖的部分已有明确结论
- [ ] 测试命令和结果可复现
- [ ] 剩余风险已记录

## 验收记录模板

每完成一个 L1 以上任务，建议保留一条记录。可以放在任务说明、PR 描述或项目日志中。

```text
## TDD 验收记录

- 任务：
- 行为：
- 本次不包含：
- 任务等级：L0 / L1 / L2 / L3 / P0
- 验收场景：正常 / 边界 / 异常
- 测试层级：单元 / 集成 / 端到端 / 人工
- 测试命令：
- 红灯证据：失败测试、失败原因、输出摘要
- 绿灯证据：目标测试结果、完整测试结果、退出码
- 人工验收：关键流程、权限、错误提示、真实集成
- 未覆盖内容：
- 剩余风险：
- 最终结论：通过 / 有条件通过 / 不通过
```

## 常见反模式

| 反模式 | 后果 | 纠正方式 |
|---|---|---|
| Agent 同一轮同时写测试和实现 | 测试容易倒推成“证明当前实现正确” | 先只写测试，人工确认后再实现 |
| 一失败就改测试 | 测试合同失效，问题被掩盖 | 先判断是测试错、需求错还是实现错 |
| 一次任务覆盖多个模块 | 红灯范围过大，难以定位 | 拆成一个可独立验收的行为 |
| 追求 100% 覆盖率 | 大量低价值测试，维护成本上升 | 按风险覆盖核心规则、边界和异常 |
| 只测正常路径 | 边界和异常在生产环境暴露 | 至少补充关键边界和失败场景 |
| 过度模拟外部依赖 | 测试全绿但真实集成失败 | 增加契约测试、集成测试或真实环境冒烟 |
| 只看“测试已通过”的文字 | 无法确认命令、范围和退出码 | 要求展示真实命令、输出和退出码 |
| 把绿灯等同于需求完成 | 技术通过但产品不可用 | 保留人工验收关卡 |
| 把“最小实现”理解成写烂代码 | 产生技术债，后续重构成本高 | 限制行为范围，不降低代码质量 |
| 实现时顺手加入未定义逻辑 | 产生没有测试保护的行为 | 暂停，先确认并补测试，或放入后续任务 |

## 如何验证这套 SOP 是否有效

不要只看流程是否“看起来完整”。建议用一个真实小任务试运行，并观察：

1. AI 是否在实现阶段修改了测试预期；
2. 红灯失败原因是否合理；
3. 测试审查是否发现了遗漏场景；
4. 合并前发现的问题是否增加；
5. 返工轮数是否减少；
6. 测试维护成本是否可接受；
7. 是否仍有“测试通过但业务不可用”的情况。

建议连续试运行 2～3 个任务后再调整。若 L1 任务的流程成本明显高于收益，可以简化人工关卡；若 L3 任务仍出现漏测，应加严测试层级和独立验收。
