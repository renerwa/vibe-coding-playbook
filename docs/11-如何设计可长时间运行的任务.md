# 如何设计可长时间运行的任务

> 用途：解释什么样的任务适合交给 Codex 或类似 Agent 长时间执行，以及怎样设计任务、控制过程、验收结果和避免失控。
> 最后更新：2026-11-08
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[什么是 Agent](07-什么是Agent.md)、[什么是 Harness Engineering](09-什么是Harness-Engineering.md)、[Vibe Coding TDD SOP v0.1](06-Vibe-Coding-TDD-SOP-v0.1.md)。
> 相关模板：[任务卡](../templates/minimal-harness/任务卡.md)、[验收与复盘](../templates/minimal-harness/验收与复盘.md)。

## 一句话结论

> **能长时间运行的任务，通常不是“从零开发整个系统”，而是“目标明确、步骤重复、结果可自动判断、失败可重试、改动可回滚”的批量任务。**

长任务的关键不是写一条很长的提示词，而是把任务设计成一个可以持续收敛的闭环：

```text
定义目标和边界
→ 执行一小步
→ 运行测试或检查
→ 根据真实反馈修正
→ 留下检查点
→ 进入下一小步
```

只要这个闭环成立，Agent 就可以连续工作几小时甚至一天。没有闭环时，运行时间越长，风险越大。

## 先纠正三个误解

| 误解 | 更准确的理解 |
|---|---|
| Agent 连续思考了 24 小时 | 模型推理是分段发生的；大量时间用于运行测试、安装依赖、构建、等待外部服务和失败重试 |
| 一句话就能完成整个系统 | 系统开发包含需求取舍、架构、权限、安全、部署和验收，仍需要人负责关键决策 |
| 跑得越久越有价值 | 只有包含自动验证、检查点和可回滚改动的长时间运行才有价值 |

“跑一天”更准确的说法是：

> 人把一个大目标拆成任务队列，Agent 在受控环境中按批次推进，自动验证能自行修正的问题，遇到业务决策或高风险操作时停下。

## 适合与不适合的任务

### 适合长时间运行

这类任务通常具有“收敛”特征：越做，待处理项越少，结果越接近明确目标。

- 批量补测试、补类型、补错误处理
- 批量迁移接口、组件、配置或依赖
- 修复一批同类 Bug 或静态检查问题
- 性能优化，直到达到明确指标
- 数据清洗、比对和校验
- 兼容性测试、回归测试和基准测试矩阵
- 文档一致性检查、索引生成和批量更新

### 不适合无人监管地长时间运行

- 从零设计整个业务系统
- 需求仍在快速变化的功能
- 需要频繁做产品取舍的任务
- 涉及生产数据、支付、权限、密钥和数据库迁移的任务
- 没有测试、没有验收标准、也没有可复现人工检查的任务
- 多个 Agent 必须修改同一批文件的任务

### 判断标准

一个任务同时满足下面五项，才适合尝试长时间自治：

1. **范围可清点**：能明确说出要处理多少个接口、文件或场景。
2. **完成可判断**：能通过测试、命令或人工步骤判断是否完成。
3. **步骤可重试**：单步失败后可以修正并重新运行。
4. **改动可回滚**：在独立分支或工作目录中操作，出错不会影响生产。
5. **决策不密集**：大部分问题有明确规则，不需要人不断做业务判断。

五项中有两项不满足，先缩短任务或补条件，不要直接延长运行时间。

## 一个具体案例

### 任务：为 20 个订单和库存接口补齐契约测试，并修复明确缺陷

假设有一个旧的订单系统，已经有基础测试，但很多接口只覆盖正常流程。可以设计一个约一天的任务：

> 为 20 个订单和库存接口补齐契约测试；测试暴露的明确实现缺陷要修复，公开接口行为不得擅自变化。

“契约测试”是检查接口的输入输出是否符合约定。例如参数错误是否返回 400、未登录是否返回 401、用户是否只能访问自己的数据。

#### 任务目标

- 20 个接口全部具备正常流程、参数错误、未登录、越权四类测试。
- 测试暴露的明确实现缺陷被修复，并为每个缺陷保留回归测试。
- 完整测试集没有新增失败。

#### 非目标

- 不新增业务功能。
- 不重构系统架构。
- 不修改数据库结构。
- 不调整公开 API 约定。
- 不顺便优化无关模块。

#### 允许修改的范围

```text
src/api/orders
src/api/inventory
tests/contracts
tests/fixtures
```

任务范围外的文件不能修改。发现必须扩大范围时，停下并请求确认。

#### 验收标准

| ID | 场景 | 预期结果 | 验证方式 |
|---|---|---|---|
| AC-01 | 正常请求 | 返回约定状态码和响应结构 | 契约测试 |
| AC-02 | 参数缺失或非法 | 返回 400 和约定错误码 | 契约测试 |
| AC-03 | 未登录 | 返回 401，不泄露业务数据 | 契约测试 |
| AC-04 | 访问其他用户数据 | 返回 403 或业务约定的拒绝结果 | 越权测试 |
| AC-05 | 完成全部接口 | 20 × 4 类场景均有测试记录 | 覆盖矩阵 |
| AC-06 | 修改后回归 | 完整测试集没有新增失败 | 完整测试命令 |

#### 验证命令

以下命令只是示例，实际内容必须替换成目标项目真实可运行的命令。

| 阶段 | 命令 | 需要保留的证据 |
|---|---|---|
| 基线 | `pnpm test` | 原有失败列表、命令、退出码 |
| 目标 | `pnpm test:contract` | 通过数量、失败摘要、退出码 |
| 完整回归 | `pnpm test` | 与基线对比后的新增失败情况 |
| 静态检查 | `pnpm lint && pnpm typecheck` | 输出摘要和退出码 |

#### 停止条件

出现以下情况必须停止，而不是自行猜测继续：

- 同一问题连续修复 3 次仍失败。
- 需要修改公开接口、数据库结构或认证逻辑。
- 需要生产环境凭据、生产数据或不可逆操作。
- 接口文档与实现冲突，无法判断哪一方正确。
- 需要扩大允许修改的目录。
- 测试必须修改预期才能通过。
- 依赖或环境连续失败，无法区分环境问题和实现问题。

#### 交付物

- 测试代码和必要的业务代码修复。
- 20 个接口的覆盖矩阵。
- 每批次的命令、结果摘要和退出码。
- 发现的问题清单、修复说明和回归测试。
- 未覆盖内容、剩余风险和人工验收步骤。

### 为什么这个任务可以跑一天

这个任务包含大量重复但不完全相同的小步骤：

```text
阅读接口约定和现有代码
→ 写一个会失败的测试
→ 运行测试，确认失败原因合理
→ 修改实现
→ 运行目标测试
→ 运行完整测试集
→ 提交检查点
→ 处理下一个接口
```

20 个接口、80 个测试场景，再叠加测试启动、依赖安装、数据库准备、失败定位、重试和代码检查，累计到 7～9 小时是正常现象。

但这仍然只是一个大项目中的一个里程碑，不等于“完成整个订单系统”。

## 推荐执行流程

### 第 1 步：人写任务合同

至少写清楚：

```text
目标：
非目标：
允许修改的范围：
关键约束：
验收标准：
验证命令：
停止条件：
交付物：
需要人工确认的点：
```

产出物：一页任务卡。可以直接复用[任务卡模板](../templates/minimal-harness/任务卡.md)。

### 第 2 步：跑基线并建立清单

Agent 先完成只读调查：

- 运行改动前的测试，记录原有失败。
- 盘点目标接口、文件或数据。
- 识别现有测试缺口和风险。
- 生成分批计划，不立即扩大改动。

产出物：基线记录、范围清单、分批计划和风险清单。

### 第 3 步：按批次执行

每批控制在 3～5 个同类对象，例如 3～5 个接口。每批内部使用固定循环：

1. 阅读约定和相关代码。
2. 先写失败测试或复现步骤。
3. 运行并确认失败原因合理。
4. 做最小修复，不顺手重构。
5. 运行目标测试和完整测试。
6. 保存检查点并更新进度文件。

产出物：可独立验收的小批次改动。

### 第 4 步：定期设人工检查点

建议每 1～2 小时查看一次，只检查三类信息：

- 已完成数量与总进度。
- 是否出现范围漂移或未确认的接口变化。
- 是否有需要业务判断、权限或数据决策的问题。

不需要对每个文件、每条命令都逐步回复。

### 第 5 步：独立验收

由另一个 Agent 或人重新执行验证，不依赖实现者的口头汇报：

- 复跑目标测试和完整测试。
- 检查覆盖矩阵是否与验收标准对应。
- 检查改动是否都在允许范围内。
- 检查失败路径、权限和边界条件。
- 输出通过项、未覆盖项和剩余风险。

产出物：验收报告，而不是一句“已完成”。

### 第 6 步：人工业务验收

技术检查通过不代表业务一定正确。人仍要确认：

- 用户是否能完成真实目标。
- 错误提示是否可理解。
- 权限和数据范围是否符合预期。
- 是否存在“测试通过、产品不可用”的情况。

## 最佳实践

### 任务设计

- **把愿望变成战役**：不要写“完善整个订单系统”，要写“20 个接口、80 个场景、分 5 批完成”。范围能清点，才适合长时间执行。
- **先冻结契约和验收标准**：否则 Agent 可能把现有 Bug 写成测试预期，得到“测试全绿但业务错误”的结果。
- **明确非目标**：长任务最常见的失败之一不是做不出来，而是顺手做了太多无关改动。
- **为每批设定独立完成信号**：让 Agent 能自己判断当前批次是否结束，而不是一直扩大范围。

### 执行机制

- **小步提交**：每 3～5 个对象形成一次可回滚检查点，避免最后才发现整体方向错误。
- **用文件保存外部记忆**：维护 `plan.md`、`progress.md` 或任务日志，记录已完成、未完成、已知失败和待确认问题。不要只依赖长聊天记录。
- **保持一个主要写入者**：初期由一个 Agent 改代码，其他 Agent 只读调查或独立验收。并行写代码要求文件不重叠且接口已冻结。
- **让失败先被分类**：区分需求不清、测试错误、实现缺陷、环境问题和范围漂移，再决定是否修复。不要所有失败都靠重试。
- **设置预算和止损线**：限制时间、重试次数和改动范围。同一问题连续失败 3 次就停下报告。

### 验收机制

- **规则必须配自动检查**：能用测试检查的，不要只写“请注意”；能自动拦截的，不要长期依赖人眼。
- **实现者不自证完成**：至少安排一次独立验收，复跑命令并检查真实改动。
- **保留原始证据**：命令、输出摘要、退出码、改动文件和脱敏样例，必须能被另一个人复现。
- **人工把关高风险动作**：生产数据、密钥、迁移、支付、权限变更必须有人确认。
- **不要以运行时长衡量效果**：真正应观察的是完成的可验收项、返工次数、范围控制和证据完整度。

## 可直接复制给 Codex 的启动提示词

```text
请先阅读项目根目录的 AGENTS.md 和任务卡：[路径]。

这是一个批次化长任务。先只做调查和基线检查，不要立即修改业务代码：
1. 运行任务卡中的基线命令，记录原有失败；
2. 盘点任务范围内的对象，生成分批计划；
3. 写出范围、风险、验收标准和停止条件；
4. 把计划写入 plan.md，等待我确认后再执行。

执行时遵守以下规则：
- 每批只处理任务卡范围内的 3～5 个同类对象；
- 每批按“先写失败测试或复现步骤 → 运行 → 最小修复 → 运行目标测试 → 运行完整测试”的顺序执行；
- 禁止修改、跳过、删除或弱化测试预期；
- 禁止扩大范围、顺手重构或修改未授权的公开接口；
- 禁止访问生产数据、密钥或执行不可逆操作；
- 每批完成后更新进度文件并保存可回滚检查点；
- 同一问题连续修复 3 次仍失败时停止并报告；
- 遇到需求冲突、范围扩大、接口变更或高风险操作时停止，不要自行猜测。

每批汇报必须包含：
完成项、实际运行的命令、输出摘要、退出码、改动文件、未完成项、剩余风险和下一批计划。

完成后不要只说“已完成”。请按验收标准逐条给出证据，并接受独立验收。
```

## 常见失败模式

| 失败模式 | 后果 | 应对 |
|---|---|---|
| 任务写成“完成整个系统” | 范围无限扩大，Agent 自行假设需求 | 改成可清点的里程碑 |
| 没有基线测试 | 无法区分原有失败和新引入失败 | 改动前先运行并记录基线 |
| 测试照着当前实现写 | 把 Bug 固化成预期行为 | 先冻结业务契约和验收例子 |
| 为了绿灯修改测试 | 测试失去约束作用 | 修改测试预期必须人工确认 |
| 一次改几十个文件 | 失败后难以定位，回滚成本高 | 每批小步提交 |
| 只靠聊天记录保存进度 | 上下文压缩后遗漏关键决策 | 使用任务卡、计划文件和进度日志 |
| 多个 Agent 同时写同一批文件 | 冲突、覆盖和重复修改 | 保持一个主要写入者 |
| 没有停止条件 | 无限重试，消耗时间和额度 | 设置重试、时间和范围止损线 |
| 只看“测试通过”文字 | 无法确认是否真的执行 | 要求命令、输出、退出码和改动范围 |

## 如何验证这套方法是否有效

先用一个 2 小时左右的小批次试运行，例如 3～5 个接口，观察：

1. Agent 是否先跑基线，而不是直接改代码。
2. 改动是否都在允许范围内。
3. 测试失败时是否先分析原因，而不是直接改测试。
4. 每批是否留下命令、退出码和改动记录。
5. 独立验收能否发现实现者遗漏的问题。
6. 返工次数是否比纯对话式开发减少。

通过后再扩展到半天、一天。不要第一次就追求最长运行时间。

## 最小落地建议

如果只做三件事，优先做这三件：

1. 为任务写一页任务卡，明确目标、非目标、验收标准和停止条件。
2. 固定一条真实可运行的验证命令，并要求保留基线、目标测试和完整测试证据。
3. 每 3～5 个对象形成一个检查点，安排一次独立验收。

做到这三点，再考虑多 Agent、并行任务和更长周期的自动化。否则增加的工具只会放大不清晰的任务边界。
