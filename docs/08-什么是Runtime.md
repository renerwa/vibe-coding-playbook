# 什么是 Runtime（运行时）

> 用途：解释 Runtime 的定义、它与操作系统、框架、SDK、构建阶段的区别，并整理常见 Runtime。
> 最后更新：2026-11-07
> 默认读者：有技术常识但非科班出身的产品经理。
> 不覆盖：各 Runtime 的底层实现、性能调优和具体部署配置。

## 一句话结论

> **Runtime（运行时）是程序执行期间，为某种语言或平台提供执行规则和基础能力的那层支撑。它不等于“运行的那段时间”，也不等于操作系统。**

更准确地说：代码描述“要做什么”，Runtime 决定“怎么执行、能用哪些能力、受哪些限制”。

## 为什么“运行时”这个翻译容易让人困惑

`runtime` 在英文里至少有两种常见用法：

1. **表示时间阶段**：`at runtime`，意思是“程序执行的时候”。
2. **表示支撑层**：`the Java runtime`，意思是“Java 程序执行所依赖的运行环境或运行时系统”。

中文“运行时”把“时”直译了出来，容易让人理解成一个时间点。于是会出现两种语感差别很大的说法：

- “运行时错误”很自然，因为它指的是执行期间发生的错误。
- “Node.js 是一个运行时”很别扭，因为 Node.js 是一套环境，不是一个时间。

本文约定：单独说 **Runtime** 时，指执行支撑层；说“在运行时”时，指程序执行阶段。

## 先分清几个相近说法

| 说法 | 含义 | 例子 |
|---|---|---|
| runtime（阶段） | 程序执行期间，与编译时、构建时相对 | 配置在程序运行时读取 |
| runtime environment（运行环境） | 范围更宽，包含 Runtime、操作系统、依赖、配置等 | 本地环境、测试环境、生产环境 |
| runtime system（运行时系统） | 某种语言或平台提供的执行支撑 | JVM、CLR、CPython |
| runtime library（运行时库） | 程序执行时依赖的基础库 | C Runtime、C++ 标准库 |
| runtime error（运行时错误） | 程序开始执行后发生的错误 | 端口被占用、配置缺失、空值访问 |

所以，看到“运行时”三个字时，先判断它说的是**阶段**、**环境**，还是**支撑层**，不要直接套同一个理解。

## Runtime 负责什么

不同 Runtime 的职责不完全相同，但通常包括以下几类能力：

- **加载和执行代码**：把源代码或中间格式变成实际运行的行为。
- **内存管理**：分配内存，并在支持垃圾回收（GC，自动回收不再使用内存）的 Runtime 中负责回收。
- **提供标准库和平台 API**：例如文件、网络、时间、字符串处理、HTTP 服务等基础能力。
- **管理并发**：线程、事件循环（event loop，负责调度异步任务）、协程等。
- **处理异常**：定义错误如何抛出、捕获和终止程序。
- **提供安全边界**：限制代码能访问的文件、网络和系统资源。
- **屏蔽平台差异**：让同一份代码更容易运行在不同操作系统上。

并不是每个 Runtime 都提供全部能力。例如，浏览器 Runtime 不提供直接按路径读取本地文件的能力；Go Runtime 把调度和垃圾回收编译进了最终程序；C Runtime 通常不提供托管内存和垃圾回收。

## 为什么需要 Runtime

因为 CPU 只认识机器指令和底层资源，不认识 Python 的列表、Java 的对象或 JavaScript 的异步回调。Runtime 的作用，是把这些高层语言规则翻译成 CPU 和操作系统能执行的操作，并统一管理运行所需的资源。

没有 Runtime，要么代码无法执行，要么每个程序都要自己实现内存管理、异常处理、并发调度、网络访问等基础设施。

具体有四个原因：

1. **代码不是 CPU 直接能执行的**：Python、Java、JavaScript 的源代码或字节码不是机器码，需要解释器、虚拟机或即时编译（JIT）把它转换成实际行为。
2. **语言特性需要落地**：对象模型、垃圾回收、异常、模块加载、异步任务等都不是操作系统提供的，必须由 Runtime 实现。
3. **资源需要统一管理**：操作系统只提供内存页、线程、文件和网络接口；Runtime 决定这些资源如何分配给语言层面的对象、任务和请求。
4. **平台差异和安全边界需要处理**：同一份代码要尽量能跨操作系统运行；浏览器等环境还要限制代码能访问的文件、网络和系统资源。

### 一个具体例子

```python
items = []
items.append(1)
```

操作系统只负责给程序分配内存页。它不知道什么是 Python 列表，也不知道列表扩容、元素引用和垃圾回收该怎么处理。这些由 CPython 这个 Runtime 实现。

再比如：

```js
setTimeout(() => console.log("done"), 1000);
```

操作系统可以提供计时和线程能力，但它不知道“一秒钟后执行这个 JavaScript 回调”是什么意思。事件循环、回调队列和任务调度由 JavaScript Runtime 负责。

### 为什么不是所有程序都需要“重型” Runtime

更准确地说：**程序都需要某种执行支撑，但不一定需要大型托管 Runtime。**

- **C/C++**：编译成机器码，通常只需要 C Runtime、`libc` 和启动代码。
- **Go**：Runtime 编译进最终二进制，负责 goroutine 调度和垃圾回收。
- **Rust**：Runtime 很薄，没有垃圾回收，甚至可以使用 `no_std` 运行在嵌入式环境。
- **裸机程序**：可以没有操作系统和常规 Runtime，但仍然需要自己提供启动代码和基础运行支撑。

所以“某语言不需要 Runtime”通常只是说它**不需要重量级的托管运行时**，不等于完全没有任何执行支撑。

### 需要 Runtime 的代价与收益

Runtime 带来的主要收益是：

- 更高的开发效率
- 自动内存管理或更安全的并发模型
- 跨平台能力
- 标准库和统一 API
- 沙箱、权限和错误处理机制

代价是：

- 额外的内存和启动开销
- 版本和依赖管理复杂度
- 某些场景下不如直接操作底层资源灵活

选择 Runtime，本质上是在**开发效率、可移植性、安全性和运行开销**之间做取舍。

## Runtime 在系统里的位置

可以用下面的分层来理解。实际系统的边界会更复杂，但先建立这个大致模型就够了：

```text
应用代码 / 框架
       ↓
Runtime（语言或平台的执行支撑）
       ↓
操作系统（进程、内存、文件、网络、权限）
       ↓
硬件
```

- **操作系统**：管理所有进程共享的硬件和系统资源。
- **Runtime**：实现某种代码的执行规则，并提供该语言或平台的基础能力。
- **框架**：提供应用结构和生命周期，例如 FastAPI、Django、Spring。
- **应用代码**：实现具体业务逻辑。

框架通常运行在 Runtime 之上。例如，Django 是 Python 的 Web 框架，实际由 Python Runtime 执行；Spring 是 Java 生态的框架，实际由 JVM 执行。

## Runtime 和操作系统为什么不是一回事

操作系统确实也在程序运行期间提供内存、文件和网络能力，但它通常不被称为“某个程序的 Runtime”。核心区别不是“有没有在运行期间提供服务”，而是“为谁提供什么层级的服务”。

| 维度 | 操作系统 | Runtime |
|---|---|---|
| 服务对象 | 所有进程，语言无关 | 特定语言或平台 |
| 核心职责 | 进程、内存页、文件、网络、权限、调度 | 实现该语言的执行规则和基础 API |
| 内存管理 | 提供虚拟内存和内存页 | 管理对象、堆、垃圾回收等 |
| 标准库 | 提供系统调用；部分基础库随系统或工具链提供 | 提供语言级标准库和平台 API |
| 替换关系 | 同一系统可以运行多种 Runtime | 同一 Runtime 可以跨多个操作系统 |

以内存为例：

- 操作系统负责给程序分配“内存页”，并做进程隔离和保护。
- JVM 的垃圾回收器负责判断哪些 Java 对象还可以回收。
- Node.js 使用的 V8 引擎负责 JavaScript 对象的内存管理。

操作系统并不知道“Java 对象”“Python 字典”或“JavaScript Promise”是什么。这些概念由对应的 Runtime 实现。

更准确的说法是：

> **操作系统是 Runtime 的宿主和资源提供者，但不是通常意义上的“那个 Runtime”。**

在很宽泛的意义上，操作系统也可以被视为一种运行环境；但在工程语境中，Runtime 通常默认指语言或平台的运行时。

## Runtime、构建时和编译时

这三个概念经常混在一起，实际可以先按“程序有没有启动”来区分：

| 阶段 | 主要做什么 | 典型问题 |
|---|---|---|
| 编译时 | 把源代码翻译成机器码、字节码或其他中间格式 | 语法错误、类型错误 |
| 构建时 | 安装依赖、编译、打包、生成可部署产物 | 依赖找不到、打包失败、构建配置错误 |
| 运行时 | 启动进程、读取配置、连接数据库、处理请求 | 端口占用、环境变量缺失、权限不足、空值访问 |

几个具体例子：

- TypeScript 类型检查不通过：通常属于构建时或编译时问题。
- 代码访问了不存在的对象属性：通常属于运行时问题。
- 启动时发现 `DATABASE_URL` 没有配置：属于启动阶段的问题，广义上也属于运行时问题。
- `npm run build` 成功，但服务启动后连不上数据库：构建没问题，运行时环境有问题。

“启动时”有时会被单独拿出来讨论，但相对于“构建完成之前”，它仍然属于程序已经进入执行的阶段。

## 同一段代码，不同 Runtime 能力不同

以 JavaScript 为例：

```js
const fs = require("fs");

fs.readFile("config.json", "utf8", (error, data) => {
  if (error) {
    console.error(error);
    return;
  }
  console.log(data);
});
```

这段代码在 Node.js 中可以读取文件，因为 Node.js Runtime 提供了文件系统 API。

放到浏览器里就不行。浏览器 Runtime 出于安全考虑，不允许网页直接按路径读取用户电脑上的文件，通常必须由用户主动选择文件。

这不是 JavaScript 语法不同，而是 **Runtime 提供的能力和限制不同**。

## 常见 Runtime

Runtime 没有一份绝对完整的清单。下面按使用场景列出常见的几类，并标注建议的优先级。

> 先解释两个表中会反复出现的词：
>
> - **垃圾回收（GC）**：自动回收不再使用的内存。
> - **事件循环（event loop）**：调度异步任务的机制，让程序可以同时处理多个等待中的操作。

### 语言与平台 Runtime

| Runtime | 主要运行对象 | 说明 | 建议 |
|---|---|---|---|
| Node.js | JavaScript，TypeScript 通常先编译 | 基于 V8 引擎，提供事件循环和文件、网络等 Node.js API，常用于 Web 后端 | 必知 |
| 浏览器 JavaScript Runtime | 网页中的 JavaScript | 由 JavaScript 引擎和浏览器 Web API 组成，例如 Chrome 的 V8、Firefox 的 SpiderMonkey、Safari 的 JavaScriptCore | 必知 |
| CPython | Python | Python 的参考实现，也是最常见的 Python Runtime | 必知 |
| JVM | Java 字节码 | Java 虚拟机，常见实现是 HotSpot；Kotlin、Scala 等也可运行在 JVM 上 | 必知 |
| CLR / CoreCLR | .NET 中间语言（IL） | .NET 的公共语言运行时，执行 C#、F#、VB 等语言编译后的代码 | 必知 |
| Go Runtime | Go 编译后的程序 | 编译进最终二进制，负责 goroutine 调度、垃圾回收等，不是单独安装的“Go 虚拟机” | 常见后端需了解 |
| ART | Android 应用字节码 | Android Runtime，负责执行 Android 应用代码，不等同于桌面 JVM | 按需了解 |
| Deno | JavaScript、TypeScript | 基于 V8，强调权限控制和现代工具链 | 按需了解 |
| Bun | JavaScript、TypeScript | 集运行时、包管理、打包和测试工具于一体 | 按需了解 |
| PyPy | Python | Python 的另一种实现，使用即时编译（JIT）提升部分场景的性能 | 按需了解 |
| BEAM | Erlang、Elixir 字节码 | Erlang 虚拟机，擅长轻量级进程和高容错场景 | 按需了解 |
| Ruby MRI | Ruby | 最常见的 Ruby 实现 | 按需了解 |
| Zend Engine | PHP | PHP 的核心执行引擎；PHP-FPM 是进程管理器，不是 Runtime 本身 | 按需了解 |
| C Runtime（CRT）/ libc | C 程序 | 提供程序启动、基础库和系统调用封装，通常没有托管垃圾回收 | 按需了解 |
| C++ Runtime（如 libstdc++、libc++） | C++ 程序 | 提供 C++ 标准库和运行时支持 | 按需了解 |
| Wasmtime、Wasmer、浏览器 Wasm Runtime | WebAssembly | 执行 `.wasm` 二进制格式，强调可移植和沙箱隔离 | 按需了解 |

### 容易被统称为 Runtime 的其他东西

“Runtime”在不同语境下还可能指别的东西。它们名字相同，但不是语言 Runtime：

| 说法 | 实际指什么 | 例子 |
|---|---|---|
| 容器 Runtime | 创建和运行容器的底层组件 | containerd、runc；Docker 生态也常把相关组件统称为容器运行时 |
| Serverless Runtime | 云函数平台提供的执行环境 | AWS Lambda Runtime、Cloudflare Workers Runtime |
| Agent Runtime | Agent 的执行宿主或框架，定义 Agent 如何调用模型、工具和文件系统 | 不同 AI 产品的定义不完全统一 |
| 浏览器 Runtime | JavaScript 引擎加浏览器提供的 Web API 和安全沙箱 | DOM、`fetch`、定时器、本地存储等 |

所以在 AI 或部署语境中看到 Runtime，先问一句：**它说的是语言 Runtime、容器 Runtime，还是 Agent 的执行环境？**

## 在 Vibe Coding 中怎么用

当 AI 说下面这些话时，可以这样理解：

| AI 的说法 | 更准确的理解 |
|---|---|
| “这个项目需要 Node.js 20 Runtime” | 需要 Node.js 20 这套执行环境，不只是安装了 Node.js 这个名字 |
| “这里会发生 runtime error” | 程序启动或执行后才会出现的错误，不是语法检查错误 |
| “把配置放到 runtime 注入” | 在程序启动或执行时提供配置，而不是打包进构建产物 |
| “在 runtime 里运行测试” | 在具体的执行环境中运行，环境版本、依赖和权限都会影响结果 |
| “Agent Runtime” | 运行 Agent 循环、工具调用和文件操作的执行宿主或框架 |

### 检查项目实际使用的 Runtime

可以从两个方向检查：

1. **直接查看本机版本**：

```powershell
node --version
npm --version
python --version
py --version
java -version
dotnet --info
go version
```

Windows 上如果 `python --version` 打开了应用商店或没有输出，可以尝试 `py --version`。命令能运行，只能说明本机装过对应环境，不代表项目使用的就是同一版本。

2. **查看项目声明和部署配置**：

- `package.json` 中的 `engines` 字段
- `.nvmrc`、`.python-version`、`global.json` 等版本声明文件
- `pyproject.toml`、`requirements.txt` 等依赖声明
- `Dockerfile` 的基础镜像，例如 `FROM node:20`
- CI 配置中的运行环境
- 云平台或部署平台选择的 Runtime 版本

### 一个最小排查顺序

遇到“本地能跑、部署后不行”时，按这个顺序排查：

1. **先确认错误发生在构建时还是运行时**：构建日志和启动日志要分开看。
2. **确认 Runtime 类型和版本**：是 Node.js、Python、JVM，还是容器或 Serverless Runtime。
3. **确认依赖是否一致**：锁文件、系统依赖、原生扩展是否匹配。
4. **确认运行环境差异**：操作系统、CPU 架构、环境变量、文件权限、网络访问。
5. **确认代码能力边界**：是否使用了当前 Runtime 不提供的 API。

## 最小掌握标准

读完后，能做到下面几点就够了：

1. 能用自己的话说清：Runtime 是执行支撑层，不只是“运行的时间”。
2. 能区分 Runtime、操作系统、框架和 SDK。
3. 看到 `runtime` 时，能判断它指的是执行阶段、运行环境，还是某种 Runtime 产品。
4. 能检查项目声明和本机实际使用的 Runtime 版本。
5. 能区分构建时错误和运行时错误。
6. 知道同一门语言在不同 Runtime 中，能使用的 API 和受到的权限限制可能不同。

下面这些内容可以暂缓，不影响日常协作：

- 垃圾回收算法的具体实现
- JIT（即时编译）的编译流程
- 事件循环的底层调度细节
- JVM、CLR 的字节码格式和内存布局
- 容器 Runtime 的底层实现

## 常见误区

- **“运行时就是运行的那段时间”**：不完整。它还常指执行期间提供支撑的那套环境或机制。
- **“操作系统就是 Runtime”**：操作系统是宿主和资源提供者；语言 Runtime 负责语言级的执行规则和 API。
- **“Node.js 和浏览器都是 JavaScript，所以行为一样”**：语法可能一样，但可用 API、安全边界和运行模型不同。
- **“JDK 就是 JVM”**：JDK 包含 JVM、标准库和开发工具；JVM 只是执行 Java 字节码的运行时。
- **“.NET SDK 就是 .NET Runtime”**：SDK 用于开发和构建，Runtime 用于运行已经构建好的程序。
- **“创建 Python 虚拟环境就会换 Python 版本”**：虚拟环境主要隔离依赖包，Python 版本仍取决于创建环境时使用的解释器。
- **“用了 Docker 就不会有 Runtime 差异”**：镜像能固定一部分环境，但操作系统内核、CPU 架构、环境变量和外部服务仍可能不同。
- **“runtime error 就是语法错误”**：语法错误通常更早暴露；runtime error 是程序开始执行后发生的问题。

## 一句话记忆

> **代码规定“要做什么”，Runtime 规定“怎么执行、能用什么”；操作系统负责提供资源，Runtime 负责实现这套代码的执行规则。**
