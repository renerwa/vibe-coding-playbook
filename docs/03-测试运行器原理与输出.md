# 测试运行器（Test Runner）原理与输出

> 用途：解释测试代码如何被查找、执行、判定和汇报。
> 最后更新：2026-11-03
> 术语说明：更准确的名称是“测试运行器（Test Runner）”，不是“测试解释器”。本文不展开 TDD 流程，相关概念见 [TDD 开发模式](01-TDD开发模式.md)。

## 它是什么

测试运行器是一个开发期工具，负责：

1. 找到测试文件和测试用例；
2. 准备测试环境；
3. 逐个执行测试；
4. 捕获断言失败和程序异常；
5. 汇总结果，输出报告和退出码。

它本身不判断业务是否正确。“100 元打八折应付 80 元”这条规则必须由测试代码表达，运行器只负责执行并报告结果。

## 三个容易混淆的角色

| 角色 | 负责什么 | 例子 |
|---|---|---|
| 语言解释器 | 执行 Python、JavaScript 等程序 | Python、Node.js |
| 测试框架 | 提供断言、测试组织、模拟和测试夹具能力 | pytest、Vitest |
| 测试运行器 | 发现、调度测试并汇总结果 | pytest、Jest、Vitest、Playwright Test |

实际工具经常把测试框架和运行器合在一个产品里。例如 `pytest` 既提供编写测试的能力，也提供执行测试的命令。Node.js 的 `npm test` 只是一个命令入口，背后通常调用 Vitest 或 Jest。

## 它从哪里来

测试运行器通常作为项目的开发依赖安装，而不是作为应用运行时依赖：

```powershell
# Python 示例
python -m pip install pytest
python -m pytest
```

```powershell
# Node.js 示例
npm install --save-dev vitest
npm test
```

真实项目会把版本记录在 `pyproject.toml`、`requirements-dev.txt` 或 `package.json` 中，让本地开发、其他同事和 CI 使用同一套工具。

不建议依赖全局安装，因为全局版本可能与项目不兼容，也缺少项目所需的插件和依赖。全局安装最多是让命令出现在系统路径中，并不等于安装了项目的测试环境。

## 如何发现测试

测试运行器按命名规则和配置查找测试，而不是随意执行所有代码。以 `pytest` 为例，常见规则是：

- 文件名：`test_*.py` 或 `*_test.py`；
- 函数名：以 `test_` 开头；
- 类名：以 `Test` 开头。

Vitest、Jest 等常见规则是 `*.test.ts`、`*.spec.js` 等。具体规则由项目配置决定。

运行器还会跳过 `.venv`、`node_modules`、构建目录等无关位置，避免把依赖包里的测试也执行一遍。也可以只跑一个文件：

```powershell
python -m pytest tests/unit/test_price.py -q
```

## 运行流程与原理

以一次普通测试为例：

```text
执行测试命令
    ↓
读取配置，扫描并收集测试
    ↓
导入测试文件
    ↓
执行测试前的准备逻辑（fixture）
    ↓
调用测试函数
    ↓
执行断言，比较实际值与预期值
    ↓
捕获异常，记录通过、失败或报错
    ↓
执行清理逻辑，汇总结果
    ↓
输出报告和退出码
```

几个关键点：

- **收集**：运行器先确定这次要执行哪些测试，而不是边扫边跑。
- **隔离**：测试框架通常为每个测试准备相对独立的状态，避免前一个测试的数据污染后一个测试。
- **夹具**：Fixture（测试夹具）是测试前准备、测试后清理的机制，例如创建临时数据库、启动测试服务。
- **断言**：断言是“实际结果必须满足某个条件”的检查。条件不成立时通常抛出一个异常。
- **捕获**：运行器捕获这些异常，转成“失败”记录，而不是让整个程序直接退出。

## 如何判定通过和失败

对单个测试，最基础的判定是：

- 测试函数正常执行结束，且没有断言失败或未处理异常 → 通过；
- 断言不成立 → 失败；
- 代码抛出异常、超时、测试环境启动失败 → 失败或报错；
- 测试被显式跳过 → 记为跳过；
- 预期某个异常发生且实际确实发生 → 可以判定通过。

需要特别注意：**没有有效断言的测试也可能显示为通过**。运行器只能判断“有没有报错”，不能判断测试本身是否覆盖了有价值的业务规则。

是否继续执行后续测试，取决于运行器配置。默认通常会在一个测试失败后继续运行其余测试；也可以配置成遇到第一个失败就停止。

## 输出包含什么

典型的测试输出包括：

- 本次收集了多少个测试；
- 每个测试的通过、失败、跳过状态；
- 失败测试所在的文件和函数；
- 实际值、预期值或异常堆栈；
- 总耗时；
- 总结行，例如 `3 passed, 1 failed`；
- 进程退出码。

示例：

```text
tests/unit/test_price.py .F

FAILED tests/unit/test_price.py::test_20_percent_coupon
assert 90 == 80

1 passed, 1 failed in 0.12s
```

其中 `.` 通常表示通过，`F` 表示失败。终端中的红色和绿色只是状态显示，部分环境会关闭颜色。

## 退出码为什么重要

命令行程序执行结束后会返回一个退出码。以 `pytest` 为例：

- `0`：所有收集到的测试都通过；
- `1`：存在失败；
- `2`：执行被中断；
- `5`：没有收集到测试。

不同运行器的具体数值可能不同，但核心约定相同：**成功通常返回 0，失败返回非 0**。

CI（持续集成）正是读取这个退出码来决定是否阻止合并，而不是依靠人眼判断日志。运行器还可以输出 JUnit XML 或 HTML 报告，供 CI 和代码托管平台展示。

## 它能证明什么，不能证明什么

测试运行器能证明：

- 这些测试在指定环境中确实被执行了；
- 测试代码中的断言全部成立；
- 执行结果可被重复检查。

它不能证明：

- 测试覆盖了所有业务场景；
- 测试断言写得正确；
- 外部真实服务在线上也会正常工作；
- 用户界面和业务流程一定符合真实使用习惯。

因此，运行器是执行和报告工具，不是质量裁判。测试质量、覆盖范围和最终验收仍需要人负责。
