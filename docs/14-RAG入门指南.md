# RAG 入门指南：让大模型先查资料，再回答问题

> 用途：用一条完整链路解释 RAG 解决什么问题、用户提问后系统如何返回结果、每个环节为什么存在，以及如何验证效果。
> 最后更新：2026-11-11
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[向量数据库入门指南](./13-向量数据库入门指南.md)。
> 不覆盖：具体 RAG 框架的部署、Embedding 与重排模型的训练、多模态 RAG 的完整实现。

## 一句话结论

> **RAG 不是把知识训练进模型，而是在每次回答前，把相关资料找出来放到模型眼前。它把“知道什么”和“怎么回答”拆成了两件事。**

如果只记一个比喻：

> **普通大模型是闭卷考试，RAG 是开卷考试。**

闭卷考试考的是模型记住了多少；开卷考试考的是它能不能找到正确资料，并且读懂、用对。RAG 提升的不是模型的“记忆力”，而是它在回答这一刻能看到的证据质量。

## 一、问题不是模型不会说，而是它不知道你的情况

假设你做了一个公司内部制度问答助手。员工问：

> 试用期员工可以申请几天年假？

大模型很可能会自信地回答：

> 根据劳动法，试用期员工同样享有年假，通常为 5 天。

这句话读起来很像真的，但它可能不符合你们公司的制度：也许公司规定试用期员工不享受年假，也许按入职月份折算，也许上海和北京的政策不同。模型并不知道这些，它只是根据训练数据里的常见说法做了一个“合理推测”。

这类错误通常来自三个原因：

- **知识有截止时间**：模型训练完成之后发生的事情，它不知道。
- **不知道私有资料**：公司制度、项目文档、产品手册，从来没有进入过它的训练数据。
- **没有出处**：即使答案碰巧对了，也无法证明它依据的是哪一条规定。

最直接的办法是把制度全文粘进提示词，让模型“看着资料回答”。资料只有一两页时，这确实有效。但资料一多，问题就来了：

- **上下文窗口有限**：模型一次能读入的文本有上限，不可能把整个知识库都塞进去。
- **成本和延迟上升**：每次提问都带上大量无关内容，既慢又贵。
- **无关信息会干扰判断**：资料越多，模型越容易抓错重点。
- **更新麻烦**：制度改一条，就要重新组织整段提示词。
- **权限无法控制**：不同部门、不同项目的人，不应该看到同一批资料。

于是就有了 RAG 要解决的核心问题：**资料很多、经常更新、还要求答案有依据时，怎样让模型在每次回答前只看到最相关的那一小部分？**

## 二、三条路：塞提示词、微调、RAG

面对“模型不知道私有知识”这个问题，常见的做法有三种。它们不是互相替代的关系，但解决的是不同问题。

| 做法 | 本质 | 适合场景 | 主要代价 |
|---|---|---|---|
| 把资料塞进提示词 | 每次提问时，把相关资料一起交给模型 | 资料少、变化慢、可以人工挑选 | 上下文有限，成本和延迟随资料量上升 |
| 微调（Fine-tuning） | 用私有数据继续训练模型，改变模型参数 | 主要想调整表达风格、输出格式或特定任务能力 | 知识更新要重新训练，难以逐条追溯出处 |
| RAG | 资料放在外部知识库，回答前检索相关片段 | 资料多、更新频繁、需要权限和引用 | 多了一套检索、索引和评测工程 |

这里要澄清一个常见误解：**微调不是给模型装一个数据库。** 微调更像“训练一种做事方式”，比如让模型总是按固定格式写报告、学会某个行业的表达习惯。它可以注入一部分知识，但知识会以参数的形式“化”进模型里，既不好更新，也不好逐条验证。

RAG 则把知识留在外部：文档还是文档，数据库还是数据库。需要更新时，重新处理相关文档即可；需要追责时，可以指出答案来自哪一段原文。模型负责理解和表达，资料负责提供事实依据。

两者也可以组合：用微调让模型更懂业务语言和输出规范，用 RAG 提供最新、可追溯的事实。但对大多数知识库问答场景，应该先做 RAG，而不是先微调。

## 三、RAG 的核心：把“闭卷考试”改成“开卷考试”

RAG 的全称是 Retrieval-Augmented Generation，拆开看就是三个动作：

- **Retrieval（检索）**：从资料库里找出和问题相关的片段。
- **Augmented（增强）**：把这些片段整理后放进提示词，增强模型回答时所依据的上下文。
- **Generation（生成）**：模型阅读这些材料，组织成自然语言答案。

所以一条最小的 RAG 链路可以画成这样：

```text
用户问题
   │
   ▼
检索器：去资料库找相关片段
   │
   ▼
相关资料 + 来源信息
   │
   ▼
生成器：阅读资料，组织答案
   │
   ▼
回答 + 引用
```

这里有两个角色：

- **检索器**负责“找”，通常由 Embedding 模型（把文字转成向量的模型）和向量数据库组成。
- **生成器**负责“读和说”，通常是大语言模型。

“增强”不是让模型变得更聪明，而是改变它回答时能看到的内容。模型仍然需要理解问题、判断资料是否相关、处理资料之间的矛盾，所以 RAG 不能消灭所有错误。它只是把“凭空编造”变成了“有材料可查，但仍可能读错”。

这也决定了后面所有工程细节的意义：**检索器找得准不准，决定了模型有没有机会答对；生成器读得对不对，决定了最终答案可不可信。**

还要记住：**向量数据库只是 RAG 的一个零件。** RAG 还包括文档处理、分块、上下文组装、生成约束、引用和评测。只把文档向量化，不等于就有了一个可靠的 RAG 系统。

## 四、一条完整链路：离线建库 + 在线回答

RAG 不是一个单独的模型，而是一条流水线。它分成两个阶段：

- **离线建库**：提前把文档处理成“可被找到”的形态。
- **在线回答**：用户提问时，实时检索并生成答案。

很多人只关注在线回答，忽略了离线建库。实际上，RAG 效果不好，很大一部分原因在入库阶段就已经埋下了。

### 离线：先把资料变成“可被找到”的形态

一份 PDF、Word 或网页，不能直接扔进向量数据库。它需要经过下面几步。

**第一步：解析和清洗。**

把各种格式的文档转成纯文本，同时去掉页眉、页脚、导航栏、广告、重复的水印和乱码。还要保留真正有用的结构信息：文档标题、章节路径、更新时间、适用对象、原文链接。

如果这一步做得粗糙，后面检索到的可能是一堆目录和页脚，而不是答案。

**第二步：分块。**

把长文档切成适合检索的小段，通常叫 **chunk（片段）**。常见做法是每块 500～800 字，块与块之间重叠 50～100 字。

为什么要切？因为一整篇文章可能同时讲招聘、假期、报销和离职。把它变成一个向量，语义会被“平均”掉，用户问假期时不一定能精准命中。切得太碎也不行，一句话一个块会丢失上下文，模型看到的只是孤立的句子。

分块的目标不是“切得均匀”，而是“每一块尽量只讲一个完整的小主题”。

**第三步：补上下文。**

切出来的片段经常会失去主语。比如原文写“上述假期需提前三天申请”，单独看这一块，模型不知道“上述假期”指什么。

常见做法是在片段前面补一行上下文：

```text
文档：员工手册
章节：假期制度 / 年假
适用对象：试用期员工

上述假期需提前三天申请……
```

这几行不一定是原文，但它能显著降低检索和回答时的歧义。

**第四步：向量化。**

用 **Embedding 模型**把每个片段转成一串数字，也就是**向量**。向量可以理解为文本的“语义指纹”：意思相近的文字，向量距离通常更近。

这里有一个必须记住的规则：**建库和查询必须使用同一个 Embedding 模型，同一个版本，同一个维度。** 不同模型给出的向量属于不同坐标系，不能混在一起比较。换模型可以，但必须全量重算、重建索引。

**第五步：入库。**

把片段正文、向量和元数据一起存起来。元数据不是装饰，它决定了系统能不能做过滤、引用和更新。

一个实用的片段记录通常包含：

| 字段 | 作用 |
|---|---|
| `chunk_id` | 唯一标识这个片段 |
| `content` | 片段正文，最终要交给模型阅读 |
| `embedding` | 用于相似度检索的向量 |
| `doc_id` | 指向原始文档 |
| `title` / `section` | 生成引用时告诉用户出处 |
| `source_url` | 让用户能点回原文 |
| `effective_date` | 判断制度是否仍然有效 |
| `acl` / `tenant_id` | ACL（访问控制列表）和租户标识，控制哪些用户能检索到 |
| `version` | 文档更新后区分新旧版本 |

注意，向量数据库里存的是**正文和向量**，不是“答案”。它返回的是一批候选片段，最终怎么组织成答案，是后面生成环节的事。

### 在线：从问题到答案

用户提问后，系统通常按下面的顺序工作。

**1. 理解问题。**

如果用户说“那试用期呢？”，系统需要结合上一轮对话，把它改写成“试用期员工的年假有几天？”。这一步叫**查询改写**，目的是让检索器拿到一个完整、明确的问题。

同时，系统会识别过滤条件：用户属于哪个租户、哪个部门，能看哪些文档，问题涉及哪个地区、哪个生效日期。这些条件会影响后面的检索范围。

**2. 把问题向量化。**

用和建库时相同的 Embedding 模型，把问题转成查询向量。

**3. 检索候选片段。**

拿查询向量去向量数据库里找最相似的若干条，通常先取 10～20 条，这个数量叫 **top-k**。同时应用元数据过滤，比如只看当前租户、当前有效版本、用户有权限访问的文档。

数据库返回的通常是：片段 ID、相似度分数、正文、文档标题、章节、权限标签等。它不是一段现成答案。

相似度分数只适合在同一个模型、同一批数据内部排序，不要把它当成跨系统通用的“正确率”。0.8 在不同数据和模型下，含义可能完全不同。

**4. 可选：补充关键词检索。**

纯向量检索擅长“意思相近”，但对专有名词、编号、错误码不一定敏感。比如用户搜“ERR_4012”，关键词检索可能比向量检索更可靠。

所以很多系统会同时做一路关键词检索，再用融合算法合并结果。常见的关键词算法叫 **BM25**，常见的融合方法叫 **RRF（倒数排名融合）**。这一步不是最小版本的必需品，但对术语很多的资料库很有价值。

**5. 重排。**

初筛出来的候选，不一定都能回答问题。有的片段主题相关，但没有给出答案；有的片段只是提到了同一个词。

**重排（rerank）**会把“问题 + 每个候选片段”放在一起逐条判断相关性，再重新排序。它比单纯比较向量更准确，但速度更慢，所以只对少量候选做。重排后通常保留前 3～5 条。

**6. 组装上下文。**

把选中的片段按重要性排序，去掉重复内容，加上来源编号，拼成一段材料：

```text
[1] 来源：《员工手册》/ 假期制度
试用期员工每年享有 5 天年假……

[2] 来源：《假期政策 FAQ》/ 申请流程
年假需提前三个工作日提交申请……
```

这一步要注意上下文长度。不能把所有候选都塞进去，否则既浪费成本，也会让模型抓不住重点。经验上，最重要的内容放前面，同时避免把大量互相矛盾或重复的材料混在一起。

**7. 生成答案。**

把问题、材料和控制规则一起交给大模型。规则通常包括：

- 只能依据给定材料回答；
- 每条关键结论标注来源编号；
- 材料不足时明确说“现有资料无法回答”；
- 不要用材料之外的知识补充猜测。

模型返回的可能是：

> 根据现行《员工手册》，试用期员工每年享有 5 天年假 [1]。年假需要提前三个工作日申请 [2]。

**8. 返回和记录。**

后端把 `[1]`、`[2]` 解析成文档名、章节和可点击链接，再返回给前端。同时记录这次请求的日志：问题、召回的片段 ID、相似度分数、重排结果、最终答案和引用。

这些日志不是可选项。没有它们，你只能看到“答案好像不对”，却不知道是没检索到、排序错了，还是模型读错了。

## 五、跟着一个问题走一遍

把上面的流程放进一个具体场景，会更容易理解。

假设知识库里有《员工手册》《假期政策 FAQ》《考勤制度》，还有一份已经过期的旧版员工手册。用户问：

> 试用期员工年假有几天？

系统先结合上下文，把它改写成：

> 上海办公室试用期员工的年假天数是多少？

然后应用过滤条件：当前租户、用户有权限的文档、当前生效版本。旧版员工手册虽然语义上也很相关，但因为 `effective_date` 已过期，会在检索阶段被排除。

向量检索可能返回这样的候选：

| 排名 | 片段 | 相似度 | 是否保留 |
|---|---|---|---|
| 1 | 员工手册 / 假期制度：试用期员工年假规定 | 0.87 | 保留 |
| 2 | 假期政策 FAQ / 申请流程 | 0.82 | 保留 |
| 3 | 考勤制度 / 请假审批 | 0.79 | 重排后降级 |
| 4 | 旧版员工手册 / 年假条款 | 0.77 | 被生效日期过滤 |
| 5 | 员工手册 / 病假规定 | 0.74 | 丢弃 |

重排模型会判断：第 1 条直接回答“有几天”，第 2 条补充“怎么申请”，第 3 条只讲审批流程，不能回答天数。最终只把第 1、2 条放进上下文。

模型看到的材料可能是：

```text
[1] 来源：《员工手册》/ 假期制度
试用期员工每年享有 5 天年假，按入职月份折算。

[2] 来源：《假期政策 FAQ》/ 申请流程
年假需提前三个工作日提交申请，由直属主管审批。
```

最终回答：

> 根据现行《员工手册》，试用期员工每年享有 5 天年假，并按入职月份折算 [1]。申请年假需要提前三个工作日提交，由直属主管审批 [2]。

如果检索结果里没有“试用期年假”的规定，系统应该回答：

> 现有资料没有说明试用期员工的年假天数，建议向人力资源部门确认。

而不是根据“一般劳动法规定”自行补一个数字。**能否在资料不足时停下来，是 RAG 可信度的重要组成部分。**

## 六、每个环节为什么不能省

RAG 的很多知识点，单独看像是“最佳实践”，放进链路里其实都能对应一个具体故障。下面这张表可以帮助理解它们为什么存在。

| 如果省掉什么 | 可能出现的问题 |
|---|---|
| 文档清洗 | 页眉、目录、广告被当成正文，检索结果很脏 |
| 合理分块 | 一块里混了多个主题，或者一句话被切成两半 |
| 上下文头 | 片段里的“上述”“该政策”失去指代，模型看不懂 |
| 统一 Embedding 模型 | 文档和问题的向量不在同一个坐标系，检索失真 |
| 元数据过滤 | 搜到其他项目、过期版本或无权访问的资料 |
| 关键词检索 | 专有名词、编号、错误码搜不到 |
| 重排 | 主题相关但不能回答问题的片段排在前面 |
| 上下文长度控制 | 材料太多，模型抓不住重点，成本和延迟上升 |
| 引用要求 | 答案无法追溯，用户不知道依据是什么 |
| 拒答规则 | 资料不足时模型仍然编造 |
| 索引更新 | 文档改了、删了，系统还在返回旧内容 |
| 请求日志 | 出错后无法判断是检索问题还是生成问题 |

但这不意味着第一版必须把所有能力都做上。可以分成两层：

- **基线必需**：解析、分块、补上下文、统一 Embedding、元数据过滤、引用、拒答、索引更新。
- **效果增强**：关键词混合检索、重排、查询改写、父子块、多轮检索。

先把基线跑通，再用评测结果决定要不要加增强项。不要因为“别人都在用重排”就一开始把链路堆满。

## 七、RAG 的上限由检索决定

这是整篇文章最重要的一句话：

> **生成模型决定答案说得好不好，检索结果决定它有没有机会说对。**

如果正确资料根本没有被检索出来，后面换再多模型、写再多提示词，也只能在错误材料上做文章。所以排查 RAG 问题时，顺序应该是“先看检索，再看生成”。

可以把失败分成三类。

**第一类：没找到。**

正确片段不在前 k 条结果里。常见原因包括：

- 文档切得太碎，答案被切断；
- 片段缺少上下文，向量表达的语义不完整；
- 用户用了同义词、口语或缩写，Embedding 没匹配上；
- 过滤条件太严，把正确文档排除了；
- 索引没有更新，正确内容还没入库。

这类问题要看 **Recall@k**，也就是“正确片段有没有进入前 k 条”。入门阶段可以准备 30 个真实问题，先看正确片段是否进入前 5。

**第二类：找到了，但排得太靠后。**

正确片段在候选里，但被大量“主题相似却没回答问题”的内容挤到后面，最终没进入上下文。常见解决办法是混合检索、重排、调整 top-k，或者改进分块。

**第三类：资料对了，但答案错了。**

正确片段已经交给模型，模型却读错、拼接错、忽略了限定条件，或者把旧版本和新版本混在一起。这时才应该检查提示词、上下文顺序、材料冲突和模型能力。

排查时最有效的方法，是把一次请求的“问题 → 召回片段 → 重排结果 → 最终上下文 → 答案”完整保存下来。只看最终答案，很难定位问题出在哪一层。

## 八、RAG 不是万能：适用边界

RAG 很适合“资料多、更新快、需要引用”的知识问答，但不是所有问题都该用它。

**适合用 RAG 的场景：**

- 公司制度、产品手册、项目文档、客服知识库；
- 资料会持续更新，不能靠重新训练模型来同步；
- 不同用户能看到的内容不同，需要权限过滤；
- 答案需要标注来源，方便核对和追责。

**不一定适合的场景：**

- **资料很少且稳定**：只有几页说明，直接放进提示词更简单。
- **实时结构化数据**：问“库存还有多少”“这个订单到哪了”，应该查数据库或调用业务接口，而不是做向量检索。向量检索擅长找文本，不擅长算数。
- **需要通读整份长文档做全局分析**：RAG 通常只取几个片段，可能漏掉全文结构。这类任务要考虑长上下文、分段总结或专门的分析流程。
- **需要生成新图片**：这属于图像生成，不是 RAG。RAG 可以检索并返回已有图片，但不会凭空画出新图。
- **需要精确计算或执行操作**：应该调用计算器、代码或业务工具，而不是让模型“读资料算”。

长上下文模型的出现，确实降低了“所有东西都必须 RAG”的程度。但长上下文没有自动解决权限、更新、成本和可追溯性。把整个知识库塞进上下文，既不经济，也很难保证模型不被无关内容干扰。

RAG 还可以和 Agent 结合。普通 RAG 是“每次提问都检索一次”，Agentic RAG 则让模型自己判断：要不要查、查几次、要不要改写问题、要不要继续追查。这会更灵活，但失败路径也更多。对入门项目，先把单轮 RAG 做稳，再考虑这种复杂度。

如果资料里有图片，处理思路也不是“把图片直接塞进向量库”。常见做法是给图片生成文字说明，和周围正文一起建索引，命中后返回原图；更复杂的情况才使用多模态向量。具体可以回看[向量数据库入门指南](./13-向量数据库入门指南.md)中关于图片的章节。

## 九、最小可行方案

如果现在要做一个能验证的 RAG，不建议一上来就上框架、微调和多 Agent。先选一个边界清楚的小场景，把下面这条链路跑通。

**目标**：让用户能对一批文档提问，得到有出处的答案；资料不足时能明确拒答。

**第一步：限定范围。**

先选一个领域，比如“公司假期制度”，准备 30～50 篇结构清晰的文档。不要一开始就把整个网盘导进来。

**第二步：建立文档和片段表。**

原文和片段分开存。片段表至少包含正文、向量、文档 ID、章节、生效日期、权限标签和原文链接。

**第三步：解析、分块、补上下文。**

每块 500～800 字，重叠 50～100 字；在片段前补文档名、章节路径和适用对象。先处理一类文档，确认切出来的块能独立表达一个完整意思。

**第四步：统一向量化。**

选一个中文效果够用的 Embedding 模型，文档和查询共用。用 PostgreSQL + pgvector（PostgreSQL 的向量扩展）之类的方案就足够起步，不必一开始引入独立向量数据库集群。

**第五步：实现查询接口。**

接收问题，做必要的改写，向量化后取 top-5 或 top-10，带上权限和生效日期过滤。先只做向量检索也可以，但要把候选片段和分数记录下来。

**第六步：约束生成。**

提示词里明确三件事：只能依据材料回答、关键结论标引用、资料不足就拒答。不要只写“请根据资料回答”，要把“不能做什么”也说清楚。

**第七步：准备评测集。**

准备 30 个真实问题，每个问题标注正确片段和标准答案。不要只用“随便问几句感觉还行”来判断。

**第八步：记录日志，再决定增强项。**

保存问题、召回片段、分数、重排结果、最终答案和引用。先看是“没找到”还是“找到了没用对”，再决定要不要加混合检索、重排或查询改写。

第一版可以先不做这些：微调、复杂前端、多 Agent、GraphRAG（基于知识图谱的 RAG）、全自动文档同步。它们不是没价值，而是会把问题混在一起，让你看不清效果到底来自哪里。

## 十、怎么验证：不要用“能跑”当完成

RAG 最危险的地方，是它很容易“看起来能用”。随便问一句，返回一段通顺的话，再加两个引用，很容易让人误以为系统已经可靠。真正要验证的是：该找到的有没有找到，找到的有没有用对，说出来的有没有依据。

可以用下面这张表做入门验收：

| 检查项 | 怎么测 | 关注点 |
|---|---|---|
| 检索命中 | 30 个问题，正确片段是否进入前 5 | 没找到时，先修分块、查询和过滤 |
| 回答正确 | 对照标准答案逐条核对 | 是否遗漏限定条件、混用新旧版本 |
| 引用准确 | 点开引用，看原文是否真的支持结论 | 引用不能只是“看起来相关” |
| 拒答能力 | 问资料里没有的内容 | 是否会编造，是否会明确说不知道 |
| 权限隔离 | 用无权限账号提问 | 是否召回或返回了越权内容 |
| 更新同步 | 修改、删除文档后重新提问 | 旧片段是否还在被召回 |
| 延迟和成本 | 记录每次请求的耗时和 token（模型处理文本的基本单位）消耗 | 是否在可接受范围内 |
| 可排查性 | 随机抽一条错误答案 | 能否从日志定位到具体片段和步骤 |

指标不用一开始追求漂亮数字。先建立一个基线，再对比每次改动。比如第一版 30 个问题里有 20 个能命中正确片段，加入上下文头和重排后变成 27 个，这就是可解释的进步。

还要主动测试几类“坏情况”：

- 资料里有两份互相冲突的制度，系统会不会说明冲突；
- 文档已过期，系统会不会误用旧版本；
- 用户问一个资料里完全没有的问题，系统会不会拒答；
- 文档正文里藏有“忽略以上指令”之类的恶意内容，系统会不会把它当成命令；
- 用户没有权限，但问题恰好能命中敏感文档，系统会不会泄露。

其中，文档里藏有恶意指令这一类情况叫**提示词注入**：检索到的文档本身也可能包含“忽略以上指令”之类的内容。RAG 系统不能默认“资料里的每句话都是可信指令”，而要把资料当作待阅读的内容，而不是待执行的命令。

## 十一、上线前检查清单

- [ ] 正确片段能在前 5 条召回结果中出现。
- [ ] 无权访问的文档不会出现在候选和引用里。
- [ ] 每条关键结论都有可点开的来源。
- [ ] 资料不足时，系统会明确拒答。
- [ ] 文档修改或删除后，旧索引会同步清理。
- [ ] 新旧版本文档不会同时被当成有效依据。
- [ ] 文档中的恶意指令不会被当成系统命令执行。
- [ ] 请求日志能还原“问题、召回片段、上下文、答案”的完整链路。
- [ ] 延迟和成本在业务可接受范围内。
- [ ] 团队知道当前版本的已知失败类型，而不是把“能回答”当成“已可靠”。

## 结语

RAG 的本质，不是让模型记住更多知识，而是让它在回答前看到正确的证据。

它把一个大问题拆成了三个可以分别改进的小问题：

- **找得到吗？** 取决于文档处理、分块、Embedding 和检索策略。
- **用对了吗？** 取决于重排、上下文组装和提示词约束。
- **说得有依据吗？** 取决于引用、拒答和权限控制。

所以，评价一个 RAG 系统，不要只问“它答得像不像人”，而要问：

> **它有没有找到正确的资料？有没有正确使用这些资料？能不能把出处摆到用户面前？**

一句话记忆：

> **RAG = 先检索证据，再增强上下文，最后生成有出处的回答。**
