# 验收与复盘

> 用途：在任务提交前检查范围、证据和真实结果，并把重复错误转成可复用控制。
> 原则：没有证据不算完成；测试通过不等于业务一定正确；复盘不是写感想，而是改流程。

## 1. 提交前验收清单

### 任务与范围

- [ ] 任务卡的目标、范围、非目标、验收标准和验证命令都已填写。
- [ ] 任务等级已确定，测试和人工关卡与风险匹配。
- [ ] 改动文件都在允许范围内，没有无关重构、格式化或改名。
- [ ] 没有未经确认的新依赖、新框架、新服务或公共接口变更。
- [ ] 如果范围发生变化，任务卡已更新并获得确认，而不是事后补理由。

### 测试与命令

- [ ] 改动前已运行基线（改动前的测试结果），知道哪些失败是原有的。
- [ ] 新增或修改的行为有测试；没有测试时有可复现的人工验证步骤和原因。
- [ ] 目标测试通过，完整测试集没有新增失败。
- [ ] lint（自动检查代码风格和常见错误）、类型检查或构建按项目要求通过。
- [ ] 测试预期没有被修改、跳过、弱化或删除。
- [ ] 失败和环境问题已区分，没有把“环境坏了”说成“功能还没实现”。

### 数据、安全与交付

- [ ] 权限、数据隔离、输入校验和错误提示符合验收标准。
- [ ] 数据库迁移、配置变更和兼容性影响已有说明，必要时验证回滚。
- [ ] 日志和证据中没有密钥、令牌、生产数据或个人敏感信息。
- [ ] API、数据模型、配置和运行文档已按需更新。
- [ ] 剩余风险、未覆盖内容和需要人工确认的点已写清。

### 最终结论

- [ ] 机械检查已通过。
- [ ] 关键业务路径已由人实际走通。
- [ ] 结论只能是：通过 / 有条件通过 / 不通过；不能只写“完成”。

## 2. 证据要求

证据必须“可复现、可核对、可脱敏”。不要只保存对自己有利的片段。

| 证据 | 最低要求 | 不能接受的替代 |
|---|---|---|
| 改动差异（diff） | `git diff --stat` 和关键文件的实际改动；说明哪些文件为什么改 | 只说“改了后端” |
| 测试结果 | 完整命令、通过/失败数量、失败摘要、退出码 | 只说“测试全过” |
| 失败证据 | 失败测试名称、真实报错、为什么这是预期失败 | 截掉报错，只留最后一行 |
| 静态检查 | lint、类型检查或构建命令及结果 | 用“应该没问题”代替 |
| 人工验收 | 前提、步骤、输入、预期、实际结果；必要时脱敏截图或请求响应 | 只看页面“像是正常” |
| 环境信息 | 必要时记录 Runtime（运行时）版本、依赖状态或测试环境 | 本地结果直接等同于生产 |
| 结论 | 通过项、未覆盖项、剩余风险、最终结论 | 用“基本完成”模糊收尾 |

保存建议：放在任务卡末尾、PR（代码合并请求）描述或项目日志中。证据要能让另一个人不看聊天记录也能复跑。

## 3. 失败分类

先分类，再决定修什么。不要把失败都归因于“Agent 不行”，也不要都归因于“需求没说清”。

| 类型 | 典型表现 | 第一步 | 不要做什么 |
|---|---|---|---|
| 需求歧义或变更 | 验收标准互相矛盾，或做到一半目标变了 | 停下，补充或修改任务卡并确认 | 让 Agent 猜，再事后解释 |
| 测试设计错误 | 断言绑定内部实现、场景遗漏、失败原因不合理 | 先修测试合同，再继续实现 | 直接改业务代码迁就错误测试 |
| 实现缺陷 | 正常测试失败、边界处理错误、异常未处理 | 最小修复，补回归测试（防止已修问题再次出现的测试） | 大范围重写或顺手重构 |
| 环境或依赖问题 | 版本不符、数据库不可用、端口冲突、命令不存在 | 先修环境，保留原始错误 | 把环境失败当作红灯或功能完成 |
| 范围或上下文漂移 | 改了无关文件、遗漏项目约定、一次做多个行为 | 回退无关改动，拆分任务，补充上下文 | 用更长的提示词掩盖结构问题 |
| 数据或安全缺陷 | 越权、数据串号、敏感信息泄露、迁移不可逆 | 立即停止，人工审查并补专项测试 | 只补一条正常路径测试 |
| 体验或主观问题 | 功能可用但提示难懂、流程不符合产品预期 | 人工评审，明确判断标准 | 强行用单元测试证明“体验好” |
| 虚假完成 | 没跑命令却说通过、隐藏失败、证据不完整 | 复跑命令，核对原始输出，收紧验收 | 只口头提醒下一次注意 |

## 4. 复盘记录模板

```text
## 任务复盘

- 任务与等级：
- 原目标：
- 实际结果：
- 验收证据位置：
- 第一次失败发生在哪一步：
- 失败分类：需求 / 测试 / 实现 / 环境 / 范围 / 数据安全 / 体验 / 虚假完成
- 直接原因：
- 根因：是规则缺失、上下文缺失、测试缺失、工具缺失，还是判断错误？
- 影响：返工轮数、耗时、是否影响用户或数据
- 做对了什么：
- 下次如何更早发现：
- 沉淀方式：规则 / 测试 / lint / 检查清单 / 文档
- 具体改动：
- 负责人和复查日期：
- 剩余风险：
```

复盘要回答“哪个环节允许错误发生”，而不只是“这次哪里写错了”。

## 5. 把重复错误转成控制

### 触发条件

- 同类问题在 2～3 个任务中重复出现，应沉淀控制。
- 数据、安全、权限、金额类问题出现一次，就应沉淀专项测试并人工复查。
- 一次性笔误、偶发环境波动不要立刻升级成永久规则。

### 选择控制方式

优先选择能自动拦截的方式；只有无法自动判断时，才写成提醒。

| 错误模式 | 首选控制 | 例子 |
|---|---|---|
| 可明确判断的行为错误 | 自动化测试 | 未登录返回 401；用户不能读取其他组织的数据 |
| 风格、导入、简单静态问题 | lint 或类型检查 | 禁止未使用变量、统一错误类型 |
| 范围漂移、禁止事项 | `AGENTS.md` 规则或任务卡约束 | 新增接口不得顺手重构列表查询 |
| 容易遗漏的人工步骤 | 检查清单 | 提交前必须核对迁移回滚和脱敏 |
| 上下文或命令反复找错 | 目录地图、脚本或 README | 固定测试命令和数据准备步骤 |
| 复杂判断或取舍 | 专题文档 + 人工确认点 | 高风险迁移需要备份和回滚方案 |

### 沉淀步骤

1. **保留原始证据**：错误输出、diff、命令和任务卡，不凭记忆复盘。
2. **归因到流程**：确认是规则、任务边界、测试、工具还是人工判断缺失。
3. **只选一个主要控制**：能写测试就不只写提醒；能 lint 就不靠人眼。
4. **写成可执行条件**：说明触发场景、预期行为、验证方法，避免“注意安全”这类空话。
5. **验证控制有效**：故意复现原场景或运行相关测试，确认新控制能拦住。
6. **2～3 个任务后复查**：有效保留；无效删除或改写，避免规则无限增长。

### 沉淀记录

```text
### 规则或测试沉淀

- 重复现象：
- 原始证据：
- 根因分类：
- 控制方式：AGENTS 规则 / 测试 / lint / 类型检查 / 检查清单 / 文档
- 具体改动：
- 触发场景：
- 预期行为：
- 验证方式：
- 复查日期：
- 复查结论：保留 / 调整 / 删除
```

### 规则质量检查

- [ ] 说的是具体触发条件和可观察行为，不是抽象口号。
- [ ] 与现有规则不重复；冲突时已明确优先级。
- [ ] 有对应测试、lint 或人工检查方式。
- [ ] 没有把单个偶发问题过度泛化。
- [ ] 没有把项目细节塞进通用模板；项目规则放在目标项目的 `AGENTS.md`。

## 6. 最小复盘结论

每个任务至少回答三句话：

1. 这次是否按任务卡交付，证据是否可复跑。
2. 最大的失败或返工来自哪一类问题。
3. 下一次用什么规则、测试或检查更早拦住它。
