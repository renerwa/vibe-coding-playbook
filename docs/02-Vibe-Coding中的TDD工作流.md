# Vibe Coding 中的 TDD 工作流

> 用途：说明如何让 AI Agent 按 TDD 方式开发，以及人应该在哪些节点验收。
> 最后更新：2026-11-06
> 前置知识：TDD 的定义、红绿重构循环和适用边界见 [TDD 开发模式](01-TDD开发模式.md)。本文不重复介绍。
> 不覆盖：测试运行器的内部机制见 [测试运行器原理与输出](03-测试运行器原理与输出.md)；完整代码案例见 [TDD 项目实例](04-TDD项目实例.md)。

## 核心原则

在 Vibe Coding 中，TDD 的作用不只是“让 AI 多写几个测试”，而是把需求变成一条可执行的协作边界：

- **人负责定义正确**：确认业务规则、验收场景和风险边界；
- **Agent 负责实现与验证**：写测试、写代码、运行命令并汇报证据；
- **测试负责充当合同**：实现可以变，但测试描述的业务行为不能被随意改动；
- **CI 负责重复验证**：在干净环境中重新执行，避免只依赖本机结果。

人不需要亲手敲测试代码，但必须对“测试是否覆盖了正确的事”负责。

## 最小工作流

### 1. 切出一个小任务

一次只交付一个可以独立验收的行为。例如不要直接做“完整订单系统”，而是先做“金额满 100 元时减免 10 元”。

产出物：

- 一句话目标；
- 明确的输入和输出；
- 不在本次范围内的内容。

### 2. 写清验收例子

至少列出三类例子：

- 正常情况：最常见、最有价值的路径；
- 边界情况：刚好等于阈值、空值、最大值等；
- 异常情况：非法输入、缺少权限、外部服务失败等。

例如“满 100 减 10”：

| 场景 | 输入 | 预期 |
|---|---|---|
| 正常 | 120 元 | 应付 110 元 |
| 边界 | 刚好 100 元 | 应付 90 元 |
| 边界 | 99.99 元 | 应付 99.99 元 |
| 异常 | 负数金额 | 拒绝并返回明确错误 |

### 3. 让 Agent 只写测试

要求 Agent 本阶段只新增或修改测试，不修改业务实现。测试写完后必须运行，并展示真实的失败输出。

此阶段进入“红灯”。红灯的具体含义见 [TDD 开发模式](01-TDD开发模式.md#核心循环红绿重构)。

### 4. 人工审查测试

重点看四件事：

1. 测试是否覆盖了前面的验收例子；
2. 断言是否检查业务结果，而不是绑定内部实现；
3. 是否存在一个测试同时检查太多行为；
4. 失败原因是否是“功能尚未实现”，而不是环境或语法错误。

如果测试本身写错，先修测试，不要急着进入实现。

### 5. 让 Agent 写最小实现

确认测试合理后，再要求 Agent 修改业务代码，使测试通过。实现阶段不允许为了让测试变绿而删除或弱化测试。

建议先运行目标测试，再运行完整测试集。此阶段进入“绿灯”。

### 6. 单独进行重构

重构应作为独立步骤提出，并明确约束：不改变外部行为、不修改测试预期、重构后重新运行全套测试。

### 7. 人工验收并记录证据

自动化测试通过后，还要验证测试难以覆盖的部分，例如页面观感、真实外部服务、权限策略和操作体验。最终保留：

- 验收条件；
- 实际执行的测试命令；
- 通过数量和失败信息；
- 人工验收结论。

## 可直接复用的提示词

### 只写测试

```text
目标：【本次要实现的一个行为】

验收场景：
1. 【正常场景】
2. 【边界场景】
3. 【异常场景】

本阶段只写测试，不修改业务实现。
请遵循项目现有测试目录和命名约定，复用已有测试工具。
完成后运行相关测试，展示真实失败输出，并逐条说明失败原因。
不要为了让测试通过而跳过、弱化或删除测试。
完成后停止，等待我确认。
```

### 写最小实现

```text
现在进入实现阶段。
请读取当前失败的测试，写出满足这些测试的最小业务实现。
不要修改测试的预期行为。
完成后先运行目标测试，再运行完整测试集。
请给出：修改文件、关键设计取舍、完整命令、最终结果和退出码。
如果存在失败，请先定位原因，不要用跳过测试的方式处理。
```

### 重构

```text
现在只做重构，不增加新功能，不改变外部行为，不修改测试预期。
请说明要改善的问题，并按小步骤修改。
每次修改后运行相关测试，最终运行完整测试集。
如果重构需要改变接口或行为，先停下来，把它当作新任务另行讨论。
```

## 给 Agent 的上下文清单

为了减少返工，任务开始时提供以下信息：

- 业务目标和不在范围内的内容；
- 相关接口、数据结构或页面行为；
- 正常、边界、异常验收例子；
- 项目现有目录和命名约定；
- 测试命令、运行环境和依赖安装方式；
- 不能改动的模块、数据或兼容性要求。

上下文不是越多越好。只提供完成任务所必需的规则和文件，避免把整个仓库和历史争论一次性塞进去。

## 每轮必须检查的关卡

- **红灯关卡**：测试是否真的失败，原因是否合理；
- **测试审查关卡**：测试是否检查了业务行为，而非实现细节；
- **实现关卡**：Agent 是否修改或绕过了测试；
- **回归关卡**：完整测试集是否全部通过；
- **验收关卡**：关键业务流程是否经过人工确认。

## 常见反模式

- 让 Agent 同一轮同时写测试和实现，测试容易倒推成“证明当前实现正确”；
- Agent 一遇到失败就修改测试，而不是修业务代码；
- 一次任务覆盖多个模块，红灯范围过大，难以定位；
- 大量模拟外部依赖，测试全绿但真实集成仍然失败；
- 只相信“测试已通过”的文字，不检查命令、输出和退出码；
- 把绿灯直接等同于需求完成，跳过人工验收和异常场景检查。

## 完成定义

一个 TDD 任务只有同时满足以下条件才算完成：

1. 验收场景已转成自动化测试；
2. 测试曾真实经历失败，之后才通过；
3. 实现没有通过修改测试来规避问题；
4. 完整测试集通过；
5. 关键业务流程已人工验收；
6. 测试命令和结果可复现。
