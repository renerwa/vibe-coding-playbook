# TDD 开发模式

> 用途：解释 TDD 是什么、为什么有效，以及它的核心工作循环。
> 最后更新：2026-11-03
> 不覆盖：AI 协作步骤、测试运行器机制、完整项目示例。分别见 [02](02-Vibe-Coding中的TDD工作流.md)、[03](03-测试运行器原理与输出.md)、[04](04-TDD项目实例.md)。

## 一句话定义

TDD（Test-Driven Development，测试驱动开发）是一种“先定义怎样算做对，再实现功能”的开发模式。它把测试当作可执行的需求说明，用测试结果驱动代码设计和实现。

它关注的重点不是“测试覆盖率有多高”，而是：

- 在写代码前，是否已经明确了可验证的预期行为；
- 每次只实现一个足够小的行为；
- 修改代码后，能否快速确认原有行为没有被破坏。

## 它解决什么问题

1. **需求含糊**：只写“支持优惠券”无法验收，写成具体输入和预期输出后才能开发。
2. **反馈太晚**：等全部功能做完再测，问题会集中暴露，定位和修复成本更高。
3. **回归风险**：修复一个 Bug 时，容易破坏另一个已有功能。自动化测试可以充当安全网。
4. **AI 或开发者“看起来做完了”**：测试提供了可重复执行的完成标准，而不是只凭主观感觉判断。

## 核心循环：红、绿、重构

“红”和“绿”是测试结果的比喻，不是两个工具，也不是额外的开发阶段。测试失败常显示为红色，测试通过常显示为绿色。

### 1. 红（Red）：先写一个会失败的测试

为下一个最小行为写测试，然后运行它。此时功能通常还没实现，所以测试应当失败。

先看到失败有两个目的：

- 证明测试确实在检查目标行为；
- 避免测试因为写错、没有断言或根本没有被执行而“假通过”。

需要检查失败原因是否符合预期。理想情况是“功能尚未实现”；如果失败来自文件路径错误、依赖缺失或语法错误，应先修正测试环境。

### 2. 绿（Green）：写最少代码让测试通过

只实现当前测试要求的最小行为，不顺手扩展尚未定义的功能。运行测试，直到它通过。

“最少”不是永久简陋，而是避免在没有测试保护时一次加入过多逻辑。复杂度应该在后续循环中由新的测试逐步拉出来。

### 3. 重构（Refactor）：在绿灯保护下整理代码

在不改变外部行为的前提下，调整命名、拆分函数、消除重复或改善结构。每次小步修改后重新运行测试，确保仍然是绿灯。

重构不是重写功能；它应当保持已有测试所描述的行为不变。

## 四条关键原则

1. **测试先行**：先写预期，再写实现。
2. **小步前进**：一次只增加一个可描述、可验证的行为。
3. **测试行为，不绑定实现细节**：优先验证输入、输出和状态变化，不要断言内部调用了哪个私有函数。
4. **完成前运行完整测试集**：不仅运行新测试，也要确认旧功能没有被破坏。

## 概念边界

- **单元测试**：直接验证一个小模块或函数的测试，通常速度快、隔离性强。
- **集成测试**：验证多个模块、数据库或 API 组合在一起时的行为。
- **回归测试**：用于确认修改后原有行为仍然正确的测试。
- **TDD 是一种开发节奏**，不等于只写单元测试，也不等于所有测试都必须先写。

## 适合与不适合

| 场景 | 适用程度 | 说明 |
|---|---|---|
| 稳定的业务规则 | 高 | 输入输出明确，容易写自动化断言 |
| API 契约、数据转换 | 高 | 适合先定义请求、响应和异常 |
| Bug 修复 | 高 | 先写复现测试，再修复，防止问题回归 |
| 需求探索、一次性原型 | 中低 | 规则还在变化，先验证方向可能更重要 |
| 纯视觉设计、主观体验 | 低 | 机器难以判断“好不好看”，需要人工评审 |

## 常见误解

- **“TDD 就是写完再补测试”**：不是。核心区别是测试先于实现，并驱动设计。
- **“绿灯就代表系统正确”**：不是。绿灯只代表现有测试通过；测试可能漏掉关键场景。
- **“所有代码都必须 100% 覆盖”**：不是。优先覆盖核心业务规则、关键路径和高风险边界。
- **“TDD 不需要设计”**：不是。测试会推动接口和职责拆分，但仍需要整体设计。

## 最小落地标准

如果只想开始实践，先做到这四点：

1. 每个任务写出正常、边界、异常三类验收例子；
2. 每次只处理一个行为；
3. 先运行测试确认失败，再写实现；
4. 提交前运行完整测试集，并保留可复现的命令与结果。
