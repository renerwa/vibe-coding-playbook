# Cloudflare Workers 入门指南：边缘能解决什么，不能解决什么

> 用途：用一条从“用户请求”到“数据库返回”的链路，解释 Cloudflare Workers 与 Serverless、边缘计算的关系，以及为什么通常只迁移一部分函数、什么时候值得用。
> 最后更新：2026-11-14
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[什么是 Runtime](08-什么是Runtime.md)、[什么是沙箱](12-什么是沙箱.md)。
> 不覆盖：最新价格与配额的具体数字、完整 API、Durable Objects 的深入设计、具体框架迁移步骤。

## 先记住三句话

1. **Cloudflare Workers 是 Serverless，但不是普通 Serverless，而是“边缘 Serverless”。**
2. **它把代码放到离用户更近的节点，但不会把数据库也搬过去。**
3. **它最擅长让请求在边缘结束；如果每个请求都必须回中心数据库，收益会很小。**

如果只记一张图：

```text
用户
  │
  ▼
最近的 Cloudflare 边缘节点（Worker）
  ├─ 能本地判断 / 缓存命中 → 直接返回
  └─ 必须查数据 / 做事务 → 中心后端 / 数据库
```

这张图就是全文主线：**边缘负责“就近决策”，中心负责“数据和事务”。**

## 一、先把三个词分开：Worker、Serverless、Edge

这三个词经常被混在一起，但它们回答的是不同问题。

| 概念 | 回答的问题 | 容易误解 |
|---|---|---|
| Serverless | 谁管服务器、怎么扩容、怎么计费 | 不是“没有服务器” |
| Edge（边缘） | 代码在哪里执行 | 不是“数据也在本地” |
| Worker | 用什么执行、具体是什么产品 | 不是“所有后端都能直接搬” |
| Isolate | 执行环境有多重 | 不是虚拟机，也不是完整容器 |
| 事件驱动 | 什么触发代码 | 不是只能处理 HTTP 请求 |

所以更准确的公式是：

> **Cloudflare Workers = Serverless 的运维与计费模式 + Edge 的部署位置 + V8 isolate 的执行方式 + 事件驱动的编程模型。**

### 1. Serverless 不是“没有服务器”

Serverless 的意思是：**你不用自己采购、启动、打补丁和扩容服务器，平台替你管理，你按请求或资源付费。**

服务器仍然存在，只是从“你管”变成“平台管”。所以 Serverless 不是一种语言，也不是一个具体产品，而是一种运维和计费模式。

### 2. Edge 不是“把数据库也搬过去”

“边缘”指的是离用户较近的网络节点，通常叫 PoP（Point of Presence，接入点）。它缩短的是“用户到代码”的距离。

它不会自动缩短“代码到数据库”的距离。如果代码在边缘，但每次都要回中心数据库，数据库那段延迟仍然存在。

### 3. Worker 是部署单元，不一定只对应一个函数

“Worker”这个词在程序员嘴里很泛，可能指：

- 浏览器或 Node.js 里的并发线程（Web Worker / worker thread）；
- 后台任务消费者（queue worker / celery worker）；
- Cloudflare Workers 这个边缘计算产品。

本文只讨论最后一种。还要注意：**一个 Cloudflare Worker 是一个部署单元，不一定只对应一个函数。** 一个 Worker 可以按路径、域名或事件类型路由多个处理逻辑。

## 二、它和“把 serverful 改成 serverless”是什么关系

结论先说：

> **Cloudflare Workers 不是把整个 serverful 自动转换成 serverless，而是让你把 serverful 中适合放到边缘的那一部分，改造成边缘 serverless。**

关键词是三个：**一部分、边缘、重新设计**。

实际项目里常见三种关系：

| 模式 | Worker 的角色 | 原来的后端 | 典型场景 |
|---|---|---|---|
| 边缘网关 | 鉴权、路由、限流、改请求头、缓存 | 保留，继续做核心业务 | 最常见 |
| 局部替换 | 替代重定向、Webhook、轻量 API、图片处理 | 部分保留 | 渐进式改造 |
| Serverless 原生 | 整个应用基于 Worker + KV/R2/D1/Queues 等构建 | 可能不再需要传统服务器 | 新项目、简单应用 |

大多数真实系统最终不是“纯 serverless”，而是：

```text
边缘 Worker：鉴权、路由、缓存、限流
        │
        ▼
中心后端：订单、支付、复杂事务
        │
        ▼
中心数据库
```

也就是：

> **边缘 Worker + 中心 serverful 后端 + 托管数据库/存储**

只迁移一部分函数，不是妥协，而是边缘计算的正常姿势。因为边缘的收益来自“少回源、少查库”，不是来自“把所有代码都放过去”。

## 三、请求链路与延迟预算

先看传统 Web 请求的路径：

```text
用户
  │
  ▼
DNS 解析
  │
  ▼
中心机房的应用服务器
  │
  ▼
数据库
  │
  ▼
逐层返回
```

这里每一段都可能产生网络往返。用户在欧洲，服务器在美国，一次请求就要跨大西洋；如果一次页面加载要调用五六个接口，延迟会不断累加。

Cloudflare Workers 把代码放到边缘后，路径变成：

```text
用户
  │
  ▼
最近的 Cloudflare 节点（PoP）
  │  路由匹配：这个 URL 归哪个 Worker 管？
  ▼
Worker 运行时（V8 isolate）
  │  执行 fetch(request, env, ctx)
  ├─ 读取绑定资源：KV / R2 / D1 / Queues ...
  ├─ 调用上游 API 或源站
  ▼
返回响应（可写入缓存）
```

V8 是 Chrome 使用的 JavaScript 引擎；isolate 是 V8 里的轻量隔离运行时，很多 isolate 可以共享一个进程。

但“放到边缘”不等于“所有延迟都消失”。可以把一次请求拆成几段：

| 延迟来源 | 传统服务器 | Worker | 边缘能否明显改善 |
|---|---|---|---|
| 用户到计算节点 | 可能跨洲 | 通常到较近节点 | 能 |
| TLS 握手 | 可能跨区 | 已接入 Cloudflare 代理时本就在边缘完成 | 不是 Worker 的增量收益 |
| 边缘执行代码 | 没有 | 有少量计算和初始化成本 | 可能增加一点 |
| 边缘到源站 | 没有 | 需要回源时仍然存在 | 不能消除 |
| 源站到数据库 | 存在 | 存在 | 不能消除 |
| 数据库查询本身 | 存在 | 存在 | 不能消除 |

一个容易忽略的事实：**如果你已经把域名接入 Cloudflare 代理（CDN，内容分发网络），TLS（加密连接握手）本来就在边缘终止。** Worker 带来的增量主要是“在边缘执行逻辑”和“少回源”，不是“第一次把 TLS 变近”。

### “在最近的地方启动一个运行环境”这句话，需要修正

这个说法接近，但不精确。

更准确的理解是：

> **Cloudflare 在节点上维护可复用的运行时池。请求来了，平台把代码交给一个已经准备好的 V8 isolate 执行；没有可用实例时，才需要初始化。**

不是每个请求都新开一台虚拟机，也不是每个请求都启动一个容器。它是轻量运行时，通常比传统 Serverless 的冷启动轻，但“完全零冷启动（第一次执行或长时间未执行后的初始化）”也不准确：代码初始化、加载依赖仍然可能耗时。

“最近”也要加限定：通常是离用户较近的 Cloudflare 节点，实际路由会受网络状况、节点容量和 Anycast（任播，同一个地址在全球多处宣告）路由影响。它不是用户的手机，也不一定是物理距离最近的机房。

## 四、边缘到底能省什么、不能省什么

这是判断“值不值得用”的核心。

### 能省的东西

| 能省的东西 | 例子 | 效果 |
|---|---|---|
| 回源请求 | 缓存命中、静态响应、重定向、A/B 分流 | 最明显 |
| 数据库查询 | 本地校验 JWT（带签名的令牌）、检查 API Key、读取功能开关 | 明显 |
| 跨区往返次数 | 在边缘聚合多个上游请求、并行调用 | 中等 |
| 连接建立成本 | 连接复用、Hyperdrive 连接池 | 中等 |
| 源站压力 | 拦截无效请求、机器人、超限流量 | 降低源站负载 |
| 故障切换 | 把请求路由到健康的后端 | 提升可用性 |

### 不能省的东西

| 不能省的东西 | 原因 |
|---|---|
| 中心数据库的 RTT（Round-Trip Time，往返时间） | 数据在远方，查询就要走那么远 |
| 强事务和复杂一致性 | 订单、支付、库存扣减通常要集中处理 |
| 重计算 | 视频转码、批量处理受 CPU 和时长限制 |
| 大文件传输 | 请求体、流量和成本都会放大 |
| 数据驻留合规 | 代码全球执行不等于数据可以全球存储 |
| 冷启动和新增一跳 | 边缘执行本身也有成本，路径可能变长 |

一句话：

> **边缘省的是“回源次数”，不是“数据库距离”。**

### 一个具体的延迟对比

假设用户在新加坡，中心数据库在美国，跨洋 RTT 约 200ms。以下数字只是示意，不是实测值。

```text
没有 Worker：
用户（新加坡） → 源站（美国） → 数据库（美国）
约 200ms + 本地数据库耗时

有 Worker，但每个请求都查美国数据库：
用户（新加坡） → Worker（新加坡） → 数据库（美国）
约 5ms + 200ms

有 Worker，且能在边缘缓存/验签后直接返回：
用户（新加坡） → Worker（新加坡） → 返回
约 5ms
```

结论很清楚：**如果每个请求都必须回中心数据库，Worker 只是把第一段变短，第二段仍然存在；如果请求能在边缘结束，收益才明显。**

可以用一个粗略公式判断：

> **边缘收益 ≈ 被避免的回源次数 × 每次回源节省的 RTT + 本地处理节省的时间 − 新增的一跳、冷启动和一致性成本。**

如果“被避免的回源次数”接近零，这个公式很可能算不过来。

## 五、一个具体架构：边缘网关 + 中心后端

比“把整个后端搬上去”更常见的，是下面这个结构：

```text
用户
  │
  ▼
边缘 Worker
  ├─ 校验 Token / API Key
  ├─ 限流、黑白名单、A/B 分流
  ├─ 查询边缘缓存
  ├─ 补充租户/区域请求头
  └─ 命中 → 直接返回
       │
       └─ 未命中 → 中心 API → 数据库
```

### 例子 1：跨境 SaaS 的登录鉴权

用户分布在欧洲、东南亚和北美。客户端每次请求都带一个 Token。可以把三件事放到 Worker：

1. 用公钥在本地校验 Token 的签名和有效期；
2. 从 Token 中取出租户 ID，补到请求头里；
3. 根据租户所在区域，把请求转发到合适的后端。

无效请求在边缘就被拒绝，不用占用中心服务器。有效请求也只多经过一小段边缘逻辑。

这里的关键是：**签名校验可以在本地完成，不需要每次查数据库。** 但 Token 吊销列表可能需要 KV、Durable Objects 或中心服务，并且要接受一定的传播延迟。这个取舍必须在设计时说清楚。

### 例子 2：商品详情页

| 请求 | 边缘能做什么 | 仍然要回中心什么 |
|---|---|---|
| 商品详情 | 缓存商品 JSON、图片和 HTML 片段 | 价格、库存等强实时字段 |
| 搜索列表 | 缓存热门查询结果 | 个性化排序、实时库存 |
| 下单 | 校验登录态、做基础限流 | 订单创建、支付、库存扣减 |
| Webhook | 验签、去重、写入队列 | 真正的业务处理 |

这个结构解决的是：

- 无效请求不必回源；
- 缓存命中不必查库；
- 简单判断可以就近完成；
- 源站只处理真正需要它的请求。

它没有解决的是：

- 数据库仍然在中心；
- 订单和支付仍然要集中事务；
- 缓存仍然要考虑过期和一致性；
- 用户资料如果每次都必须读中心库，边缘收益有限。

## 六、Binding：资源接口，不是本地资源

Cloudflare Workers 通过 **Binding（绑定）** 访问平台资源。绑定在配置文件里声明，代码通过 `env` 使用。

常见能力可以这样理解：

| 能力 | 一句话解释 | 架构上的含义 |
|---|---|---|
| Workers KV | 全球分布的键值存储 | 读取快，但最终一致，不适合余额和库存 |
| R2 | 兼容 S3 的对象存储 | 适合图片、备份、日志，不是数据库 |
| D1 | 基于 SQLite 的 SQL 数据库 | 适合轻量关系型数据，不是 MySQL/PostgreSQL 的完全替代 |
| Queues | 异步消息队列 | 通常是“至少一次”投递，消费者要幂等（重复执行结果一致） |
| Durable Objects | 有状态、可协调的对象 | 单个对象内强一致，适合聊天室、计数器、锁 |
| Cron Triggers | 定时触发 | 使用 UTC，任务要短小 |
| Hyperdrive | 加速访问区域数据库 | 优化连接建立和路径，不消除查询 RTT |
| Workers AI | 在 Cloudflare 网络上调用模型推理 | 模型能力、成本和限制要单独评估 |
| Service Bindings | Worker 之间内部调用 | 需要清晰的服务边界 |

这里必须澄清一个关键点：

> **Binding 不是把数据库变成本地变量。它只是让 Worker 通过平台接口访问资源。**

还有一个相关事实：**Worker 通常是无状态的。** 同一个用户的两次请求可能落在不同的 isolate 上，内存里的变量不能当作可靠存储。需要状态时，要用 KV、D1、Durable Objects 等外部能力。

所以：

- Worker 访问中心数据库，仍然是远程调用；
- Hyperdrive 主要优化连接建立和网络路径，不会让查询变成“本地查询”；
- KV、D1 的只读复制能力（具体以官方为准）可以让部分数据更近，但要接受一致性代价；
- Durable Objects 解决的是“某个对象的协调”，不是通用报表和复杂查询；
- Queues 把任务异步化，但消费者仍然要访问真正的业务系统。

这也是为什么“边缘函数还要访问数据库，不是一样远程调用吗”这个质疑是成立的。区别只在于：**有些请求可以在边缘结束，有些不能。边缘计算的价值取决于前者占多少。**

## 七、最小代码与部署

下面这段代码会在 `/api/hello` 返回一个 JSON：

```js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);

    if (url.pathname === "/api/hello") {
      return Response.json({
        message: "Hello from the edge",
        colo: request.cf?.colo ?? "unknown"
      });
    }

    return new Response("Not Found", { status: 404 });
  }
};
```

三个参数分别是：

- `request`：进来的请求，包含 URL、方法、请求头和请求体。
- `env`：绑定资源，例如 `env.MY_KV`、`env.MY_DB`。
- `ctx`：请求生命周期工具，例如用 `ctx.waitUntil()` 在返回响应后继续做日志上报等收尾工作。

`request.cf.colo` 是处理这次请求的 Cloudflare 节点代码，例如 `HKG`、`SIN`，调试时可以用它确认请求落在哪个机房。

一个对应的 `wrangler.toml` 可能长这样：

```toml
name = "hello-worker"
main = "src/index.js"
compatibility_date = "2025-01-01"
```

`compatibility_date` 不是版本号，而是用来固定运行时行为的日期。它会影响某些 API 的默认行为，实际项目应以初始化模板生成的日期为准，不要随意改动。

本地开发和部署通常用 `wrangler`（Cloudflare 的命令行工具）：

```bash
npm create cloudflare@latest hello-worker
cd hello-worker
npx wrangler dev
npx wrangler deploy
```

- `wrangler dev` 在本地模拟 Worker 运行环境；
- `wrangler deploy` 把代码发布到 Cloudflare 网络。

本地能跑通，不代表生产一定正确。本地模拟不覆盖真实网络、缓存、权限、证书和存储行为，后面会专门讲验证。

## 八、它和普通 Serverless 的区别

Cloudflare Workers 是 Serverless 的一个分支，但和“普通 Serverless”不完全一样。

| 维度 | 普通 Serverless（例如 AWS Lambda） | Cloudflare Workers |
|---|---|---|
| 部署位置 | 通常部署在某个区域 | 部署到全球边缘网络 |
| 执行单位 | 微虚拟机或容器一类 | V8 isolate |
| 启动成本 | 通常更重 | 通常更轻 |
| 运行时 | 支持语言和系统能力更完整 | 以 JS/TS、WASM（WebAssembly，一种可移植的二进制格式）为主，Node.js 只部分兼容 |
| 典型用途 | 通用事件处理、后端任务 | 边缘鉴权、路由、轻量 API |
| 主要限制 | 冷启动、区域延迟 | 运行时限制、边缘到数据仍然远程 |

可以这样记：

> **普通 Serverless 解决“不用管服务器”；边缘 Serverless 还多解决“代码离用户近”。**

同类产品还有 Vercel Edge Functions、Deno Deploy、Fastly Compute、AWS Lambda@Edge 等。它们都属于“Serverless + 边缘”的不同组合，运行时、限制和生态不一样，不能简单互换。

另外，Cloudflare Pages 的 Functions 也构建在 Workers 之上。如果项目是静态站点加少量接口，Pages 可能比单独管理 Worker 更顺手。

## 九、什么时候值得用

先看一个二维判断：

| | 请求能在边缘结束 | 请求必须回中心数据 |
|---|---|---|
| 全球用户、延迟敏感 | 高收益 | 收益有限，先优化数据层 |
| 单区域用户、源站就在附近 | 收益有限 | 不建议为边缘而边缘 |

再看具体问题：

| 问题 | 如果是 | 如果否 |
|---|---|---|
| 用户是否分布在全球，且延迟敏感？ | 边缘执行可能有明显收益 | 先别为了“边缘”而上边缘 |
| 逻辑是否短小、事件驱动？ | 适合 Worker | 重计算、长任务要换方案 |
| 是否能避免回源或数据库查询？ | 收益可能明显 | 收益通常有限 |
| 能否接受最终一致、缓存延迟？ | 可以用 KV/缓存 | 需要强一致，留在中心 |
| 能否接受运行时和平台限制？ | 可以进入方案设计 | 不要假设“以后都能兼容” |
| 是否有明确指标，例如 p95（95% 请求的延迟上限）、回源率、数据库查询数？ | 可以做可验证的试点 | 先定义指标，否则无法判断收益 |
| 团队是否能维护日志、回滚、安全和配额？ | 可以上线 | 先补运维能力，再谈上线 |

一页纸判断流程：

```text
这个请求必须访问中心数据库吗？
├─ 否 → 适合放到边缘
└─ 是 → 能缓存、读副本或异步处理吗？
    ├─ 能 → 边缘可能有用，但要验证一致性
    └─ 不能 → 留在中心，不要为了边缘而边缘
```

最小可行方案不需要重构整个后端：

1. 选一个边界清晰的场景，例如“登录鉴权”或“统一重定向”；
2. 记录现状基线：p50/p95 延迟、回源率、数据库查询数、源站 QPS（每秒请求数）；
3. 只把这一小段逻辑放到 Worker；
4. 灰度 5% 流量，观察至少一个完整业务周期；
5. 用数据决定扩大、保留还是回滚。

如果试点只证明了“能返回 Hello World”，那还不算完成。真正有价值的结果是：**回源少了多少、数据库查询少了多少、p95 改善多少、故障时是否可控、每月多花多少钱。**

## 十、成本和限制：免费不等于零成本

Cloudflare Workers 的计费通常围绕两类资源：**请求数**和**CPU 时间**。免费额度适合开发和轻量验证，但生产环境要按峰值请求、CPU 消耗和配套资源一起估算。具体配额和价格会调整，上线前必须查官方最新文档。

需要区分两个时间概念：

- **CPU 时间**：代码真正消耗处理器的时间；
- **墙上时钟时间**：从请求开始到响应结束的真实耗时，包含等待网络、等待数据库等。

Worker 可能在等待 I/O 时不消耗多少 CPU，但仍然有请求时长限制。所以“CPU 没超”不等于“请求可以无限等待”。

常见限制还包括：内存、请求体大小、子请求数量、代码包大小、运行时 API 兼容性。具体数字会调整，上线前应以 Cloudflare 官方 limits 文档为准。

| 成本项 | 说明 |
|---|---|
| Worker 请求与 CPU | 按请求数和计算时间计费 |
| KV / D1 / R2 / Queues | 读写次数、存储、消息数量 |
| 日志与追踪 | 采样、保留时间、导出可能产生费用 |
| 源站与第三方 API | Worker 回源仍然消耗对方资源 |
| 工程成本 | 拆分、迁移、观测、回滚和安全测试 |

R2 的一个常见卖点是**不收出口流量费**，但这不等于所有 Cloudflare 服务都免费，也不等于没有存储和操作成本。

还要注意三类“非价格成本”：

1. **平台锁定**：代码依赖 Workers 运行时、Binding 和 Durable Objects 后，迁移不是改一个配置就能完成。
2. **可观测性**：日志是否全量、保留多久、能否按请求追踪，都会影响排障。不要假设默认日志足够。
3. **本地与生产差异**：本地模拟能验证基本逻辑，但真实网络、缓存、权限、证书和存储行为仍要在预发布环境验证。

## 十一、上线前怎么验证

Cloudflare Workers 很容易“看起来能用”：返回一个 Hello World，延迟很低，部署很快。但真正要验证的是：**在真实流量、真实故障和真实权限下，它是否仍然正确。**

| 指标 | 怎么测 | 通过标准 |
|---|---|---|
| 回源率 | 对比上线前后源站请求量 | 该减少的请求确实减少 |
| 每请求数据库查询数 | 看日志、追踪或数据库指标 | 边缘没有偷偷增加查库次数 |
| 地域延迟 | 从主要用户地区测 p50/p95 | 有可解释的改善，长尾没有变差 |
| 错误率 | 对比 4xx/5xx 和超时 | 不明显高于原方案 |
| 缓存命中率 | 看命中、未命中、过期、清除 | 个性化内容不会被错误缓存 |
| 鉴权 | 测无效、过期、伪造、无权限 Token | 该拒绝的在边缘拒绝，且不泄露信息 |
| 依赖故障 | 模拟 KV、D1、R2、上游 API 超时 | 有明确降级或错误响应，不静默成功 |
| 回滚 | 发布坏版本再回滚 | 能在可接受时间内恢复 |
| 成本 | 按峰值请求和 CPU 消耗估算 | 在预算内，且知道最坏情况 |
| 安全与合规 | 检查密钥、CORS（跨域策略）、SSRF（服务端请求伪造）、PII（个人敏感信息）、数据地区 | 满足业务和安全要求 |

建议的验证顺序是：**先功能，再故障，再性能，最后成本和合规**。不要一开始就压测，因为功能错了，性能数字没有意义。

一个实用的上线方式是灰度：先让 5% 的流量经过 Worker，对比错误率、p95 延迟、回源率和源站负载；确认稳定后再扩大。不要一次性把全部流量切过去。

## 十二、常见误区

- **“Cloudflare Workers 是免费 CDN”**：CDN 主要缓存内容，Workers 执行代码；免费额度也不是无限量。
- **“可以把整个后端原样搬上去”**：运行时、状态、数据访问、失败处理都要改，不是改部署方式。
- **“边缘一定比中心快”**：如果每次都要回中心数据库，边缘只省了第一段，甚至可能多一跳。
- **“无状态所以更简单”**：无状态意味着不能依赖内存，必须显式设计存储、一致性和并发。
- **“代码全球部署，数据也全球”**：代码执行位置和数据存储位置是两件事，合规要分别确认。
- **“本地能跑，生产就没问题”**：本地模拟不覆盖真实网络、缓存、证书、权限和存储行为。
- **“Workers 就是 Node.js”**：只兼容一部分 Node.js API，很多包和原生依赖不能直接用。
- **“用了 Serverless 就不用运维”**：仍然要管配置、日志、告警、回滚、安全和成本。
- **“Durable Objects 可以替代数据库”**：它解决的是单个对象的状态协调，不是通用查询和报表。
- **“只迁移一部分说明方案不彻底”**：边缘计算本来就应该只迁移适合边缘的那部分。

## 十三、术语速查

| 术语 | 一句话解释 |
|---|---|
| Serverless | 平台管理服务器，开发者按请求或资源付费 |
| Edge（边缘） | 离用户较近的网络节点，不等于用户设备 |
| PoP | Point of Presence，Cloudflare 的接入机房 |
| Anycast | 同一个地址在全球多处宣告，让用户被路由到较近节点 |
| Isolate | V8 里的轻量隔离运行时，启动成本低于虚拟机 |
| Binding | 把 KV、R2、D1 等资源以配置方式接到 Worker 上 |
| Cold start | 代码第一次执行或长时间未执行后的初始化成本 |
| Origin（源站） | Worker 后面的原始服务器或后端服务 |
| CDN | 内容分发网络，主要把静态内容缓存到离用户近的节点 |
| RTT | Round-Trip Time，一次请求和响应往返的时间 |
| p95 | 95% 的请求都快于这个值，用来观察长尾延迟 |
| Idempotent（幂等） | 同一个操作执行多次，结果与执行一次相同 |

## 最小掌握标准

做到下面五条，就足够在日常协作和方案判断中不被名词带偏：

1. 能说出 Cloudflare Workers 的本质：部署在边缘的 Serverless 请求/事件处理器。
2. 能区分 Serverless、Edge、Worker 三个概念分别回答什么问题。
3. 知道它适合短小、事件驱动、能在边缘结束的逻辑，不适合重计算和复杂事务。
4. 知道“无状态”“最终一致”“至少一次投递”分别意味着什么风险。
5. 能用回源率、数据库查询数、p95 延迟和成本四项指标验证是否值得用。

下面这些可以暂缓，不影响日常判断：

- V8 isolate 的底层实现和调度细节；
- Durable Objects 的完整一致性设计；
- Workers 所有绑定服务的 API；
- 具体框架的迁移和构建配置。

## 一句话记忆

> **边缘不是把数据库搬到用户身边，而是把“不需要数据库的决策”搬到用户身边；能本地结束的请求越多，边缘越有价值。**
