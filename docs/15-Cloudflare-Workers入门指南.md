# Cloudflare Workers 入门指南：把代码放到离用户最近的边缘

> 用途：解释 Cloudflare Workers 是什么、解决什么问题、如何工作、适合与不适合什么场景，以及产品和工程上如何判断是否该用。
> 最后更新：2026-11-14
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[什么是 Runtime](08-什么是Runtime.md)、[什么是沙箱](12-什么是沙箱.md)。
> 不覆盖：最新价格与配额的具体数字、完整 API、Durable Objects 的深入设计、具体框架迁移步骤。

## 一句话结论

> **Cloudflare Workers 不是“另一台服务器”，而是“部署在全球边缘节点上的请求处理函数”。用户请求到达离他最近的节点，代码就地执行并返回结果，不必先回到某个中心机房。**

如果只记一个比喻：

> **传统后端像“全城只有一家总店”；CDN 像“把成品海报提前贴到各小区”；Cloudflare Workers 像“每个小区都有一间能做简单加工的小店”。**

这三者的区别不在于谁更高级，而在于**把什么放到离用户更近的地方**：CDN 放的是静态文件，Cloudflare Workers 放的是可以执行的一小段代码。

## 一、先分清：Worker 和 Cloudflare Workers 不是一回事

“Worker”在程序员嘴里是一个很泛的词，通常指“负责干活的执行单元”。它至少有三类常见含义：

| 说法 | 通常指什么 | 主要解决什么问题 |
|---|---|---|
| Web Worker / worker thread | 浏览器或 Node.js 里的并发线程 | 不让主线程被耗时计算卡住 |
| queue worker / celery worker | 后台任务消费者 | 异步处理、削峰、失败重试 |
| Cloudflare Workers | Cloudflare 的边缘计算产品 | 让代码在离用户近的节点执行 |

所以，**Worker 更像“岗位名称”，Cloudflare Workers 是“产品名称”**。听到前者，要先问它在哪里运行、由谁触发；听到后者，才知道说的是 Cloudflare 这套平台。

本文只讨论 Cloudflare Workers。

## 二、它解决的不是“没有服务器”，而是“离用户太远”

先看一个传统 Web 请求的路径：

```text
用户
  │
  ▼
DNS 解析
  │
  ▼
中心机房的应用服务器
  │
  ▼
数据库
  │
  ▼
逐层返回
```

这里每一段都可能产生网络往返。用户在欧洲，服务器在美国，一次请求就要跨大西洋；如果一次页面加载要调用五六个接口，延迟会不断累加。

传统做法通常有三类：

- **把服务器放在一个中心机房**：架构简单，但离得远的用户慢。
- **用 CDN 缓存静态文件**：图片、CSS、JS 可以就近拿到，但动态逻辑还是要回源。
- **用普通 Serverless**：不用管服务器了，但函数通常仍部署在某个区域，离用户还是可能很远。

Cloudflare Workers 的思路是：**把“处理请求的一小段代码”也放到边缘节点**。用户请求先到离他较近的 Cloudflare 节点，代码在那里执行，必要时再访问中心数据库或源站。

这里的“边缘”（edge）指的是**离用户较近的网络节点**，不是用户的手机或电脑。Cloudflare 在全球有大量机房节点，通常称为 PoP（Point of Presence，接入点）。用户不需要手动选机房，网络路由会把他带到较近的节点。

但边缘不是魔法。它能缩短“用户到代码”的距离，不能自动缩短“代码到数据库”的距离。如果每个请求都要回中心数据库查一次，边缘省下的只是第一段网络延迟。

## 三、请求进来后发生了什么

可以把一次请求拆成下面这条链路：

```text
用户
  │
  ▼
最近的 Cloudflare 节点（PoP）
  │  路由匹配：这个 URL 归哪个 Worker 管？
  ▼
Worker 运行时（V8 isolate）
  │  执行 fetch(request, env, ctx)
  ├─ 读取绑定资源：KV / R2 / D1 / Queues ...
  ├─ 调用上游 API 或源站
  ▼
返回响应（可写入缓存）
```

几个关键词需要解释。

### 1. Anycast：同一个地址，被带到较近的节点

Cloudflare 使用 Anycast（任播）技术：同一个 IP 地址在全球多个节点同时宣告，网络路由会把用户带到相对较近的那个节点。用户不需要知道机房在哪里，也不需要改 DNS 指向。

### 2. Route：什么样的请求交给哪个 Worker

一个 Worker 可以绑定到一个域名、一个路径或一组规则。例如：

- `example.com/api/*` 交给 API Worker；
- `example.com/admin/*` 交给鉴权 Worker；
- 某个自定义域名整体交给一个 Worker。

路由匹配决定了“哪些请求会进入你的代码”，也决定了哪些请求继续走普通源站。

### 3. V8 isolate：轻量的 JavaScript 运行时

V8 是 Chrome 使用的 JavaScript 引擎。**isolate（隔离运行时）** 是 V8 里的一个轻量执行环境。很多 isolate 可以共享同一个进程，启动成本比虚拟机或容器低。

这也是 Cloudflare Workers 和传统服务器的一个重要区别：

- 不是每个请求开一台虚拟机；
- 不是维护一个常驻的 Node.js 进程；
- 而是把代码放进一个受限制的运行时里，请求来了就执行。

“轻量”不等于“没有冷启动”。代码初始化、加载依赖、建立连接仍然需要时间，只是通常比启动一个完整容器轻。

### 4. Handler：代码的入口函数

一个最小的 Worker 会导出一个 `fetch` 处理函数。请求进来时，平台调用它，把你的 `Response` 返回给用户。后面会给出代码例子。

### 5. Binding：把外部资源挂到 Worker 上

Worker 不能假设自己能访问任意文件系统或任意数据库。它通过 **Binding（绑定）** 访问平台提供的资源，例如 KV、R2、D1、Queues。绑定在配置文件里声明，代码通过 `env` 读取。

这带来两个好处：权限边界更清楚，密钥不需要写死在代码里。代价是代码和平台绑定得更紧，迁移时不能直接搬走。

### 6. Response：直接返回，或转发给源站

Worker 可以直接生成响应，也可以把请求转发给源站，再加工源站返回的内容。它还可以配合 Cache API 控制缓存，但 Worker 本身不等于缓存：**它是一段可执行的请求处理逻辑**。

这里有一个容易忽略的事实：**Worker 通常是无状态的**。同一个用户的两次请求可能落在不同的 isolate 上，内存里的变量不能当作可靠存储。需要状态时，要用 KV、D1、Durable Objects 等外部能力。

## 四、和几个容易混淆的方案对比

| 方案 | 代码运行位置 | 运行单位 | 启动特点 | 状态 | 典型用途 |
|---|---|---|---|---|---|
| 传统服务器 | 固定机房 | 常驻进程 | 启动较慢，之后常驻 | 可以保存在内存和磁盘 | 完整 Web 后端 |
| 容器 | 机房或云平台 | 容器 | 秒级到分钟级 | 可以保存在容器内 | 微服务、可移植部署 |
| 普通 Serverless | 云厂商的某个区域 | 函数实例 | 可能有冷启动 | 通常无状态 | 事件处理、定时任务 |
| CDN | 边缘节点 | 缓存规则 | 无需启动业务代码 | 只缓存内容 | 静态资源加速 |
| Cloudflare Workers | 全球边缘节点 | V8 isolate | 轻量、通常较快 | 通常无状态 | 边缘鉴权、路由、轻量 API |

三个常见误解需要提前澄清：

- **Serverless 不是“没有服务器”**：服务器仍然存在，只是平台替你管理，你按请求或资源付费。
- **边缘计算不是“一定更快”**：如果逻辑很重，或者每次都要访问中心数据库，边缘带来的收益会被抵消。
- **Cloudflare Workers 不是完整 Node.js**：它支持 JavaScript/TypeScript、WebAssembly 和一部分 Node.js 兼容 API，但不是所有 npm 包都能直接运行。

## 五、一个最小例子

下面这段代码会在 `/api/hello` 返回一个 JSON：

```js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);

    if (url.pathname === "/api/hello") {
      return Response.json({
        message: "Hello from the edge",
        colo: request.cf?.colo ?? "unknown"
      });
    }

    return new Response("Not Found", { status: 404 });
  }
};
```

三个参数分别是：

- `request`：进来的请求，包含 URL、方法、请求头和请求体。
- `env`：绑定资源，例如 `env.MY_KV`、`env.MY_DB`。
- `ctx`：请求生命周期工具，例如用 `ctx.waitUntil()` 在返回响应后继续做一些收尾工作。

`request.cf.colo` 是处理这次请求的 Cloudflare 节点代码，例如 `HKG`、`SIN`，调试时可以用它确认请求落在哪个机房。

一个对应的 `wrangler.toml` 可能长这样：

```toml
name = "hello-worker"
main = "src/index.js"
compatibility_date = "2025-01-01"
```

`compatibility_date` 不是版本号，而是用来固定运行时行为的日期。它会影响某些 API 的默认行为，实际项目应以初始化模板生成的日期为准，不要随意改动。

本地开发和部署通常用 `wrangler`（Cloudflare 的命令行工具）：

```bash
npm create cloudflare@latest hello-worker
cd hello-worker
npx wrangler dev
npx wrangler deploy
```

- `wrangler dev` 在本地模拟 Worker 运行环境；
- `wrangler deploy` 把代码发布到 Cloudflare 网络。

本地能跑通，不代表生产一定正确。本地模拟不覆盖真实网络、缓存、权限和存储行为，后面会专门讲验证。

## 六、Worker 只是“前台”，后面还有一排柜子

Cloudflare Workers 不只是一个孤立的函数。它周围有一组配套服务，通常通过 Binding 挂到 Worker 上：

| 能力 | 一句话解释 | 适合什么 | 要注意什么 |
|---|---|---|---|
| Workers KV | 全球分布的键值存储 | 配置、功能开关、缓存元数据 | 最终一致，写入不是立刻全球可见 |
| R2 | 兼容 S3 的对象存储 | 图片、备份、日志、静态文件 | 不是数据库，不适合频繁改小文件 |
| D1 | 基于 SQLite 的 SQL 数据库 | 轻量关系型数据、原型、小规模业务 | 不是 MySQL/PostgreSQL 的完全替代品 |
| Queues | 异步消息队列 | 解耦、削峰、失败重试 | 通常是“至少一次”投递，消费者要幂等 |
| Durable Objects | 有状态、可协调的对象 | 聊天室、计数器、锁、协作状态 | 不是通用数据库，设计要围绕“单个对象” |
| Cron Triggers | 定时触发 | 定时清理、报表、同步任务 | 使用 UTC，任务要短小 |
| Hyperdrive | 加速访问区域数据库 | 让 Worker 更高效地连接传统数据库 | 它加速连接，不替代数据库 |
| Workers AI | 在 Cloudflare 网络上调用模型推理 | 轻量分类、摘要、向量化 | 模型能力、成本和限制要单独评估 |
| Service Bindings | Worker 之间内部调用 | 拆分多个 Worker、内部服务调用 | 需要有清晰的服务边界 |

“绑定”可以理解成：**平台把某个资源以配置的方式接到你的 Worker 上，代码通过 `env` 使用它**。这比把数据库密码写进代码更安全，但也意味着资源类型和平台能力会影响架构设计。

几个产品经理需要知道的边界：

- **KV 是最终一致**：写入后，不同节点可能短暂看到旧值。它适合配置和缓存，不适合库存扣减、账户余额。
- **D1 是 SQLite**：适合轻量关系型数据，但不要把 MySQL/PostgreSQL 的复杂事务和运维经验直接套过来。
- **Queues 可能重复投递**：消费者要能处理“同一条消息执行两次”的情况，这叫幂等。
- **Durable Objects 不是万能数据库**：它擅长“某一个对象的强一致协调”，不擅长替代大规模关系查询。

另外，Cloudflare Pages 的 Functions 本质上也是构建在 Workers 之上的。如果项目是静态站点加少量接口，Pages 可能比单独管理 Worker 更顺手。

## 七、什么场景适合用

Cloudflare Workers 最适合“**短小、事件驱动、离用户近**”的逻辑。常见场景包括：

| 场景 | Worker 做什么 | 收益 | 注意事项 |
|---|---|---|---|
| 边缘鉴权 | 校验 Token、拦截未授权请求、补充租户信息 | 无效请求不必回源 | 密钥轮换、时钟偏差、日志要设计 |
| API 网关 / BFF | 聚合接口、改请求头、做协议转换 | 减少客户端往返 | 不要把重业务全塞进边缘 |
| A/B 测试 | 按用户、地区、比例分流 | 就近决策，延迟低 | 分流规则要可解释、可回滚 |
| 重定向与 SEO | 域名跳转、规范化 URL、响应头 | 统一入口，减少源站压力 | 避免缓存错误的重定向 |
| Webhook 入口 | 验签、去重、入队 | 快速返回，异步处理 | 验签失败要拒绝，不能只记日志 |
| 轻量内容加工 | 改 HTML、压缩、图片简单处理 | 就近返回定制内容 | 大文件和大计算不适合 |
| 多区域读接口 | 在边缘返回缓存或轻量数据 | 降低跨区延迟 | 数据新鲜度和一致性要说明 |
| SaaS 自定义域名 | 按域名识别租户、路由到对应服务 | 统一接入体验 | 证书、域名验证、租户隔离要验证 |

举一个具体例子。假设你有一个跨境 SaaS，用户分布在欧洲、东南亚和北美。登录后，客户端每次请求都带一个 Token。可以在边缘做三件事：

1. 校验 Token 是否有效、是否过期；
2. 从 Token 中取出租户 ID，补到请求头里；
3. 根据租户所在区域，把请求转发到合适的后端。

无效请求在边缘就被拒绝，不用占用中心服务器；有效请求也只多经过一小段边缘逻辑。这个方案的关键不在“代码写得多聪明”，而在于**鉴权规则、密钥轮换、失败回退和日志是否可靠**。

## 八、什么场景不适合用

Cloudflare Workers 有明确的运行时限制，不是所有后端都适合搬上去：

| 看起来适合 | 为什么通常不适合 |
|---|---|
| 视频转码、批量图片处理 | CPU 时间和请求时长有限，重计算应该交给专门服务 |
| 完整 Node.js 单体应用 | 运行时不是完整 Node.js，原生依赖和本地文件系统可能不可用 |
| 高频事务数据库 | 连接方式、事务边界和一致性要求与边缘函数不匹配 |
| 大文件上传和长期存储 | 请求体大小、流式处理和本地磁盘都有约束，通常应直接用对象存储 |
| 长时间后台任务 | Worker 适合短任务；长任务应拆成队列加消费者，或使用专门的计算服务 |
| 依赖本地磁盘的程序 | 没有可依赖的持久本地文件系统 |
| 强数据驻留合规业务 | 全球边缘执行不等于数据一定留在某个国家或地区，要单独确认合规 |
| 复杂单体后台 | 拆成边缘函数会让边界更碎，维护成本可能更高 |

一个简单的判断句：**如果这段逻辑需要跑很久、吃很多 CPU、依赖完整操作系统，或者必须和中心数据库做复杂事务，就不适合直接放进普通 Worker。**

## 九、成本和限制：免费不等于零成本

Cloudflare Workers 的计费通常围绕两类资源：**请求数**和**CPU 时间**。免费额度适合开发和轻量验证，但生产环境要按峰值请求、CPU 消耗和配套资源一起估算。具体配额和价格会调整，上线前必须查官方最新文档。

需要区分两个时间概念：

- **CPU 时间**：代码真正消耗处理器的时间；
- **墙上时钟时间**：从请求开始到响应结束的真实耗时，包含等待网络、等待数据库等。

Worker 可能在等待 I/O 时不消耗多少 CPU，但仍然有请求时长限制。所以“CPU 没超”不等于“请求可以无限等待”。

除了 Worker 本身，还要算这些成本：

- KV 的读写次数；
- D1 的行读写和存储；
- R2 的存储和操作次数；
- Queues 的消息数量；
- 日志、指标和追踪的保留与采样；
- 访问源站、第三方 API 和其他云服务的流量。

R2 的一个常见卖点是**不收出口流量费**，但这不等于所有 Cloudflare 服务都免费，也不等于没有存储和操作成本。

还要注意三类“非价格成本”：

1. **平台锁定**：代码依赖 Workers 运行时、Binding 和 Durable Objects 后，迁移不是改一个配置就能完成。
2. **可观测性**：日志是否全量、保留多久、能否按请求追踪，都会影响排障。不要假设默认日志足够。
3. **本地与生产差异**：本地模拟能验证基本逻辑，但真实网络、缓存、权限、证书和存储行为仍要在预发布环境验证。

## 十、上线前怎么验证

Cloudflare Workers 很容易“看起来能用”：返回一个 Hello World，延迟很低，部署很快。但真正要验证的是：**在真实流量、真实故障和真实权限下，它是否仍然正确。**

可以用下面这张表做入门验收：

| 检查项 | 怎么测 | 通过标准 |
|---|---|---|
| 功能正确 | 覆盖正常请求、边界参数、错误方法 | 状态码、响应头、响应体都符合约定 |
| 地域延迟 | 从主要用户地区测 p50/p95 | 比原方案有可解释的改善，且没有明显长尾 |
| 缓存行为 | 测命中、未命中、过期、清除 | 不会把个性化内容错误缓存给其他用户 |
| 鉴权 | 测无效、过期、伪造、无权限 Token | 该拒绝的请求在边缘被拒绝，且不泄露信息 |
| 依赖故障 | 模拟 KV、D1、R2、上游 API 超时 | 有明确降级或错误响应，不会静默成功 |
| 限流 | 做突发流量和单租户高频测试 | 超限返回明确错误，不拖垮源站 |
| 日志与追踪 | 随机抽一条错误请求 | 能还原请求 ID、节点、耗时、依赖调用和错误原因 |
| 回滚 | 发布一个坏版本再回滚 | 能在可接受时间内恢复，旧版本可重新上线 |
| 成本 | 按峰值请求和 CPU 消耗估算 | 在预算内，且知道最坏情况会花多少 |
| 安全 | 检查密钥、CORS、SSRF、注入、PII | 密钥不进入代码和日志，外部输入不被直接信任 |
| 合规 | 确认数据经过哪些地区、保留多久 | 满足业务所在地区的要求 |

建议的验证顺序是：**先功能，再故障，再性能，最后成本和合规**。不要一开始就压测，因为功能错了，性能数字没有意义。

一个实用的上线方式是灰度：先让 5% 的流量经过 Worker，对比错误率、p95 延迟和源站负载；确认稳定后再扩大。不要一次性把全部流量切过去。

## 十一、产品经理怎么判断“该不该用”

可以用下面这组问题做初筛：

| 问题 | 如果是 | 如果否 |
|---|---|---|
| 用户是否分布在全球，且延迟敏感？ | 边缘执行可能有明显收益 | 先别为了“边缘”而上边缘 |
| 逻辑是否短小、事件驱动？ | 适合 Worker | 重计算、长任务要换方案 |
| 是否已经在用 Cloudflare？ | 集成成本较低 | 要评估新增供应商和运维成本 |
| 能否接受运行时和平台限制？ | 可以进入方案设计 | 不要假设“以后都能兼容” |
| 是否有明确指标，例如 p95、源站流量、转化率？ | 可以做可验证的试点 | 先定义指标，否则无法判断收益 |
| 团队是否能维护日志、回滚、安全和配额？ | 可以上线 | 先补运维能力，再谈上线 |

最小可行方案不需要一上来重构整个后端。可以按这个顺序做：

1. 选一个边界清晰的场景，例如“登录鉴权”或“统一重定向”；
2. 记录现状基线：p50/p95 延迟、错误率、源站请求量；
3. 只把这一小段逻辑放到 Worker；
4. 灰度 5% 流量，观察至少一个完整业务周期；
5. 用数据决定扩大、保留还是回滚。

如果试点只证明了“能返回 Hello World”，那还不算完成。真正有价值的结果是：**延迟改善多少、源站少扛多少请求、故障时是否可控、每月多花多少钱。**

## 十二、常见误区

- **“Cloudflare Workers 是免费 CDN”**：CDN 主要缓存内容，Workers 执行代码；免费额度也不是无限量。
- **“可以把整个后端搬上去”**：它适合边缘的短逻辑，不适合完整单体、重计算和复杂事务。
- **“边缘一定比中心快”**：如果每次都要回中心数据库，边缘只省了第一段网络。
- **“无状态所以更简单”**：无状态意味着你不能依赖内存，必须显式设计存储、一致性和并发。
- **“代码全球部署，数据也全球”**：代码的执行位置和数据存储位置是两件事，合规要分别确认。
- **“本地能跑，生产就没问题”**：本地模拟不覆盖真实网络、缓存、证书、权限和存储行为。
- **“Workers 就是 Node.js”**：只兼容一部分 Node.js API，很多包和原生依赖不能直接用。
- **“用了 Serverless 就不用运维”**：仍然要管配置、日志、告警、回滚、安全和成本。
- **“Durable Objects 可以替代数据库”**：它解决的是单个对象的状态协调，不是通用查询和报表。

## 十三、术语速查

| 术语 | 一句话解释 |
|---|---|
| Edge（边缘） | 离用户较近的网络节点，不等于用户设备 |
| PoP | Point of Presence，Cloudflare 的接入机房 |
| Anycast | 同一个地址在全球多处宣告，让用户被路由到较近节点 |
| Isolate | V8 里的轻量隔离运行时，启动成本低于虚拟机 |
| Binding | 把 KV、R2、D1 等资源以配置方式接到 Worker 上 |
| Cold start | 代码第一次执行或长时间未执行后的初始化成本 |
| Origin（源站） | Worker 后面的原始服务器或后端服务 |
| Serverless | 平台管理服务器，开发者按请求或资源付费 |
| CDN | 内容分发网络，主要把静态内容缓存到离用户近的节点 |
| Idempotent（幂等） | 同一个操作执行多次，结果与执行一次相同 |

## 最小掌握标准

做到下面五条，就足够在日常协作和方案判断中不被名词带偏：

1. 能说出 Cloudflare Workers 的本质：部署在边缘的请求处理函数。
2. 能区分 Worker、CDN、普通 Serverless 和传统服务器的差别。
3. 知道它适合短小、事件驱动、低延迟的逻辑，不适合重计算和复杂事务。
4. 知道“无状态”“最终一致”“至少一次投递”分别意味着什么风险。
5. 能用延迟、错误率、源站流量和成本四项指标验证是否值得用。

下面这些可以暂缓，不影响日常判断：

- V8 isolate 的底层实现和调度细节；
- Durable Objects 的完整一致性设计；
- Workers 所有绑定服务的 API；
- 具体框架的迁移和构建配置。

## 一句话记忆

> **Worker 是岗位名，Workers 是产品名；Cloudflare Workers 的本质，是把“处理请求的一小段代码”放到全球边缘，让用户就近得到响应。**
