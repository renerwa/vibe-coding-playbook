# 多 Agent 使用指南

> 用途：说明 Codex 中主 Agent、子 Agent、普通对话和多 Agent 协作的使用方式，并提供可直接套用的任务模板、配置示例和验收清单。
> 状态：v0.1.1，先用真实小任务试运行，再根据成本和效果调整。
> 最后更新：2026-11-08
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[什么是 Agent](07-什么是Agent.md)、[多 Agent 协作理解与实操](05-多Agent协作理解与实操.md)。
> 不覆盖：外部 Agent 框架的实现细节、复杂企业级调度、并行写入的完整 Git 工程方案。
> 文档定位：本文偏“怎么做”和“什么时候做”；概念辨析和完整 FAQ 见 05 号文档。
> 阅读顺序：本文按“为什么需要 → 是什么 → 何时用 → 怎么触发 → 怎么做 → 怎么配置 → 怎么实践和验收”组织，而不是按提问顺序展开。

## 先从一个场景说起

用 AI 做一个中等规模的功能时，主对话里往往要同时处理很多事情：读现有代码、查接口、跑测试、看日志、写实现、做验收。每件事都留在同一个上下文里，主线程会越来越长，最早确认的需求容易被后面的报错和命令输出淹没。

这种情况可以称为**上下文污染**：有用的信息被大量中间过程盖住了。继续发展还会出现**上下文退化**：对话越长，模型越难抓住真正重要的目标、约束和决策。多 Agent 要解决的，首先就是这个问题。

主 Agent 可以把相对独立的调查、测试和审查交给临时子 Agent，让它们在各自的 Agent 线程里处理噪声；主 Agent 只保留目标、约束、关键决策和最终整合。它不是“让更多 Agent 一起开会”，而是一种分工和上下文隔离机制。

本文要回答四个问题：主 Agent 和子 Agent 分别是什么；什么时候值得拆；怎么正确触发和配置；以及怎样避免多 Agent 常见的失控。

## 一句话结论

> **主 Agent 是当前主线程的负责人；子 Agent 是它为局部任务临时启动的独立执行者。多 Agent 的正确用法不是自动组队，而是：按需委派、并行调查、单点决策、单点写入、独立验收。**

多 Agent 的价值不在于“Agent 越多越好”，而在于把噪声较大的调查、测试、日志分析和独立审查移出主线程，让主 Agent 继续掌握需求、约束和最终决策。

## 核心概念

| 概念 | 是什么 | 不是什么 |
|---|---|---|
| 主 Agent | 当前主对话线程里的总负责人，负责目标、拆分、决策、整合和最终答复 | 不是特殊模型，也不是必须手动创建的岗位 |
| 子 Agent | 主 Agent 为某个局部任务启动的独立执行者，有自己的 Agent 线程 | 不是新开的普通对话，也不会自动共享主对话记忆 |
| Agent 线程 | 子 Agent 读文件、运行命令、形成结论的独立上下文 | 不是另一个主对话，也不是长期在线的团队成员 |
| 自定义 Agent | `.codex/agents/*.toml` 中的角色配置，描述这个角色能做什么、应该怎么做 | 不是正在运行的 Agent，更不是自动派活规则 |

补充说明：

- **Agent 实例**：某个角色被实际创建出来的一次具体执行。同一个模板可以创建多个实例。
- **调度规则**：规定什么情况下使用哪个 Agent。它和角色模板是两件事。
- **普通新对话**：会创建另一个主 Agent，和原对话平级，不会自动把结果交回原对话。

### 多个普通对话意味着什么

同一个项目下打开多个普通对话，可以理解为：

> **多个独立的“主线程 / 主 Agent 会话实例”。它们上下文独立、地位平级、不会自动协作，但共享同一个项目工作区。**

也就是说：

- 对话层面互不关联；
- 项目层面并非完全隔离。

| 项目 | 是否共享 |
|---|---|
| 对话历史、记忆、推理上下文 | 不共享 |
| 任务目标、中间结论 | 不共享，除非人工转述 |
| 各自的子 Agent 层级 | 不共享 |
| 项目文件、Git 工作区 | 共享 |
| `AGENTS.md`、项目配置、Skills、MCP（Model Context Protocol，Agent 接入外部工具的协议） | 通常共享 |
| 本机端口、开发服务器、数据库环境 | 共享，可能互相影响 |
| 最终结果 | 不会自动合并，需要人工或主 Agent 整合 |

多个普通对话适合处理不相关任务，例如一个对话整理文档、另一个对话改代码。它们不适合在没有隔离的情况下同时修改同一个功能。并发写入时，至少需要独立文件范围；更稳妥的是使用独立分支或 worktree（同一 Git 仓库的独立工作目录），并由人负责最终整合。

## 什么时候值得拆

| 场景 | 建议 |
|---|---|
| 改一个文件、小文案、小 bug | 主 Agent 直接做 |
| 接手陌生代码库 | 先派两个只读调查 Agent |
| PR（Pull Request，代码合并请求）审查 | 可按安全、测试缺口、可维护性拆分，最后统一汇总 |
| 前后端功能 | 先并行调查，再冻结接口，最后单点实现 |
| 多个页面目录互不重叠 | 可以考虑多个前端实例，但需要明确文件边界 |
| 多个 Agent 必须改同一文件 | 改成一个写入者 |
| 没有测试或验收标准 | 先补验收，不要急着并行 |
| 强依赖任务 | 顺序执行，或分阶段执行 |
| 纯视觉、主观体验 | 以人工评审为主，不为“好不好看”强行拆 Agent |

判断标准可以压缩成一句话：**任务之间是否真的独立、并行收益是否明显、结果是否容易核对。** 三个问题里有一个回答不了，就先不要拆。

## 怎么触发子 Agent

### 能力开启不等于自动组队

本地 Codex 当前默认启用子 Agent 工作流，但这只表示工具能力可用，不代表每个复杂任务都会自动拆给多个 Agent。

更准确的理解是：

1. **能力层**：`agents.enabled` 默认开启，子 Agent 工具可用，App 和 CLI 能显示 Agent 线程。
2. **角色层**：内置 `default`、`worker`、`explorer` 等角色可用；也可以配置自定义 Agent。
3. **调度层**：主 Agent 根据任务和你给出的指令，决定是否创建子 Agent、创建几个、如何等待和汇总。

默认策略不是“任务复杂就自动组队”，而是：

> 只有你明确要求委派，或者适用的 `AGENTS.md`、Skill 明确要求委派时，主 Agent 才会启动子 Agent。

### 什么算明确要求

| 你的说法 | 是否构成委派意图 | 说明 |
|---|---|---|
| “帮我详细分析这个项目” | 通常不算 | 主 Agent 可以自己分析 |
| “深入研究一下这个问题” | 通常不算 | 研究深度不等于多 Agent 授权 |
| “请派两个子 Agent，分别调查前端和后端” | 算 | 有明确的 Agent 数量和分工 |
| “用并行 Agent 检查安全、测试和可维护性” | 算 | 有明确的并行和任务边界 |
| “按这个任务包拆成三个独立调查” | 算 | 说明了拆分方式和独立任务 |
| “新建一个普通对话做这件事” | 不算 | 新对话是另一个主 Agent，不是子 Agent |

因此，像“详细解释一下”这样的请求，不等于授权开多个子 Agent。对于概念解释、单文件修改和小 bug，主 Agent 直接完成通常更合适。

### 为什么不做成默认自动组队

- **成本更高**：每个子 Agent 都独立调用模型和工具，会消耗更多 token（模型处理和计费的基本单位）。
- **协调成本更高**：主 Agent 要拆分任务、传递背景、等待结果、处理冲突并统一汇总。
- **写入容易冲突**：多个 Agent 同时修改同一批文件，容易出现覆盖、接口漂移和重复劳动。
- **上下文不共享**：子 Agent 不知道主对话和其他子 Agent 的全部历史，主 Agent 必须额外打包背景。
- **小任务反而更慢**：拆分和汇总的时间可能超过直接完成的时间。

## 三种使用方式

| 方式 | 是否需要预定义 | 触发方式 | 适合场景 |
|---|---|---|---|
| 临时子 Agent | 不需要 | 在主对话里明确要求分派 | 一次性调查、排查、审查 |
| 项目调度规则 | 需要写规则 | `AGENTS.md` 或 Skill 要求委派 | 项目内反复出现的任务类型 |
| 自定义 Agent | 需要写 TOML（一种文本配置格式） | 通过名称、任务要求或调度规则使用 | 固定角色、固定模型、固定能力边界 |

### 方式一：临时子 Agent

不需要提前打开窗口，也不需要先写配置文件。你只需要在主对话里说明分工。

```text
请用子 Agent 并行调查这个功能，先不要修改代码：

- Agent A：只读调查后端路由、业务逻辑、数据库和测试；
- Agent B：只读调查前端页面、请求封装、状态管理和测试；
- Agent C：只读检查权限、异常路径和关键风险。

要求每个 Agent 返回：事实、文件路径、调用链、风险、验证命令、未确认项。
等三个都完成后，你先汇总冲突和缺口，再给我下一步方案。
```

这里的 `Agent A / B / C` 是任务标签，不是正式的 Agent 名称。主 Agent 会把它们理解为三个工作包，可能映射到内置角色，也可能根据任务调整拆分方式。

临时子 Agent 的优点是快；缺点是角色、模型和能力边界不稳定。如果某类任务会反复出现，再考虑把它固化成自定义 Agent。

### 方式二：写进 AGENTS.md

如果希望某类任务经常自动触发委派，可以在项目根目录的 `AGENTS.md` 中加入调度规则：

```markdown
## 子 Agent 调度规则

1. 单文件、小文案和小 bug：主 Agent 直接处理。
2. 陌生代码库或跨前后端任务：先派两个只读调查 Agent。
3. 实现阶段默认只有主 Agent 一个写入者。
4. 只有接口已冻结、文件完全不重叠时，才允许并行写入。
5. 功能完成后，派独立验收 Agent 检查测试和关键失败路径。
```

这类规则能显著提高自动委派的概率，但它仍然是模型遵循的指令，不是确定性的 `if/else` 调度器。不要把“写了规则”理解成“每次都一定执行”。

### 方式三：定义自定义 Agent

当角色需要长期复用，或者需要固定模型、推理强度、能力边界时，再把它写成 TOML。

个人级路径：`~/.codex/agents/`

项目级路径：项目根目录下的 `.codex/agents/`

一个文件只定义一个 Agent。三个必填字段是：

```toml
name = "readonly_explorer"
description = "只读调查代码，适合实现前摸底。"
developer_instructions = """
不要修改文件。
只返回事实、文件路径、调用链、风险和验证命令。
找不到证据时写“未确认”，不要猜测。
"""
```

其中：

- `name`：Codex 用来识别和调用这个 Agent 的名称；
- `description`：说明什么时候应该使用它；
- `developer_instructions`：定义它的核心行为和边界。

文件名最好与 `name` 一致，但官方以 `name` 字段为准。不要随便使用 `default`、`worker`、`explorer` 等内置名称，否则可能覆盖内置角色。

## 推荐工作流

最稳的多 Agent 形态不是“一群 Agent 开会”，而是“流水线 + 独立检查”：

```text
主 Agent 写任务包
       ↓
两个只读调查 Agent 并行工作
       ↓
主 Agent 汇总并冻结接口/文件边界
       ↓
一个实现者写代码
       ↓
独立验收 Agent 检查
       ↓
人工做业务验收
```

| 步骤 | 主 Agent 做什么 | 主要产出 |
|---|---|---|
| 1. 写任务包 | 明确目标、非目标、范围、验收标准和输出格式 | 任务说明 |
| 2. 只读调查 | 派子 Agent 分别查不同问题 | 代码地图、风险清单 |
| 3. 冻结契约 | 汇总调查结果，确定 API、数据结构、文件所有权 | 接口契约和边界 |
| 4. 单点实现 | 默认由主 Agent 或一个实现 Agent 写代码 | 可审查的代码改动 |
| 5. 独立验收 | 让另一个 Agent 按验收标准运行测试、检查失败路径 | 验收报告 |
| 6. 人工验收 | 你确认真实业务场景是否可用 | 业务验收结论 |

### 第 1 步：写任务包

不要只给一句“帮我做一下”。至少写清楚：

```text
目标：
非目标：
输入和背景：
允许修改的目录：
验收标准：
测试命令：
输出格式：
停止条件：
```

任务包的作用是让子 Agent 知道边界，也让主 Agent 后续能判断“有没有越界”。

### 第 2 步：先做只读调查

调查任务应尽量独立，例如：

- 后端路由、业务逻辑、数据库和测试；
- 前端页面、请求封装、状态管理和测试；
- 权限、异常路径、日志和失败恢复。

调查 Agent 应返回证据，而不是只给结论。没有证据的地方要明确写“未确认”。

### 第 3 步：冻结契约和文件边界

主 Agent 汇总调查结果后，确定：

- API 路径、请求参数、响应结构、错误码和权限；
- 数据库或数据结构变化；
- 哪些文件由哪个 Agent 负责；
- 共享文件由谁修改；
- 验收用例和测试命令。

没有冻结接口，不要让前端和后端并行写代码。

### 第 4 步：实现阶段保持一个写入者

初期建议：

- 主 Agent 自己写；
- 或只派一个实现 Agent；
- 每完成一个模块就运行对应测试；
- 发现契约问题先停下，不自行改接口。

只有接口稳定、文件完全不重叠、你熟悉 Git 分支或独立工作目录时，再尝试并行写入。否则“多 Agent”很容易变成“多个人同时改同一张表”。

### 第 5 步：独立验收

验收 Agent 应：

- 依据冻结的验收标准检查；
- 运行明确列出的测试或验证命令；
- 检查失败路径、边界条件和权限；
- 报告文件位置、复现方式、影响和建议；
- 不修改业务代码来让测试通过。

验收报告不是一句“已完成”，而是可供你判断的证据。

### 第 6 步：人工做业务验收

技术测试通过不等于业务验收通过。你仍然要确认：

- 用户是否真的能完成目标；
- 错误提示是否可理解；
- 权限和业务规则是否符合预期；
- 是否存在“技术上通过、产品上不可用”的情况。

## 子 Agent 输出契约

给子 Agent 一个固定的输出格式，能显著降低汇总成本：

```text
结论：
事实与证据：
文件路径：
调用链：
风险：
验证命令与结果：
未确认项：
建议下一步：
```

要求：

- 事实和推测分开写；
- 文件路径要能定位；
- 测试命令要能复现；
- 找不到证据就写“未确认”；
- 不要只返回“已完成”或“应该没问题”。

## 自定义 Agent 的常用配置

除了三个必填字段，比较常用的配置分为四类。

### 模型行为

| 字段 | 作用 | 使用建议 |
|---|---|---|
| `model` | 指定模型 | 不填则继承主 Agent；填写时使用当前账号可用的模型 |
| `model_reasoning_effort` | 推理强度 | 常用 `low`、`medium`、`high`，支持级别取决于模型 |
| `model_verbosity` | 输出详细程度 | 控制回答啰嗦程度，按需使用 |
| `model_reasoning_summary` | 推理摘要详细程度 | 偏调优项，初期可以先不用 |

如果自定义 Agent 文件显式设置了 `model` 或 `model_reasoning_effort`，该值优先；否则按显式 spawn 参数、`[agents]` 默认值、父会话设置的顺序继承。

### 能力开关

| 字段 | 作用 |
|---|---|
| `features.shell_tool` | 是否允许执行命令行工具 |
| `features.apps` | 是否允许使用 Apps 或连接器 |
| `features.plugins` | 是否允许使用插件 |
| `features.memories` | 是否允许使用记忆能力 |
| `features.request_permissions_tool` | 是否允许主动申请额外权限 |

调查和审查 Agent 通常需要保留 `shell_tool`，因为要搜索代码或运行测试。不要为了“安全”把工具全部关掉，否则 Agent 可能连基本证据都拿不到。

### Skills 开关

可以按路径禁用某个 Skill：

```toml
[[skills.config]]
path = "C:/Users/madgu/.agents/skills/your-skill/SKILL.md"
enabled = false
```

还可以使用：

- `skills.bundled.enabled = false`：关闭内置技能；
- `skills.include_instructions = false`：不自动注入技能说明。

这些属于进阶配置，初期通常不用管。

### 全局多 Agent 设置

这些字段放在 `config.toml` 的 `[agents]` 下，不是放在单个 Agent 文件里：

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 4
default_subagent_model = "gpt-6-luna"
default_subagent_reasoning_effort = "high"
```

| 字段 | 作用 |
|---|---|
| `agents.enabled` | 是否启用多 Agent 工具 |
| `agents.max_concurrent_threads_per_session` | 一个会话最多同时打开多少个子 Agent 线程 |
| `agents.default_subagent_model` | 子 Agent 的默认模型 |
| `agents.default_subagent_reasoning_effort` | 子 Agent 的默认推理强度 |

### 一个增强版示例

```toml
name = "code_reviewer"
description = "只读审查代码的正确性、安全性和测试缺口。"
model = "gpt-6.1-sol"
model_reasoning_effort = "high"

developer_instructions = """
不要修改文件。
优先报告真实缺陷，给出文件路径、复现方式和验证命令。
找不到证据时写“未确认”，不要猜测。
"""

features.shell_tool = true
features.apps = false
features.plugins = false
features.memories = false
features.request_permissions_tool = false
```

### 不要写在这些文件里的字段

下面这些通常属于主会话或全局配置，单个 Agent 文件不能覆盖：

- `sandbox_mode`
- `approval_policy`
- `model_provider`
- `mcp_servers`

子 Agent 会继承主会话的权限、Provider（模型服务提供方）和 MCP 配置。提示词里写“只读”只是行为约束，不等于系统级只读沙箱。

## 最佳实践

1. **先判断是否值得拆**：单文件、小文案、小 bug，主 Agent 直接做。
2. **主 Agent 保留关键路径**：需求解释、关键决策、冲突裁决和最终整合必须由主 Agent 负责。
3. **任务包而不是一句话**：写清目标、非目标、范围、验收标准、测试命令和停止条件。
4. **优先读多写少**：调查、测试、日志分析、PR 审查和总结适合并行；同时写业务代码要谨慎。
5. **契约先行**：先冻结 API、数据结构、错误码和文件所有权，再并行实现。
6. **单一写入者**：同一个共享文件只能有一个负责人；并行写入必须有隔离和合并方案。
7. **独立验收**：实现者不要同时担任最终验收者，验收 Agent 不应修改代码来让测试通过。
8. **证据优先**：要求文件路径、调用链、测试命令和实际结果，不接受只有“完成”的结论。
9. **控制数量**：初期 2～3 个子 Agent 通常足够；不要为了并行而并行。
10. **保留人工验收**：技术测试通过不等于业务可用，最终业务判断仍由人完成。

## 常见误区

- 把“新建一个对话框”当成子 Agent；它其实是另一个主 Agent。
- 只写了 Agent 模板，没有写调度规则，却期待它自动派活。
- 以为提示词里写“只读”就是系统级只读；真正的权限仍由主会话控制。
- 让多个 Agent 同时修改共享路由、类型定义或配置文件。
- 子 Agent 说“完成了”就直接相信，不核对证据。
- 把“详细分析”“深入研究”当成委派授权，结果开出一堆不必要的 Agent。
- 以为同一个模板创建的实例会共享记忆；它们通常各自独立。
- 过度拆分，导致协调和汇总成本超过并行节省的时间。

## 验证与复盘

### 技术验证

- 打开子 Agent 线程，检查它的关键结论是否有文件路径和证据。
- 检查主 Agent 的最终结论是否与子 Agent 的原始证据一致。
- 运行任务包中写明的测试命令，确认实际结果，而不是只看摘要。
- 查看最终 diff（代码差异），确认没有越界修改、调试代码或无关文件。
- 检查失败路径、权限边界和错误提示，而不只验证成功路径。

### 业务验证

- 用真实用户流程走一遍关键场景。
- 检查错误提示是否可理解。
- 检查权限和业务规则是否符合预期。
- 确认不存在“技术上通过、产品上不可用”的情况。

### 是否值得继续使用

可以观察四个指标：

1. 人工来回修改的次数是否减少；
2. 合并前发现的真实问题是否增加；
3. 联调问题是否减少；
4. 总开发时间是否下降。

如果拆分任务和核对结果的时间超过了并行节省的时间，就应该退回单 Agent。

### 止损条件

出现以下情况时，停止增加 Agent：

- 两个 Agent 修改了同一批文件；
- 同一问题修复两轮仍无法通过验收；
- 子 Agent 的结论互相矛盾，且没有测试能判断；
- 主 Agent 无法解释最终改动；
- 验证环境本身不可用；
- 总耗时明显超过单 Agent 方案。

## 检查清单

- [ ] 任务目标和“不做什么”已经写清楚
- [ ] 验收标准可执行、可观察
- [ ] 调查任务彼此独立，并明确只读
- [ ] 子 Agent 知道需要返回什么证据
- [ ] 接口和数据结构已经冻结
- [ ] 文件所有权已经分配
- [ ] 共享文件只有一个负责人
- [ ] 实现阶段只有一个写入者，或写入范围完全不重叠
- [ ] 验收者没有同时担任实现者
- [ ] 测试命令和实际输出已经核对
- [ ] 没有把密钥或生产凭据写进 Agent 模板
- [ ] 业务验收仍由人完成
