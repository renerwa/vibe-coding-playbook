# 多 Agent 协作：困惑梳理与最小实操

> 用途：整理一次关于 Codex 多 Agent 机制的对话，说明主 Agent、子 Agent、Agent 实例、Agent 线程分别是什么，以及在实际 Vibe Coding 中怎样使用。
> 最后更新：2026-11-05
> 默认读者：有技术常识但非科班出身的产品经理。
> 不覆盖：具体业务项目的架构设计、外部 Agent 框架的实现细节。
> 依据：OpenAI 官方文档《Subagents》以及本次对话中的实践讨论。

## 一句话结论

多 Agent 不是“默认自动组队”，而是：

> **主 Agent 根据任务需要，临时创建若干子 Agent；子 Agent 在各自线程中完成局部任务，把摘要交回主 Agent，由主 Agent 统一决策、整合和验收。**

模板只决定“某个角色应该怎样工作”，不自动决定“什么时候该派哪个 Agent”。

## 核心结论

1. **主 Agent 是当前主对话线程里的总负责人**，负责需求、拆分、协调、整合和最终答复。
2. **新建普通对话框会创建一个新的主 Agent 实例**，不是上一个对话的子 Agent，也不会自动继承聊天记忆。
3. **子 Agent 由主 Agent 创建**。你不需要提前打开窗口或手动创建运行中的子 Agent。
4. **自定义 Agent 模板不是运行中的 Agent**。它更像一份岗位说明书。
5. **同一个模板可以创建多个子 Agent 实例**；实例之间共享角色规则，但不共享记忆。
6. **每个子 Agent 通常有自己的 Agent 线程**，用来记录它读过的文件、执行的命令和中间结果。
7. **子 Agent 之间通常不直接通信**，而是由主 Agent 中转信息。
8. **模板不会自动触发任务拆分**。需要你明确要求，或者在 `AGENTS.md`、Skill 中写明调度规则。
9. **“只读”通常是提示词约束，不是系统级只读沙箱**。真正的权限仍由主会话的沙箱和审批设置决定。

## 术语表

| 名词 | 含义 | 是否是运行中的执行者 |
|---|---|---|
| Agent | 能使用工具、执行任务的 AI 工作者 | 可能是 |
| 主 Agent | 当前主对话线程里的总负责人 | 是 |
| 子 Agent | 由主 Agent 委派局部任务的 Agent | 是 |
| 自定义 Agent | 预先定义的岗位模板或配置 | 否 |
| Agent 实例 | 某个角色被实际创建出来的一次具体执行 | 是 |
| Agent 线程 | 这个实例工作的上下文、消息和工作记录 | 是，属于该实例 |
| 主线程 | 你和主 Agent 沟通的对话线程 | 是 |
| 调度规则 | 规定什么情况下使用哪个 Agent 的规则 | 否 |

“Agent 实例”是为了解释方便使用的辅助说法，不是产品里的一个单独按钮。官方文档更常使用 subagent（子 Agent）和 agent thread（Agent 线程）这两个词。

## 它们之间是什么关系

```text
项目
└─ 当前主对话（主 Agent 的主线程）
   ├─ 子 Agent 实例 A
   │  └─ Agent 线程 A：调查后端
   ├─ 子 Agent 实例 B
   │  └─ Agent 线程 B：调查前端
   └─ 子 Agent 实例 C
      └─ Agent 线程 C：独立验收

主 Agent 等待并收集各线程摘要，再统一决策和答复
```

关键区别：

- **主 Agent** 对整个任务负责；
- **子 Agent** 对局部任务负责；
- **Agent 实例** 是一次具体执行；
- **Agent 线程** 是这次执行的上下文和工作记录；
- **自定义 Agent** 只是创建实例时使用的一份角色定义。

## 快速答疑表

| 编号 | 你的困惑 | 准确结论 |
|---|---|---|
| 1 | 多 Agent 是不是默认的团队工作方式？ | 不是。默认由主 Agent 完成任务，只有需要并行或明确要求时才委派。 |
| 2 | 前端、后端、验收拆三个 Agent 合理吗？ | 有条件合理。接口冻结、文件不重叠、验收可执行时才适合；验收独立出来通常比强行拆前后端更值得。 |
| 3 | 主 Agent 是什么？ | 当前任务所在的主对话线程。 |
| 4 | 需要提前创建子 Agent 吗？ | 不需要。你明确要求后，主 Agent 会创建子 Agent。 |
| 5 | 新建一个对话框，能直接把它当某个主 Agent 的子 Agent 吗？ | 不能。普通新对话是另一个独立主 Agent，不会自动挂到原对话下面。 |
| 6 | 一个 Agent 做多件事，会自动开多个线程吗？ | 不一定。可以让一个实例顺序做，也可以让同一角色模板创建多个独立实例并行做。 |
| 7 | 同一个模板创建的新实例，是不是同一个 Agent？ | 是同一个角色类型，但不是同一个实例，也不共享记忆。 |
| 8 | 多个前端实例会共享上下文吗？ | 不会自动共享。需要主 Agent 传递摘要或共享契约。 |
| 9 | 每次新建对话都是新的主 Agent 吗？ | 是。每个普通对话都是新的主线程和主 Agent 实例。 |
| 10 | 子 Agent 怎么收到任务？ | 主 Agent 把任务包交给它，并创建独立 Agent 线程。 |
| 11 | 子 Agent 怎么把结果交回来？ | 完成后返回摘要；主 Agent 汇总，客户端可查看子 Agent 线程。 |
| 12 | 子 Agent 之间能直接聊天吗？ | 通常不直接通信，由主 Agent 中转。 |
| 13 | 官方模板有固定规范吗？ | 有。使用 TOML，放在指定目录，至少包含三个字段。 |
| 14 | Markdown 模板为什么也能跑？ | 主 Agent 把 Markdown 当提示词读取并复制给普通子 Agent；这不是官方注册机制。 |
| 15 | 自然语言模板和官方模板效果一样吗？ | 简单任务上可能相似，但机制、稳定性和可配置能力不同。 |
| 16 | 模板建好后会自动拆分任务吗？ | 不会。需要明确请求，或通过 `AGENTS.md`、Skill 写调度规则。 |
| 17 | 模板里写“只读”就安全吗？ | 不。它只是行为要求，不是系统级隔离。 |

## 几个最容易误解的问题

### 1. 模板注册不等于自动派活

模板回答的是：

> “这个 Agent 能做什么，应该怎么做。”

调度规则回答的是：

> “什么情况下应该使用哪个 Agent。”

只创建模板，不写调度规则，主 Agent 通常会自己在主对话里完成工作。

例如，即使你定义了 `frontend_explorer`，也不代表所有前端任务都会自动派给它。除非：

- 你在任务里明确要求使用它；
- 或 `AGENTS.md`、Skill 明确要求此类任务必须委派。

即使有规则，Codex 仍然是模型在判断，不是确定性的规则引擎。

### 2. 同一个 Agent 不等于同一个实例

“同一个 Agent”可能指两个不同东西：

- 同一个**角色模板**：例如都用 `frontend_explorer`；
- 同一个**运行实例**：同一个 Agent 线程继续工作。

同一个模板创建两个实例时：

```text
模板：frontend_explorer
├─ 实例 A：调查订单列表
└─ 实例 B：调查订单详情
```

它们共享规则，但各自有独立上下文和线程。

更准确的说法是：

> **同一个角色模板生成了多个独立实例；不是一个 Agent 分裂成多个共享记忆的线程。**

### 3. 新对话不是子 Agent

普通新对话：

```text
对话 1：主 Agent 实例 1
对话 2：主 Agent 实例 2
```

两者是平级关系，不会自动共享聊天记忆，也不会自动把结果交回对方。

子 Agent 线程：

```text
主 Agent（主线程）
└─ 子 Agent（子线程）
```

子 Agent 线程属于创建它的主任务，不是一个新的项目主对话。

### 4. Markdown 模板为什么也能工作

如果项目里有：

```text
Doc/Agents/frontend.md
```

并且根目录的 `AGENTS.md` 写了“参考这些模板创建子 Agent”，那么主 Agent 可能：

1. 读取 Markdown；
2. 把其中内容当成提示词；
3. 创建普通子 Agent；
4. 把规则复制到任务包中。

所以它会表现出“模板生效”的样子，但这不等于 Codex 把 Markdown 注册成了正式自定义 Agent。

这种方式的风险：

- 主 Agent 可能漏读或只读一部分；
- 规则可能随上下文变化而漂移；
- 名称不是正式标识；
- 模型、推理强度、工具能力不容易稳定配置；
- 团队协作时容易出现多份互相矛盾的说明；
- 换客户端或版本后行为可能不同。

### 5. “只读”不等于系统级只读

你可以在任务包或模板里写：

```text
不要修改任何文件。
```

这能降低修改风险，但它仍只是提示词约束。

自定义 Agent 继承主会话的权限、provider 和 MCP 配置；它不能覆盖主会话的 `sandbox_mode`、`approval_policy` 等设置。真正的安全边界仍然由主会话控制。

## 官方自定义 Agent 规范

### 位置

| 范围 | 路径 | 适用 |
|---|---|---|
| 个人级 | `C:\Users\madgu\.codex\agents\` | 所有项目 |
| 项目级 | 项目根目录下的 `.codex\agents\` | 当前项目 |

例如当前知识库项目的项目级路径是：

```text
D:\code\Vibe Coding技巧\.codex\agents\
```

每个 `.toml` 文件定义一个 Agent。

### 必填字段

```toml
name = "frontend_explorer"
description = "只读调查前端页面、请求封装和测试。"
developer_instructions = """
你是前端只读调查 Agent。

不要修改任何文件。
"""
```

三个字段分别是：

- `name`：Codex 用来识别和调用这个 Agent 的名称；
- `description`：说明什么时候应该使用它；
- `developer_instructions`：定义它的核心行为。

文件名最好与 `name` 一致；官方以 `name` 字段为准，不以文件名为准。

### 一个完整示例

```toml
name = "frontend_explorer"
description = "只读调查前端页面、请求封装、状态管理和测试；适用于实现前的代码调查。"

developer_instructions = """
你是前端只读调查 Agent。

目标：
查清指定前端功能的现有实现方式，为后续实现提供依据。

边界：
- 不修改任何文件。
- 不安装依赖。
- 不执行会改变项目环境的命令。
- 找不到证据时写“未确认”，不要猜测。

工作步骤：
1. 找到页面入口、路由和主要组件。
2. 查明请求封装、数据类型和状态管理方式。
3. 找到相关测试和验证命令。
4. 标出可能影响实现的风险点。

输出格式：
- 事实
- 文件路径
- 调用链
- 风险
- 验证方式
"""
```

### 可选配置

可以在 TOML 中配置模型行为，例如模型、推理强度、摘要方式和详细程度；也可以限制某些工具或技能。

初期建议保持最小配置：只写三个必填字段，先验证角色是否好用，再逐步增加模型和能力设置。

### 常见错误

- 把 `[agents]` 写进单个 Agent 文件：`[agents]` 应放在全局配置里；
- 一个文件写多个 Agent：每个文件只定义一个；
- 用 `.md` 代替 `.toml` 当作运行时配置；
- 使用与内置 Agent 相同的名字：`default`、`worker`、`explorer` 都是内置名称，自定义同名会覆盖内置定义；
- 把密钥、生产环境地址写进模板；
- 把具体任务的路径写死在模板里。模板描述岗位，具体文件范围应由主 Agent 的任务包提供。

## 自然语言模板：什么时候够用

如果你的目标是个人实验、快速试错、角色很少，Markdown 约定可以工作。

建议把它明确称为“提示词模板”，不要误认为正式运行时配置：

```text
docs/agents/
├─ frontend_explorer.md
└─ reviewer.md
```

根目录 `AGENTS.md` 可以只做索引：

```markdown
子 Agent 的角色说明位于 docs/agents/ 下。
这些文件是提示词模板，不是 Codex 的正式 TOML 配置。
```

如果要长期复用、团队协作、固定模型或限制工具能力，建议迁移到 `.codex/agents/*.toml`。

最稳妥的组合是：

```text
.codex/agents/*.toml   → 真正给 Codex 使用的 Agent 配置
docs/agents/*.md       → 给人阅读的说明和设计理由
AGENTS.md              → 简短索引和调度规则
```

## 让主 Agent 自动派活的写法

仅仅有模板不够，要把“触发条件”也写出来。例如在 `AGENTS.md` 中加入：

```markdown
## 子 Agent 调度规则

1. 单文件、小文案和小 bug：主 Agent 直接处理，不使用子 Agent。
2. 任务涉及不熟悉的代码或跨前后端时：先派两个只读调查 Agent。
3. 实现阶段默认由主 Agent 作为唯一写入者。
4. 只有前端和后端文件完全不重叠，且接口契约已冻结时，才允许并行实现。
5. 功能完成后，必须派独立验收 Agent 检查测试和关键失败路径。
```

也可以在每个具体任务中明确说：

```text
这个任务按多 Agent 流程执行：
先派两个只读子 Agent 分别调查前后端；
等全部完成后由你汇总；
汇总前不要修改代码。
```

但要注意：调度规则能提高自动委派的概率，不能保证每一次都按预期执行。

## 推荐的最小实操流程

### 第 1 步：写任务包

至少写清楚：

```text
目标：
非目标：
输入和背景：
允许修改的目录：
验收标准：
测试命令：
输出格式：
停止条件：
```

产出物：一份任务说明，而不是只存在于聊天记录里的口头要求。

### 第 2 步：两个只读调查 Agent

适合调查不同问题，例如：

- Agent A：后端路由、业务逻辑、数据库和测试；
- Agent B：前端页面、请求封装、状态管理和测试。

要求它们只读，返回：

- 事实；
- 文件路径；
- 调用链；
- 风险；
- 建议的验证方式。

产出物：代码地图和风险清单。

### 第 3 步：冻结契约和文件边界

主 Agent 汇总调查结果，确定：

- API 路径、请求参数、响应结构、错误码和权限；
- 数据库或数据结构变化；
- 文件所有权；
- 共享文件由谁修改；
- 验收用例。

没有冻结接口，不要让前端和后端并行写代码。

### 第 4 步：实现阶段保持一个写入者

初期建议：

- 主 Agent 自己写；
- 或只派一个实现 Agent；
- 每完成一个模块就运行对应测试；
- 发现契约问题先停下，不自行改接口。

只有文件不重叠、接口稳定、你熟悉 Git 分支或独立工作目录时，再尝试并行写入。

### 第 5 步：独立验收

验收 Agent 应：

- 依据冻结的验收标准检查；
- 运行测试或明确的验证命令；
- 检查失败路径和边界条件；
- 报告文件位置、复现方式、影响和建议；
- 不修改业务代码来让测试通过。

产出物：验收报告，而不是一句“已完成”。

### 第 6 步：你做业务验收

技术测试通过不等于业务验收通过。你仍然要确认：

- 用户是否真的能完成目标；
- 错误提示是否可理解；
- 权限和业务规则是否符合预期；
- 是否存在“技术上通过、产品上不可用”的情况。

## 什么任务适合拆多 Agent

| 情况 | 建议 |
|---|---|
| 改一个文件、小文案、小 bug | 主 Agent 直接做 |
| 接手陌生代码库 | 两个只读调查 Agent |
| 前后端功能且接口已冻结 | 可以拆前后端 |
| 前后端共享路由、类型或配置 | 先由一个负责人完成共享部分 |
| 多个页面目录互不重叠 | 可以考虑多个前端实例 |
| 没有测试或验收标准 | 先补验收，不要急着并行 |
| 多个 Agent 必须改同一文件 | 改成一个写入者 |
| 任务有强依赖关系 | 一个实例顺序做，或分阶段做 |

## 起步路线

### 阶段 1：只读调查

主 Agent + 两个只读调查 Agent。代码仍由主 Agent 写。

### 阶段 2：增加独立验收

在阶段 1 的基础上增加验收 Agent，验证“实现者说完成”是否可信。

### 阶段 3：固定模板

把反复使用的调查、审查、验收角色写成 `.codex/agents/*.toml`。

### 阶段 4：有条件并行实现

在接口稳定、文件不重叠、测试可靠、主 Agent 能集成的前提下，才考虑前端和后端并行写代码。

不要一开始就上 5 个以上 Agent。Agent 越多，上下文整理、结果核对和冲突处理成本越高。

## 判断是否值得使用

可以观察四个指标：

1. 人工来回修改的次数是否减少；
2. 合并前发现的真实问题是否增加；
3. 联调问题是否减少；
4. 整体开发时间是否下降。

如果拆分任务和核对结果的时间超过了并行节省的时间，就应该退回单 Agent。

## 止损条件

出现以下情况时，停止增加 Agent：

- 两个 Agent 修改了同一批文件；
- 同一问题修复两轮仍无法通过验收；
- 子 Agent 的结论互相矛盾，且没有测试能判断；
- 主 Agent 无法解释最终改动；
- 验证环境本身不可用；
- 总耗时明显超过单 Agent 方案。

## 检查清单

- [ ] 任务目标和“不做什么”已经写清楚
- [ ] 验收标准是可执行、可观察的
- [ ] 调查任务彼此独立，且明确只读
- [ ] 接口和数据结构已经冻结
- [ ] 文件所有权已经分配
- [ ] 共享文件只有一个负责人
- [ ] 实现阶段只有一个写入者，或写入范围完全不重叠
- [ ] 验收者没有同时担任实现者
- [ ] 测试命令和实际输出已经核对
- [ ] 没有把密钥或生产凭据写进 Agent 模板
- [ ] 业务验收仍由人完成

- 本文不是“多 Agent 一定优于单 Agent”的结论。对当前阶段而言，优先保证任务边界、验收标准和可维护性。
