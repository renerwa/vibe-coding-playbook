# 最小 Harness 模板包

> 用途：给真实的 Web 后端项目提供一套可直接复制、低维护成本的 Agent 协作模板。
> 默认读者：有技术常识但非科班出身的产品经理。
> 定位：这是协作层的“最小工作台”，不是代码框架，也不是完整研发流程。

## 一句话结论

Harness（运行框架）是让 Agent 能稳定工作的那层“工作台”：它负责提供项目上下文、任务边界、工具约束和验收反馈。本模板包只做四件事：**把规则写清、把任务切小、把证据留下、把错误沉下来**。

它不能保证 Agent 一次做对；它保证 Agent 不容易靠“看起来完成了”蒙混过关。

本包定义的是协作契约，不是强制机制。真正的文件权限、命令沙箱和工具调用由你使用的 Agent 产品执行；规则要靠测试、验收和人工复核才真正生效。

## 这套模板解决什么

- Agent 不看项目约定，改出与现有代码风格不一致的实现。
- 任务越做越大，最后交付了一堆“顺手改”的无关内容。
- Agent 说“测试通过”，但没有命令、输出和退出码。
- 验收标准写成“功能正常”，人和 Agent 对“正常”的理解不一致。
- 同类错误反复出现，每次都只靠下一轮对话提醒。

## 适用场景

| 场景 | 是否适用 | 说明 |
|---|---|---|
| 已有可运行的 Web 后端项目 | 高 | 尤其适合新增 API、业务规则、数据转换、修 Bug |
| 产品经理与 Agent 一对一协作 | 高 | 人工负责定义正确和最终验收 |
| 任务能拆成一个可独立验收的行为 | 高 | 一个任务卡只覆盖一个小目标 |
| 项目已有测试或可复现的人工验证步骤 | 高 | 没有自动化测试也可以先用人工证据 |
| 多人并行修改同一批文件 | 低 | 需要额外的分支、代码审查和冲突管理 |
| 一次性原型、方向探索 | 低 | 可以用，但不要把它当作生产交付 |
| 安全审计、资金清算、正式架构评审 | 不替代 | 本包只是最低协作层，仍需专业评审和专项测试 |

### 不适用场景

- 项目还不能安装或启动，也没有任何可复现的验证路径：先修运行环境，再谈 Harness。
- 需求本身还没有定义清楚：先做需求澄清或一次性技术试验，不要用任务卡掩盖目标缺失。
- 需要正式安全、架构或合规结论：本模板只能提供证据和检查框架，不能替代专业审查。

## 5 分钟上手

前置条件：目标项目已经能在本机安装、启动，并且你知道至少一条测试或人工验证路径。

1. **复制规则模板（约 1 分钟）**：把 `AGENTS.md.template` 复制到目标项目根目录，重命名为 `AGENTS.md`。这不是本仓库的规则文件，只有复制到目标项目后才生效。
2. **先填四项（约 2 分钟）**：只填项目目标、技术栈与 Runtime（运行时，执行代码的环境）、目录地图、安装/运行/测试命令。其余暂时保留 `[ ]`，不要一次写满。
3. **验证命令（约 1 分钟）**：在目标项目根目录实际运行这些命令，确认能复制、能复现。不可用的命令不要保留，先写“未知”并说明。
4. **创建任务卡（约 1 分钟）**：复制 `任务卡.md` 到目标项目的任务目录，例如 `docs/tasks/[日期]-[任务名].md`；只写一个目标、一个范围、三条左右可判断的验收标准。
5. **执行并验收（约 1 分钟起）**：让 Agent 先读 `AGENTS.md` 和任务卡，先跑基线（改动前的测试结果），再改动；完成后按 `验收与复盘.md` 核对证据。首次填写项目信息可能超过 5 分钟，熟练后一个 L1 小任务（单个低风险行为）通常可在 5 分钟内完成准备。

给 Agent 的最小启动话术：

```text
请先阅读项目根目录的 AGENTS.md 和任务卡：[路径]。
先运行任务卡中的基线命令并报告结果，再开始改动。
只处理任务卡范围内的事项；如果范围、验收标准或命令不清楚，先停下来问我。
完成后按验收标准逐条给出证据，不要只说“已完成”。
```

## 文件清单

| 文件 | 作用 | 使用位置 |
|---|---|---|
| `README.md` | 说明适用边界、上手步骤、加严路径和风险 | 本模板目录 |
| `AGENTS.md.template` | 目标项目的规则地图，约束上下文、命令和禁止事项 | 复制为目标项目根目录的 `AGENTS.md` |
| `任务卡.md` | 单个任务的合同：目标、范围、验收、证据和人工确认点 | 复制到目标项目的任务目录 |
| `验收与复盘.md` | 提交前检查、证据标准、失败分类和规则沉淀 | 每个任务完成时使用 |

## 一个简短例子：新增订单导出接口

**任务卡怎么写**：目标是“为订单列表增加按当前筛选条件导出 CSV（逗号分隔的表格文件）的接口”；范围是“新增导出入口、复用现有筛选和权限逻辑”；非目标明确写“不做异步导出、不做定时任务、不改订单列表接口”。验收至少写三条：未登录返回 401；普通用户只能导出自己可见的订单；筛选条件与页面结果一致，文件包含约定表头。验证命令写目标测试、完整测试和一次人工下载检查。

**怎么验收**：要求 Agent 给出改动文件清单、实际命令、退出码、目标测试与完整测试结果，以及一份脱敏的导出样例。人工核对一次“切换用户后不能看到他人订单”，并复跑命令确认不是口头声明。

**失败后怎么沉淀**：如果 Agent 为了导出改了通用查询、导致订单列表行为变化，这不是再加一句“注意别改坏”就结束。应先回退无关改动，再把“新增读取接口必须包含当前用户/组织范围，并补一条越权失败测试”写入 `AGENTS.md`，同时在测试中固定这条边界。规则负责提醒，测试负责自动拦截。

## 如何逐步加严

不要一开始引入完整平台。按实际痛点每次只加一层：

| 阶段 | 触发条件 | 增加什么 | 代价 |
|---|---|---|---|
| 1. 最小规则 | 项目刚接入 | 填好 `AGENTS.md` 的目标、目录和命令 | 需要维护命令有效性 |
| 2. 任务合同 | 出现范围漂移 | 每个任务必须写非目标和验收标准 | 前期多花 5～10 分钟 |
| 3. 证据验收 | Agent 口头宣布完成 | 强制命令、输出、退出码和人工验收记录 | 需要复跑和保存证据 |
| 4. 测试先行 | 行为反复出错 | 先写失败测试或复现测试，再实现 | 小任务也会增加测试时间 |
| 5. 自动化检查 | 同类错误重复两次以上 | 增加 lint（自动检查代码风格和常见错误）、类型检查、CI（持续集成）或回归测试 | 需要维护工具链 |
| 6. 高风险加严 | 涉及金额、权限、数据迁移、并发 | 独立审查、集成测试、回滚方案和人工验收 | 流程明显变慢，只用于高风险任务 |

判断标准：如果某个检查连续 2～3 个任务都没有发现问题，也未阻止返工，考虑降级或删除；不要为“看起来专业”长期保留无效步骤。

## 如何验证这套 Harness 真的有效

用 2～3 个真实的小任务试运行，不要用假想案例。至少观察：

| 观察项 | 合格信号 | 不合格信号 |
|---|---|---|
| 范围控制 | 改动文件都在任务卡范围内 | 出现未说明的重构、依赖或接口变化 |
| 命令可信 | 命令可复制、可复跑，有退出码 | 只有“测试通过”的文字，没有原始输出 |
| 验收闭环 | 每条验收标准都有对应证据 | 验收项被遗漏或被改成更容易通过的版本 |
| 失败诚实 | 失败、环境问题和未覆盖项被主动报告 | 用“基本完成”“应该没问题”替代结论 |
| 返工趋势 | 2～3 个任务后返工轮数下降 | 同类问题仍反复出现，规则没有沉淀 |
| 成本可接受 | 流程耗时低于返工节省的时间 | 每个小任务都被流程拖住 |

再做一次“诚实性抽查”：让 Agent 运行一条已知会失败或不适用的命令，看它是否如实报告，而不是自行改成别的命令后宣称通过。也可以检查 diff（改动差异）是否只包含任务卡允许的文件。

如果连续两个任务中，任一验收项没有证据、复跑失败或范围失控，先修 Harness，不要继续加工具。

## 主要风险

| 风险 | 表现 | 最低成本应对 |
|---|---|---|
| 规则过期 | 目录、命令或技术栈已经变化，Agent 仍按旧信息执行 | 每次命令失效时同步修正 `AGENTS.md` |
| 规则膨胀 | `AGENTS.md` 变成长篇手册，关键约束被淹没 | 控制在约 100 行，细节放到独立文档 |
| 自证完成 | Agent 自己写验收、自己判断通过 | 人工复跑命令并核对关键业务行为 |
| 证据造假或误读 | 只截取有利输出、隐藏失败、混淆退出码 | 要求原始命令、完整输出摘要和退出码 |
| 误把通过当正确 | 测试只覆盖正常路径，真实权限或数据边界仍错误 | 至少补边界、异常和高风险人工验收 |
| 过度约束 | 每个小改动都走重流程，团队开始绕过流程 | 按 L0～L3 分级（从轻量改动到高风险变更），小任务用轻量流程 |
| 泄露敏感信息 | 证据中包含密钥、用户数据、生产日志 | 提交前脱敏，只保留最小必要信息 |
| 替代专业审查 | 把模板当作安全、架构或合规保证 | 高风险变更仍走代码审查和专项检查 |

## 最小成功标准

- 目标项目有一份可执行的 `AGENTS.md`，不是空模板。
- 每个任务都有可判断的验收标准和可复跑的命令。
- 每次完成都有证据，且至少一条关键行为经过人工确认。
- 同类错误出现后，至少沉淀为规则、测试、lint 或检查清单中的一种。
- 团队知道这套模板只降低协作失误，不替代工程判断。
