# 向量数据库入门指南：从“按字段查”到“按意思找”

> 用途：用一条完整链路解释向量数据库是什么、文章如何入库、分块为什么会丢上下文、图片如何处理，以及如何查询、选型和验证。
> 最后更新：2026-11-11
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：无。
> 不覆盖：具体向量数据库的部署运维、ANN 算法的数学推导、各厂商 API 的完整参数。

## 一句话结论

> **向量数据库不是“会理解语义的数据库”，而是“能快速找出离某个向量最近的几条记录”的数据库。语义理解发生在它之前：由 Embedding 模型把文字变成向量。**

如果只记一句话：

> **MySQL 问“是哪一条”，向量数据库问“像哪几条”。**

这不是修辞，而是两种查询方式的根本区别。下面从一个普通数据库解决不了的问题开始。

## 一、MySQL 能回答“是哪一条”，但回答不了“像哪几条”

假设你有一份售后知识库，里面有一篇文章写着：

> 退款一般 1～3 个工作日到账。银行卡支付可能延迟到 5 个工作日。

用户输入的是：

> 钱什么时候退回来？

如果只用 MySQL 的 `LIKE`：

```sql
SELECT *
FROM articles
WHERE content LIKE '%退款%';
```

这篇文章很可能搜不到，因为用户没有说“退款”，说的是“钱退回来”。同义词、口语、错别字、跨语言表达，都会让“精确匹配”失效。

传统数据库擅长回答“哪一条记录的字段等于某个值”：

```sql
WHERE status = '退款中'
  AND amount > 100
  AND created_at > '2026-01-01'
```

向量数据库擅长回答另一种问题：

> 哪几条内容和这句话的意思最接近？

| 查询方式 | 典型问题 | 返回结果 |
|---|---|---|
| 传统数据库 | 状态是退款中、金额大于 100 的订单 | 精确命中的行 |
| 向量数据库 | 和“钱什么时候退回来”意思相近的文档 | 按相似度排序的几条 |

所以向量数据库不是用来替换 MySQL 的。订单、库存、账务、权限，仍然应该放在关系型数据库里；向量数据库补的是“按意思找”的能力。

## 二、向量不是魔法，它是模型给文字定的坐标

要让数据库按“意思”找，第一步是把文字变成可计算的数字。

这个过程叫 **Embedding（嵌入）**，负责转换的模型叫 **Embedding 模型**。它接收一段文字，输出一串按顺序排列的数字，这串数字就是 **向量（vector）**。数字的个数叫 **维度（dimension）**。

可以用一个二维玩具例子来理解。假设第一维大致代表“售后/钱”，第二维代表“物流/地址”：

| 内容 | 坐标（示意） |
|---|---|
| 如何申请退款 | (0.92, 0.12) |
| 钱多久能退回来 | (0.88, 0.18) |
| 退款多久到账（用户问题） | (0.90, 0.15) |
| 如何修改收货地址 | (0.10, 0.86) |
| 运费怎么算 | (0.35, 0.72) |

前三个点挤在一起，后两个在另一个角落。向量数据库做的事就是：把用户问题也变成坐标，然后找出离它最近的几条内容。

真实模型通常输出几百到几千维。人脑画不出 1536 维，但这不影响计算：维度只是坐标轴的数量，距离仍然可以算。常用的 **余弦相似度**，看的是两个向量方向的夹角；夹角越小，意思越接近。

这里有两个容易误解的地方。

第一，**向量不是原文的压缩包**。它更像“语义指纹”，不能可靠地还原出原文。所以原文必须另外存一份。

第二，**数据库不理解语义**。它不知道什么是“退款”，也不知道什么是“油机”。它只负责存数字、算距离。真正把“意思”编码进去的，是 Embedding 模型。

这也解释了一个重要事实：**不同模型算出的向量属于不同坐标系。** 模型 A 里的坐标，不能直接拿到模型 B 里比较。换模型，等于换地图。

## 三、向量数据库的结构：普通表 + 向量字段 + 近邻索引

从数据模型看，向量数据库并没有那么神秘。以 pgvector 为例，它就是在 PostgreSQL 里加了一种 `vector` 字段：

```sql
CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  content     text NOT NULL,
  embedding   vector(1024) NOT NULL,
  module      text,
  acl         text
);
```

一条记录仍然可以理解为“ID + 原文 + 元数据 + 一串向量”。**元数据**指的是标题、模块、权限、来源、更新时间这类结构化信息。

但“有向量字段”不等于“有向量检索能力”。真正的分水岭是索引。

普通 B+ 树索引擅长 `WHERE id = 123`、`WHERE status = '退款中'`；向量索引擅长：

```sql
ORDER BY embedding <=> :query_vector
LIMIT 5
```

`<=>` 是 pgvector 的余弦距离运算符。没有向量索引时，数据库也能算距离，但要把每一行都算一遍。几千条还行，几百万条就慢了。**HNSW、IVF 这类 ANN（Approximate Nearest Neighbor，近似最近邻）索引**，就是为“快速找最近的几条”设计的。它可能漏掉极少数真正最近的结果，用一点点召回率换大幅速度提升。

所以更准确的说法是：

> **普通表 + 向量字段是“形”；向量索引 + Top-K 近邻查询是“神”。**

常见的方案可以分成几类：

| 方案 | 形态 | 适合场景 |
|---|---|---|
| pgvector | PostgreSQL 扩展 | 已有 PostgreSQL；中小规模；需要事务和 SQL 过滤 |
| Chroma | 轻量、可嵌入的向量库 | 本地原型、小项目 |
| Qdrant | 独立向量数据库 | 中大规模、过滤条件较多 |
| Milvus | 分布式向量数据库 | 亿级向量、高吞吐 |
| Pinecone | 托管 SaaS | 不想运维、快速上线 |
| Elasticsearch / OpenSearch | 搜索引擎加向量检索 | 已有 ES，想同时做关键词和向量检索 |
| Faiss | 向量检索库，不是数据库 | 离线实验、自己嵌入到应用里 |

选型时先问一个问题：**我现有的数据库能不能加向量检索？** 如果已经在用 PostgreSQL，pgvector 往往是成本最低的起点。等到数据量、并发或多租户需求真的上来了，再考虑独立向量库。

## 四、把一篇文章存进去，实际发生了什么

现在把镜头拉近，看一篇文章从文件到可检索内容的过程。

假设文章是《零售管理系统 - 油机参数配置》，里面分别讲了 IP 怎么配、串口参数怎么配。它在系统里通常不是只存一条记录，而是拆成一张文档记录和多条片段记录：

- `documents` 表存文章本身：标题、系统、模块、原文、来源；
- `chunks` 表存检索片段：片段正文、向量、所属章节、权限。

整个流程可以分成五步。

### 1. 抽取和清洗

从 Markdown、Word、PDF 或网页里取出正文，去掉导航栏、页脚、广告和重复标题。PDF 还要保留页码和图片位置，后面处理图片时会用到。

### 2. 分块

把长文章切成若干片段。分块的目标不是“每段一块”，而是“每块只讲一个相对完整的主题”，同时不超过 Embedding 模型的输入长度。

例如：

- 块 1：IP 配置；
- 块 2：串口参数配置；
- 块 3：常见问题。

如果文章只有几百字，而且只讲一个主题，一整块就够了。

### 3. 补上下文

这是最容易被跳过、但非常关键的一步。

如果块里只有“IP 地址通过后台参数设置修改”，Embedding 模型不知道它是“零售管理系统里的油机参数”，还是“某个路由器的网络配置”。所以要在向量化文本前面补一行上下文：

```text
《零售管理系统 - 油机参数配置》> IP 配置
适用对象：零售管理系统中的油机设备
IP 地址通过后台“参数设置”修改，默认值为 192.168.1.100……
```

### 4. 向量化

把“上下文 + 原文”交给 Embedding 模型：

```python
embedding_text = context_header + "\n" + chunk_text
vector = embed_model.embed(embedding_text)
```

你不需要自己算向量，也不需要知道每个数字代表什么。模型返回什么，就存什么。

但要记住：**入库时用哪个模型，查询时就必须用同一个模型。** 文档用模型 A、问题用模型 B，算出来的向量不可比。

### 5. 入库和建索引

把原文、上下文、向量和元数据写入 `chunks` 表，再建向量索引：

```sql
CREATE INDEX chunks_embedding_idx
ON chunks
USING hnsw (embedding vector_cosine_ops);
```

这里有一个工程细节：**原文和用于向量化的文本要分开存。**

- `content`：原文，用来展示和交给大模型；
- `context_header`：标题、章节路径、适用对象；
- `embedding_text`：`context_header + content`，只用来算向量。

这样以后调整上下文写法，只需要重算向量，不用改原文。

这套“先把资料检索出来，再让大模型基于资料回答”的流程，通常叫 **RAG（Retrieval-Augmented Generation，检索增强生成）**。向量数据库负责“找”，大模型负责“答”。

## 五、分块：切出可检索的小主题，而不是切碎

分块是整条链路里最容易被低估的一步。切得太大，一个块混了多个主题，向量会被平均掉；切得太小，块失去上下文，用户看到“它默认是 192.168.1.100”却不知道“它”是谁。

一个实用的默认顺序是：

> **先按作者的结构切，没结构按段落，段落太长按句子，最后才按字数硬切。**

具体可以这样做：

1. 短文章不切。只有几百字、只讲一个主题的文章，直接一整块。
2. 有标题就按标题层级切：`H1 → H2 → H3`。
3. 没标题就按空行分段，把相邻段落合并到 500～700 个汉字。
4. 单段太长，按 `。！？；` 分句，再把句子打包成 500～600 字。
5. 需要时保留 50～100 字重叠，避免答案刚好被切断。
6. 每块前面补文章标题、章节路径或生成的小标题。
7. 表格保留表头；代码按函数切；FAQ 按一问一答切。

这些数字是起点，不是硬规则。最终还要看模型的 **token** 上限。token 是模型处理文本的计量单位，不等同于汉字；中文粗略估计时，可以先把一个字当作接近一个 token，但不同模型的分词器不一样，不能完全按字数硬算。

没有标题的文章很常见，不需要先人工补几百个标题。可以用文件名、第一句，或者让大模型生成 10～20 字的小标题。关键是把生成结果单独存成 `generated_title`，不要假装它是原文标题。

**分块是人工来分吗？** 不是。实际系统里是程序自动分，人工只做两件事：定规则、抽检调参。人工逐篇切分不可扩展，也不一致；只有在少量高价值文档，或者制作评测标准时，才值得手工处理。

如果自己写分块程序，第一版不需要上框架。一个 Python 文件、一个函数就够：按空行分段，合并到目标长度，超长按句子切，记录字符起止位置。真正难的不是“切”，而是边界情况：没有标点、超长段落、表格、代码块、空文本。写完之后要用这些情况做测试。

对于结构很乱的长文，还可以用 **父子分块**：用 200～300 字的小块建索引，负责精准命中；每个小块记录它属于哪个 800～1500 字的大块；检索到小块后，把大块返回给大模型。这样既保留检索精度，又补回上下文。

## 六、分块后最容易丢的，是“这块属于谁”

分块解决了长度问题，却制造了一个新问题：**块失去了出身。**

还是用油机文章举例。原始小节叫“零售管理系统 > 油机参数配置 > IP 配置”，但切出来的块可能只剩：

```text
IP 地址通过后台“参数设置”修改，默认值为 192.168.1.100。
```

这条向量会非常接近大量通用的“IP 配置”文档。用户问“油机 IP 怎么配”时，真正的油机文档可能排不到前面；用户只问“IP 怎么配”时，又会召回一堆无关内容。

原因很简单：**Embedding 模型是逐块独立处理的，它不会自动知道这篇文章的标题和上下文，除非你把这些信息写进向量化文本。**

最有效的修法，是给块补一个短上下文：

```text
《零售管理系统 - 油机参数配置》> IP 配置
适用对象：零售管理系统中的油机设备
IP 地址通过后台“参数设置”修改，默认值为 192.168.1.100……
```

这样向量里就带上了“零售管理系统 / 油机 / IP 配置”的信号。

但上下文不是越长越好。如果每个块都重复整篇摘要，所有块会变得很像，反而降低区分度。header 控制在 1～3 行，写清楚“哪篇文档、哪个章节、适用于什么对象”就够了。

除了 header，还有四种配合手段：

1. **元数据过滤。** 存 `system`、`module`、`device_type`、`section_path`，查询时按模块过滤。适合用户从“油机参数”页面进入的场景。
2. **父块或相邻块。** 检索命中一个小块后，返回它所属的小节，或者前后各一块，补全上下文。
3. **混合检索。** 向量负责“意思相近”，关键词/BM25 负责“油机”“型号”“错误码”这类专有词。两边各召回一批，再合并排序。
4. **重排。** 先召回 20～50 条，再用重排模型结合标题、章节路径和原文重新排序，选出最相关的 3～5 条。

如果产品界面知道用户正在看“零售管理系统 > 油机参数”，也可以把这个范围加进查询条件。但不要偷偷改写用户的问题而不记录；查询范围应该来自明确的入口或用户选择。

## 七、文章里有图片：先变成可检索的文字，再保留原图

文字块处理好后，还有一个常被忽略的内容：图片。

大多数知识库不需要把图片直接变成向量。更稳的做法是：

> **把图片里的文字 OCR 出来，再让视觉模型生成一句描述，然后把“描述 + OCR 文字 + 原图引用”一起存；原图单独放对象存储。**

这里两个术语解释一下：

- **OCR**：光学字符识别，把图片里的文字提取出来。
- **视觉语言模型（VLM）**：能看图并生成文字描述的模型。

不同图片要不同处理：

| 图片类型 | 例子 | 处理方式 |
|---|---|---|
| 装饰图 | Logo、图标、背景图 | 直接跳过 |
| 截图/界面 | 油机 IP 配置页面 | OCR 提取字段和值 + 描述界面 + 保存原图 |
| 流程图/接线图 | 油机与串口服务器接线 | 描述连接关系 + OCR 识别标签 + 人工抽检 |
| 图表 | 趋势图、统计图 | 提取数据或描述趋势，不能只 OCR |
| 实物照片 | 设备外观、接口位置 | 生成描述；需要相似图搜索时再加图片向量 |

一条图片记录可以长这样：

```json
{
  "article_id": "oil-config",
  "section_path": "油机参数配置 > IP 配置",
  "image_path": "s3://docs/oil/ip-config.png",
  "page": 3,
  "ocr_text": "IP地址 192.168.1.100 子网掩码 255.255.255.0",
  "caption": "零售管理系统油机网络参数配置界面，红框处为 IP 地址输入框",
  "embedding_text": "《零售管理系统 - 油机参数配置》> IP 配置\n图片说明：零售管理系统油机网络参数配置界面\n图中文字：IP地址 192.168.1.100……"
}
```

检索时用 `embedding_text`，展示时用 `image_path`，回答时可以把原图一起返回。

如果图片只是辅助说明，可以跟附近正文放在同一块；如果图片包含正文没有的关键信息，例如接线图、界面字段，就单独做一块，但保留 `parent_id` 指向所属小节。图片不要和它的说明、图注、上下文拆散。

**多模态向量**是另一条路线：用 CLIP、SigLIP 这类模型把图片和文本映射到同一个向量空间，支持“以图搜图”。但它更适合找“相似的图”，不擅长读小字。精确的 IP、端口号、波特率，仍然要靠 OCR。图片向量和文本向量要分表或分字段存，不要和 BGE、OpenAI 的文本向量混在同一个索引里。

图片处理最容易踩的坑是：只靠视觉模型描述，不保留 OCR。模型可能把 `192.168.1.100` 说错；参数、端口号、型号必须保留原始 OCR 文字，并抽检。截图里还可能包含真实 IP、设备序列号、客户信息，送外部 OCR/视觉 API 前要确认合规，必要时打码或本地部署。

## 八、查询：SQL 还是 API

内容和图片都进去了，最后看怎么查。

用 pgvector 时，查询仍然是 SQL：

```sql
SELECT id, content, document_id,
       1 - (embedding <=> :query_vector) AS similarity
FROM chunks
WHERE acl = 'customer'
  AND module = '油机参数'
ORDER BY embedding <=> :query_vector
LIMIT 5;
```

这里三部分各司其职：

- `WHERE`：普通字段过滤，例如权限、模块、文档 ID；
- `ORDER BY embedding <=> :query_vector`：按向量距离排序；
- `LIMIT 5`：取最近的 5 条。

用 Milvus、Qdrant、Pinecone 这类独立向量库时，通常不是 SQL，而是 SDK 或 HTTP API。伪代码大概是这样：

```python
results = vector_db.search(
    vector=query_vector,
    top_k=5,
    filter={"module": "油机参数", "acl": "customer"},
)
```

不同产品的参数名不一样，但核心永远是三件事：

```text
一个查询向量 + 要几条（Top-K）+ 过滤条件
```

不管用 SQL 还是 API，完整链路都是：

```text
用户问题
  → 调用 Embedding 模型
  → 得到 query_vector
  → 向量数据库检索
  → 返回 ID、距离、元数据、原文片段
  → 可选：重排
  → 取回原文或父章节
  → 交给大模型生成回答
```

这里有两个容易混淆的点。

第一，**向量数据库通常不接收原始文本，只接收向量。** 你要先调用 Embedding 模型把问题转成向量。除非平台内置了 Embedding，把文本交给它，它在内部帮你转。

第二，**向量数据库返回的不是答案，而是最相关的几条记录。** 生成答案是大模型的事。数据库返回 ID、分数和元数据；你的程序再回表取原文，必要时取父章节，最后交给大模型。

过滤条件要和检索一起传，不要先取 100 条再在程序里删掉无权限的。这样可能把正确结果漏掉，也可能让无权限内容进入模型上下文。

## 九、模型选择与迁移：一开始选对，后面少返工

查询效果好不好，很大程度上取决于 Embedding 模型选得对不对。

先区分两类模型：

- **聊天模型**：输入文字，输出文字，例如各种大语言模型；
- **Embedding 模型**：输入文字，输出向量。

你要调用的是后者。常见选择有：

| 模型 | 调用方式 | 特点 | 适合 |
|---|---|---|---|
| text-embedding-3-small | OpenAI API | 便宜、稳定，常见 1536 维 | 快速验证 |
| text-embedding-3-large | OpenAI API | 质量更高，常见 3072 维，更贵 | 对召回要求高 |
| BGE-M3 | 本地部署 / Ollama | 多语言、中文效果不错、可离线，常见 1024 维 | 内部文档、隐私敏感 |
| Qwen3-Embedding | 本地部署 / 云 API | 多语言、尺寸可选 | 中文或多语、可自托管 |
| multilingual-e5-large | 本地部署 | 多语言、比较成熟 | 多语言检索 |
| Cohere / Voyage / Jina | 云 API | 面向检索优化 | 海外业务、托管服务 |

如果是公司内部的中文文档，优先考虑 BGE-M3 这类可自部署模型，或者国内合规云平台的文本向量接口。如果只是快速验证，`text-embedding-3-small` 或国内云 API 更省事。具体模型名和可用性，以服务商当前文档为准。

选择时重点看：中文效果、最大输入长度、向量维度、成本和延迟、数据合规、批量调用能力、版本稳定性。不要只看排行榜，拿自己的 30～50 个真实问题测 **Recall@5**，比看通用榜单可靠。

比“选哪个模型”更重要的是三条规则：

1. **文档和查询必须用同一个模型。** 同一系列也不行：small 和 large 是两个模型，不能混。
2. **维度必须和数据库字段一致。** BGE-M3 常见 1024 维，OpenAI small 常见 1536 维；表里写 `vector(1024)` 还是 `vector(1536)`，要跟模型对齐。
3. **换模型必须全量重算。** 不同模型是不同的坐标系，旧向量不能和新向量放在同一个索引里比较。

所以，“用了某个模型就要一直用”更准确的说法是：

> **同一个索引内必须一直用同一个模型、同一个版本、同一个维度。换模型可以，但要全量重算、重建索引，不能混用。**

迁移时建议新建字段或新表，用新模型重新向量化，拿同一批问题比较新旧效果，确认更好后再切换查询。旧索引保留一段时间，方便回滚。表里记录 `embedding_model`、`embedding_version`、维度、距离算法，避免以后自己都忘了当初用的是什么。

## 十、怎么验证：不要用“能跑”当完成

向量检索最危险的地方，是它“看起来能用”。随便问一句，返回几条相关内容，很容易让人以为系统已经完成。真正要验证的是：**该找到的有没有找到，不该找到的有没有混进来，答案有没有被切断。**

准备 30～50 个真实问题，每个问题标注正确的原文片段，然后看：

| 检查项 | 怎么测 | 通过标准 |
|---|---|---|
| 召回 | 30～50 个问题 | 正确片段进入前 5 条 |
| 领域混淆 | 通用 IT 文档是否排到油机文档前面 | 错误领域率可控 |
| 上下文 | 只返回块，vs 返回父块 | 答案完整，不依赖猜测 |
| OCR | 20 张含参数的图片 | IP、端口、型号等数字准确 |
| 权限 | 用无权限账号提问 | 不召回越权内容 |
| 更新 | 修改文章后重新提问 | 旧内容不再出现 |

针对油机文章，可以专门做一组 A/B 测试：

- 原始块直接向量化，vs 加 `context_header`；
- 不加模块过滤，vs 加 `module = 油机参数`；
- 只返回命中块，vs 返回所属小节；
- 纯向量检索，vs 向量 + 关键词混合检索。

重点看三个指标：

- **Recall@5**：正确内容有没有进前 5；
- **MRR**：正确结果排得越靠前越好；
- **错误领域率**：前 5 条里有多少是通用 IT 文档，而不是油机文档。

还要检查“相似但没用”的结果。例如用户问“退款多久到账”，系统召回了一段“退款条件”，向量分数可能很高，但它没有回答问题。这类问题要靠重排、上下文和评测集一起解决。

最后，别忘了测试更新和删除：文章改了以后，旧片段是否还在被召回？删除文章后，向量索引是否同步清理？权限变更后，旧向量是否还能被无权限用户搜到？这些都不是“能跑”能覆盖的。

## 十一、最小可行方案

如果现在要做一个能用的知识库，不建议一上来堆复杂能力。先跑通这条最小链路：

1. 用 PostgreSQL + pgvector，或者你已经在用的数据库的向量扩展；
2. 建 `documents` 和 `chunks` 两张表，原文和片段分开存；
3. 长文章按标题/段落切，500～800 字一块，重叠 50～100 字；短文章不切；
4. 每块补 1～3 行上下文：文章标题、章节路径、适用对象；
5. 选一个中文效果够用的 Embedding 模型，文档和查询共用；
6. 建 HNSW 索引，查询取 Top-5，并带权限和模块过滤；
7. 检索命中后返回父章节或相邻块，不要只给孤立片段；
8. 准备 30～50 个真实问题，标注正确片段，测 Recall@5 和错误领域率；
9. 先只处理一类文档，确认有效后再批量导入；
10. 等基线稳定后，再考虑混合检索、重排、语义分块和多模态。

回到最初的问题：向量数据库到底特殊在哪里？

它不是让数据库突然“理解”了人类语言，而是把“意思”提前变成可计算的坐标，再用近邻索引快速找出来。**Embedding 模型负责把内容放进坐标系，向量数据库负责在坐标系里找邻居，大模型负责把找到的内容讲成人话。**

理解了这三层分工，后面的分块、上下文、图片、选型和评测，就不再是一堆孤立的知识点，而是同一条链路上的不同环节。
