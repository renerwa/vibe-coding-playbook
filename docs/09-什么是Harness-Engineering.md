# 什么是 Harness Engineering（驾驭工程）

> 用途：解释 Harness Engineering 的定义、边界、组成和最小落地方法，并把它与 Agent、Runtime、Prompt Engineering、Context Engineering 对齐。
> 最后更新：2026-11-08
> 默认读者：有技术常识但非科班出身的产品经理。
> 前置阅读：[什么是 Agent](07-什么是Agent.md)、[什么是 Runtime](08-什么是Runtime.md)。
> 不覆盖：具体 Agent 框架实现、供应商产品对比、团队组织设计。

## 一句话结论

> **Harness Engineering 是把模型之外的上下文、工具、循环、权限、反馈和观测，当作一套可设计、可测试、可持续改进的工程系统。它的目标不是让模型“更聪明”，而是让 Agent 在真实任务中更可靠、可验证、可控制。**

如果只记一个公式：

> **Agent = Model + Harness**

模型提供理解和生成能力；Harness 决定模型看到什么、能做什么、做完后如何检查，以及出错时如何纠正。它关心的不是“模型能不能生成一段代码”，而是“模型做错时，系统能不能尽早发现、阻止或修复”。

这也解释了行业里常说的“人类掌舵，智能体执行”：人负责目标、边界和最终验收，Agent 在 Harness 中执行和迭代。

## 一、先把术语边界说清

### 1. Harness 的原意

Harness 原意是马具或安全束具，作用不是提供动力，而是把已有的动力约束到可控方向。借用到软件里，它通常指“包在执行对象外面、负责连接、约束和观测的一层支撑”。

它不是模型本身，也不是一个严格的学术分类。不同产品、团队和作者使用 Harness 时，范围会有重叠，因此更适合把它理解为**行业术语和工作视角**，而不是必须逐字统一的教科书定义。

### 2. 测试领域的 test harness

在软件测试中，test harness（测试夹具/测试运行框架）指让测试能够稳定运行的外围设施，包括测试数据、启动和清理步骤、测试运行器、断言和结果报告。

这个含义和 Agent 语境有共同点：**被测试的对象不是孤立的，它需要一套环境来执行、观察和判断结果。**

### 3. Agent 语境下的宽定义

在 Agent 语境中，Harness 常被宽泛地定义为“模型之外、让 Agent 能持续工作的全部工程支撑”。于是有：

> **Agent = Model + Harness**

这里的 Harness 可以包括系统提示词、项目规则、上下文组装、工具接口、执行循环、状态与记忆、沙箱和权限、人工审批、测试与评审、日志和评测。

这和本知识库已有的简化说法并不冲突。`Agent ≈ 模型 + 工具 + 循环 + 目标` 是便于理解的行为层公式；`Agent = Model + Harness` 则强调：工具、循环等都不是模型自带的，必须由工程系统提供和约束。

### 4. Harness、Runtime 和 Agent 各在哪一层

| 概念 | 主要回答的问题 | 典型内容 |
|---|---|---|
| Model（模型） | “如何理解和生成？” | 语义理解、推理、代码生成、自然语言输出 |
| Runtime（运行时） | “代码或 Agent 在哪里执行，能用哪些底层能力？” | 模型调用、工具执行、文件与进程、网络、状态管理 |
| Harness（驾驭层） | “怎样让模型在边界内可靠地完成目标？” | 上下文、工具设计、循环、权限、反馈、验证、观测 |
| Agent（智能体） | “最终表现出什么整体能力？” | 围绕目标自主判断、行动、根据结果继续调整 |

Runtime 更偏“执行底座”，Harness 更偏“控制与验证设计”。两者会重叠：许多 Agent Runtime 已经内置了一部分 Harness 能力。日常不必强行切开，只要知道**Runtime 提供能力，Harness 决定这些能力怎样被组织、限制和检验**即可。

### 5. 产品内置 Harness 与团队外层 Harness

| 层次 | 谁负责 | 常见内容 | 特点 |
|---|---|---|---|
| 产品内置 Harness | Agent 产品/平台 | 系统提示词、内置工具、上下文压缩、审批模式、沙箱、任务列表、子 Agent | 开箱即用，受产品能力限制 |
| 团队外层 Harness | 使用 Agent 的团队 | 任务模板、项目规则、仓库脚本、测试、CI、代码评审、评测集、发布门禁 | 贴近业务，需要持续维护 |

产品内置 Harness 决定“这个 Agent 的基本工作方式”；团队外层 Harness 决定“它在这个项目里怎样算做对”。可靠的实践通常不是二选一，而是先用好内置能力，再补项目特有的规则、验证和权限。

## 二、和 Prompt Engineering、Context Engineering 的区别

三个词不是互相替代的三代技术，而是关注点不同的层级。

- **Prompt Engineering（提示词工程）**：研究怎样表达指令、角色、示例和输出要求，让模型更可能给出想要的结果。
- **Context Engineering（上下文工程）**：研究在有限的上下文窗口（模型一次能看到的文本和信息范围）里，放什么、按什么顺序放、何时检索和压缩，让模型具备做对判断所需的信息。
- **Harness Engineering（驾驭工程）**：研究整个工作系统怎样让 Agent 持续做对，包括工具、循环、权限、验证和观测。

| 维度 | Prompt Engineering | Context Engineering | Harness Engineering |
|---|---|---|---|
| 核心问题 | 该怎么说？ | 该让它看到什么？ | 它怎样工作、受什么约束、如何证明做对了？ |
| 主要对象 | 单条指令、示例、输出格式 | 任务资料、历史、检索结果、记忆、压缩策略 | 上下文、工具、循环、权限、反馈、评测的整体组合 |
| 时间尺度 | 一次回答或一个短任务 | 一次任务内，必要时跨会话 | 多步骤、长任务和持续迭代 |
| 成功标准 | 回答更符合意图 | 信息足够且不干扰判断 | 结果可复现、错误可发现、风险可控制 |
| 典型产出 | 提示词模板 | 项目知识、检索规则、上下文组织方式 | 任务合同、验证命令、测试、权限策略、日志和人工门禁 |

以“修改订单导出接口”为例：

- Prompt 解决“请按什么格式修改、输出什么”；
- Context 解决“它是否看到了接口约定、字段定义、相关代码和历史决策”；
- Harness 解决“它是否必须读约定、能否运行测试、能否接触生产数据、测试失败后是否会自动修正、最后由谁验收”。

一句话区分：**Prompt 管表达，Context 管信息，Harness 管整个可控的工作闭环。**

## 三、为什么 2026 年开始被广泛讨论

核心原因是：模型能力提升后，瓶颈从“能不能做”转向“能不能稳定做完并证明做对”。

1. **任务变长，错误会累积**：模型可以连续执行很多步骤，但一次理解偏差可能被后续步骤放大。只靠重试，往往是在重复同一个系统性错误。
2. **生成速度超过人工审查速度**：代码写得越快，越需要自动化检查、清晰边界和可追溯记录，否则人会成为最慢的瓶颈。
3. **“看起来能跑”不再足够**：真实项目还需要权限、数据安全、回归、成本、可恢复性和长期维护。
4. **Agent 开始产生真实副作用**：改文件、跑命令、调接口、操作数据库之后，仅靠对话质量无法控制风险，必须在系统层加约束和验证。

社区普遍把 Harness Engineering 一词的流行追溯到 Mitchell Hashimoto 在 2026 年 2 月的提法。他的核心意思是：**发现 Agent 犯错时，不要只重试，而要工程化地让这类错误以后不再发生。**

OpenAI 在 2026 年的大规模代码实验报告中也采用了这一说法，重点不是写更长的提示词，而是设计环境、反馈回路和控制系统；可以概括为“人类掌舵，智能体执行”。Martin Fowler 站点在 2026-04-02 发表的 Birgitta Böckeler 文章，则把 coding agent 的 harness 拆成 guides（前馈控制）和 sensors（反馈控制），并区分 computational（计算型）与 inferential（推断型）检查。

这些来源的共同点不是发明了一个新模型，而是提醒团队：**当模型逐渐具备执行能力，工程重点会转向环境、反馈和控制。**

## 四、Harness 由什么组成

| 组成 | 作用 | 常见形式 | 缺失后的典型问题 |
|---|---|---|---|
| 上下文 | 让模型知道目标、约束和现状 | 任务说明、项目规则、接口文档、代码地图、示例、记忆与压缩 | 理解偏差、重复提问、改错范围 |
| 工具 | 让 Agent 能观察和行动 | 读写文件、搜索、终端、浏览器、API、数据库工具 | 只能“建议”，不能完成；或靠猜测代替事实 |
| 循环/编排 | 管理计划、执行、观察、重试和停止 | 计划—行动—观察循环、任务拆分、子 Agent、重试上限、终止条件 | 无限试错、跑偏、任务没有明确结束点 |
| 约束/权限 | 限制能做什么、花多少、何时必须问人 | 沙箱、允许/禁止列表、分支保护、预算、审批、密钥与数据隔离 | 误删文件、泄露数据、越权操作、成本失控 |
| 反馈/验证 | 判断结果是否满足要求 | 编译、类型检查、测试、lint、契约检查、截图比对、人工评审 | “看起来完成”，但没有可验证证据 |
| 观测/评测 | 让过程可追踪、可复盘、可改进 | 日志、工具调用记录、耗时与成本、评测集、失败案例库 | 同类错误反复发生，无法判断改动是否真的变好 |

状态和记忆通常横跨“上下文”和“循环”：上下文负责让当前决策看得到必要信息，循环负责在多个步骤之间保存和更新状态。

一个最小但完整的 Harness 不一定复杂，通常只需要：

- 一份说清目标、范围、验收标准的任务说明；
- 一份短小、项目特有的规则文件；
- 一条可复现的验证命令；
- 一组覆盖关键行为的测试或验收步骤；
- 一条明确的高风险操作边界；
- 一份能回看 Agent 做了什么、结果如何的记录。

## 五、核心方法：Guide + Sensor

Harness Engineering 最实用的抓手，是把控制分成两类：**前馈引导**和**反馈检查**。

### 1. Guide：行动前缩小错误空间

Guide（引导）是在 Agent 行动前提供的约束和方向，例如接口契约、代码范例、允许修改的目录、禁止使用的库、完成定义、必须遵循的流程。

好的 Guide 不是“请认真一点”，而是可判断的具体条件：

- 新增接口必须复用现有鉴权中间件；
- 导出字段和顺序以契约为准；
- 不允许修改数据库迁移；
- 完成前必须运行目标测试和完整测试集；
- 遇到生产配置或密钥，必须停下来请求人工确认。

### 2. Sensor：行动后检查真实结果

Sensor（传感器/检查器）是在 Agent 行动后读取真实信号，判断是否偏离目标。它可以是编译器、测试、类型检查、lint、契约校验、性能检查、日志、截图，也可以是代码评审和产品验收。

反馈要真正有用，至少要满足三点：

1. **及时**：在错误扩散前返回，而不是等到发布后。
2. **可行动**：说明哪里失败、期望是什么、下一步该查什么，而不只是“失败了”。
3. **回到 Agent**：结果要进入下一轮决策，形成“执行—检查—修正—复检”的闭环。

### 3. 计算型与推断型检查

| 类型 | 判断方式 | 优点 | 局限 | 例子 |
|---|---|---|---|---|
| 计算型（computational） | 由程序按固定规则判断，结果可重复 | 快、便宜、稳定、适合自动化 | 只能检查已被明确编码的规则 | 编译、单元测试、类型检查、lint、契约测试 |
| 推断型（inferential） | 由模型或人依据标准判断 | 能处理语义、设计和主观问题 | 有波动、成本更高、标准需明确 | 需求一致性评审、代码可读性评审、UX 验收 |

实践上应先用计算型检查守住确定性规则，再用推断型检查处理“对不对、好不好、是否符合业务意图”。两者不能互相替代。

### 4. 反馈必须形成闭环

```text
Guide（前馈规则/契约）
        ↓
Agent 执行动作
        ↓
Sensor（测试/检查/评审）
        ↓
可读的失败信号回到 Agent
        ↓
Agent 修正并复检
        ↓
人工验收或停止
```

如果测试结果只展示给人看，Agent 看不到；如果规则只写在文档里，没有检查器；如果 Agent 可以无限重试，却没有停止条件——这些都只是 Harness 的一部分，不是完整闭环。

一个简单的配对原则是：**每条重要 Guide 都应尽量配一个 Sensor。**

- “必须通过测试”配测试命令；
- “不能碰生产数据”配权限隔离和审批；
- “字段顺序必须一致”配契约测试；
- “代码要易维护”配评审清单或静态检查。

## 六、具体例子：新增订单导出接口

假设任务是在一个电商后台中新增“订单导出接口”：按日期范围导出 CSV，需要权限控制，单次最多 31 天，不能把大量订单一次性读进内存，字段和顺序必须符合约定。

### 没有 Harness 时

人只说：“新增订单导出接口，支持日期范围，导出 CSV。”

Agent 可能自行决定路由、字段名和日期格式；忘记权限校验；没有限制 31 天；一次性查询全部记录；只在本地手工点了一次页面；然后回复“已完成”。

问题通常不是它完全不会写，而是：

- 需求边界没有前馈，Agent 只能猜；
- 没有测试和契约，错误不会自动暴露；
- 没有权限边界，错误可能影响真实数据；
- 人说“再改一下”时，反馈只存在于聊天里，下一次还可能犯同类错误。

### 有 Harness 时

| 环节 | 具体做法 |
|---|---|
| Guide | 任务合同写明路由、查询参数、CSV 字段及顺序、权限规则、31 天上限、时区、空结果行为、禁止修改迁移文件；给出已有导出功能的参考实现 |
| 工具 | 允许搜索代码、读取规范、运行测试、访问测试数据库；不提供生产数据库凭据 |
| 循环 | 先读契约和相关代码，再列实施计划，先补失败测试，再实现，运行目标测试和完整测试集，检查差异后停止 |
| 约束 | 只在开发分支操作；禁止读取密钥、禁止直连生产、禁止数据库结构变更；超出范围必须提问 |
| 计算型 Sensor | 契约测试检查 200/400/403 和 CSV 表头顺序；权限测试检查无权限用户；边界测试检查 31 天；集成测试检查流式输出和空结果 |
| 推断型 Sensor | 人工评审字段含义、异常文案、查询方案是否合理，以及是否引入不必要的抽象 |
| 观测 | 记录执行过的命令、测试结果、修改文件和未解决风险，供人工复核 |

这时 Agent 如果字段顺序写错，契约测试会指出期望值；如果忘记权限，403 场景会失败；如果一次性加载全部订单，集成测试或代码评审会暴露问题。它可以先自行修正，再把“通过哪些检查、还剩什么风险”交给人。

有 Harness 不代表 Agent 永不犯错，而是**错误更早暴露、反馈能回到执行者、完成有证据、高风险动作有人把关**。

## 七、常见误区

| 误区 | 为什么有问题 | 更好的做法 |
|---|---|---|
| 工具越多越好 | 工具会增加选择歧义、权限面和维护成本，Agent 可能选错工具或绕过流程 | 只为当前瓶颈增加工具；优先让工具返回结构化、可行动的结果 |
| 写一份巨型指令文件，什么规则都塞进去 | 上下文被稀释，规则互相冲突，内容很快过期，Agent 难以判断哪条最重要 | 项目规则保持短小；通用知识用链接，任务特有约束放进任务合同，按需加载 |
| 只有规则，没有验证 | 规则只是 Guide，Agent 可能误解、遗漏或自称遵守 | 每条关键规则配一个 Sensor，例如测试、检查脚本或人工门禁 |
| Agent 说“完成了”就相信 | 自然语言汇报不是验收证据，尤其在长任务中容易漏改和误判 | 要求给出测试结果、关键输出、改动范围和残余风险；按完成定义验收 |
| 换一个更强模型来解决环境问题 | 测试不可靠、权限过大、反馈缺失是系统问题，换模型只能改善局部表现 | 先修 Harness：补验证、收权限、减少歧义，再评估是否真的需要换模型 |

## 八、给产品经理的最小落地建议

不需要一开始就搭平台。先做下面五件事，就足以覆盖大多数中小型 Vibe Coding 任务。

1. **每项任务写一页任务合同**：目标、范围内、范围外、关键约束、验收例子、允许修改的边界。产出物是可复用的任务模板。
2. **固定一条验证命令**：至少能运行相关测试；没有测试时，固定一套可复现的冒烟检查。要求 Agent 执行并贴出真实结果，而不是只说“应该可以”。
3. **维护一份 10—20 行的项目规则**：只写本项目容易踩的坑，例如测试命令、目录约定、禁止操作、必须复用的事项。不要复制一份百科全书。
4. **设置两个人工门禁**：高风险动作前确认，例如生产数据、密钥、迁移、外部支付；最终验收时检查证据和残余风险。低风险任务可以只做轻量差异审查。
5. **把每次失败变成一条 Harness 改进**：复盘时只问一句：“下次怎样让这类错误自动暴露或自动避免？”选择补规则、补测试、补工具、补权限或补观测中的一项，而不是只重试。

可以用下面这张表控制投入，避免过度工程化：

| 任务类型 | 最小 Harness |
|---|---|
| 一次性文案、低风险小改动 | 清晰指令 + 人工看差异 |
| 反复出现的代码任务 | 任务模板 + 一条验证命令 + 简短项目规则 |
| 多文件、长流程功能 | 计划与停止条件 + 自动化测试 + 权限边界 + 人工验收 |
| 金额、权限、数据迁移、生产配置 | 上述全部，再加独立评审、回滚方案和更严格的门禁 |

判断 Harness 是否变好，不看工具数量，而看三个信号：同类错误是否减少；Agent 能否自己发现并修正更多问题；人是否能把时间从“反复救火”转向“定义目标和验收”。
